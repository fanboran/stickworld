## 〇、文档目的

GDD 定义了"做什么"，本文档定义"怎么搭才不变屎山"。

P0 阶段三件事必须同时上线：
1. 火柴人行为 AI（特别是战斗 AI）
2. 小队级战斗（10-30 人）
3. 定居点建设基础逻辑

这三者高度耦合：工人建造时被袭击要切战斗 AI、战斗需要建筑作为掩体、建设需要建筑网格、战斗的编队直接复用组织系统的 L1 节点。本文档定义统一的场景骨架与模块边界，让三者各自开发但接口对齐。

## 一、设计原则（三条铁律）

### 1.1 逻辑层 ≠ 表现层

所有系统状态放在 `core/entities/` 的 State 对象里，**场景节点只是 State 的视图**。

- 火柴人 HP/位置/动画状态 → `StickmanState`
- 建筑血量/等级/占地 → `BuildingState`（新建）
- 战斗进度/参战双方 → `BattleState`（已有）
- 编制关系/指挥链 → `OrganizationState`（已有）

**场景卸载时 State 不丢**，挂载到新场景就能继续。这是支持"城镇就地变战场"、"快速旅行后状态延续"的基础。

### 1.2 常驻宿主 + 动态子场景

`GameRoot` 主场景常驻，村落/战场/室内都是动态加载的子场景。

- 环境、相机、UI、时间、输入分发跨场景保持
- 地图切换 = 替换 `WorldChunkHost` 的子节点

### 1.3 接口契约

模块间通信一律走 `api.gd` 或 EventBus。**任何 `get_node("../...")` 跨模块引用视为 Bug**。

依赖方向严格单向（见 §二 模块依赖图）。

## 二、模块依赖图（防循环依赖）

```
                    ┌──────────────┐
                    │  GameRoot    │ (常驻容器)
                    └──────┬───────┘
                           │
        ┌──────────┬───────┼────────┬──────────┐
        ▼          ▼       ▼        ▼          ▼
   Environment  Camera  SceneLoader  InputDispatcher  UIRoot
                           │
                           ▼
                    ┌──────────────┐
                    │  MapInstance │ (村落/战场/室内)
                    │  ├─PlacementGrid
                    │  ├─Buildings
                    │  └─StickmanEntities
                    └──────┬───────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
   construction        combat             organization
        │                  │                  │
        └──────────┬───────┴──────────────────┘
                   ▼
                units (StickmanEntity + AI)
                   │
                   ▼
               StickmanRig (已有渲染)
```

**单向依赖规则**：
- 上层依赖下层，禁止反向
- `units` 不直接调 `combat`，由 `combat` 通过 `units/api.gd` 拉数据+下令
- `combat` 不直接调 `construction`，通过 EventBus 通知（如建筑被破坏）
- 跨模块引用 → 走 `api.gd` 或 EventBus

## 六、已知问题与技术债（2026-07-18 审计）

> 本章节由对照代码实现的审计产生，按严重程度排序。每项含：现象、根因、影响、修复方案。
> 审计方法：grep 关键装配点 + 读取核心脚本 + 检查测试结果文件时效性。
> 修复后删除对应项。

### P0-1 🟡 Chunk 流式加载为空壳（中等，标题误导）

- **现象**：`SceneLoader.preload_chunk()` / `unload_chunk()` 只有 TODO 注释，直接 emit 信号不实际加载（见 [scene_loader.gd:236-246](file:///f:/VSCode/game-2/stick-world/modules/world/scripts/scene_loader.gd)）。
- **根因**：阶段 0.8 实际实现的是"地图间出口触发器切换"（`ChunkTrigger.target_map_id` -> `travel_to_map`），而非"地图内 Chunk 分段加载"。两者被混为一谈。
- **影响**：当前每张地图是整张一次性加载。P0 阶段单张地图足够小，性能可接受。但文档标题"Chunk 流式加载"有误导性，让人以为已实现。
- **修复方案**：
  - 文档已在本 v7 中修正措辞（[场景与战斗/地图与场景图.md](场景与战斗/地图与场景图.md) §3.2、阶段 0.8）
  - 代码暂不改，等真正需要大地图时再补全 `preload_chunk` / `unload_chunk`
  - 可考虑把 `preload_chunk` / `unload_chunk` 改名为 `_stub_preload_chunk` 或加 `push_warning("Chunk 流式加载未实现")` 避免静默失败

### P0-2 🟡 战略图闭环未完成（中等，close_strategic_map 半成品）

- **现象**：[world_map/api.gd](file:///f:/VSCode/game-2/stick-world/modules/world_map/api.gd) 的 `close_strategic_map()` 注释写"TODO: 完整实现需要恢复场景图的 CameraRig 和 InputDispatcher"，当前仅做 ModalOverlay 隐藏。`api.initialize(manifest_path)` 也是 TODO 占位。
- **根因**：战略图模块的数据加载和状态恢复未完成，当前依赖测试代码硬编码注入数据。
- **影响**：玩家从战略图 ESC 返回场景图时，CameraRig/InputDispatcher 状态可能不正确。战略图无法通过正式 `manifest.tres` 加载数据。
- **修复方案**：详见 [世界地图数据流.md](世界地图数据流.md) §8 未实现项清单。战略图侧的完整重构属于阶段 1 范围。

### P0-4 🟢 StickmanRig IK 日志噪音（轻微，体验问题）

- **现象**：[stickman_rig.gd](file:///f:/VSCode/game-2/stick-world/modules/units/scripts/stickman_rig.gd) 每次实例化打印约 18 行 IK 修改器详细信息（`[IK] stack.enabled = true...`）。5 个 NPC + 1 玩家 = 108 行日志。`stickman_entity.gd:171` 还有 `print("[StickmanEntity] foot_offset = ...")` 残留。
- **影响**：日志噪音严重，掩盖真正有用的输出。无法通过日志级别关闭（是 `print()` 非 `push_warning`）。
- **修复方案**：将 IK 日志改为 `push_warning` 或包在 `OS.is_debug_build()` 判断内；删除 foot_offset 的 print 残留。

### P0-5 🟢 开场 IK workaround 是 hack（轻微，技术债）

- **现象**：[stickman_entity.gd:176-193](file:///f:/VSCode/game-2/stick-world/modules/units/scripts/stickman_entity.gd) 前 0.25s 模拟向右移动触发 IK 解算，然后重置位置。
- **根因**：Skeleton2D + IK 修改器在 `_ready()` 后首帧未正确解算，需要"骗"一下 IK 让它工作。
- **影响**：功能正常但设计不优雅。若 IK 系统升级可能失效。
- **修复方案**：调研 Godot 4.x Skeleton2D + IK 初始化最佳实践，寻找根本解法。P0 阶段可接受 workaround。

### P0-6 🟢 ConstructionManager 硬编码数值（轻微，待数据驱动）

- **现象**：[construction_manager.gd](file:///f:/VSCode/game-2/stick-world/modules/construction/scripts/construction_manager.gd) 中 `width=2`、`total_work=10.0` 硬编码，注释写"将来从建筑配置表读取"。`config/buildings/buildings.tres` 存在但未被读取。`get_buildings_in_region` 不区分 region。
- **影响**：所有建筑行为一致（同样宽度、同样建造时间），无法体现建筑差异。
- **修复方案**：接入 `config/buildings/buildings.tres` 数据表，按 `def_id` 读取 `footprint_w` / `base_work` 等字段。

### P0-7 🟢 GdUnit4 未引入（规范冲突）

- **现象**：[workspace rule.md](file:///f:/VSCode/game-2/.trae/rules/rule.md) 强制要求"生成的任何功能代码，必须附带相应的 GdUnit4 单元测试"，但 [tests/README.md](file:///f:/VSCode/game-2/stick-world/tests/README.md) 明确写"项目暂时没有引入 GdUnit4 插件"，使用自研 `TestRunner` + `assert()`。
- **影响**：规范与实现冲突。自研测试框架功能有限（无 mock、无参数化测试、无 CI 集成）。
- **修复方案**：与创始人确认是否引入 GdUnit4。若引入，规划迁移路径；若暂不引入，更新 rule.md 的措辞为"建议"而非"必须"。

### P0-8 🟢 RefCounted 持有 Node 引用的生命周期风险（轻微，架构隐患）

- **现象**：
  - [organization_manager.gd](file:///f:/VSCode/game-2/stick-world/modules/organization/scripts/organization_manager.gd) `extends RefCounted` 但被当 Node 用（[game_root.gd:225](file:///f:/VSCode/game-2/stick-world/modules/world/scripts/game_root.gd) 直接 `new()` 不挂场景树）
  - [battle_ai_director.gd](file:///f:/VSCode/game-2/stick-world/modules/combat/scripts/battle_ai_director.gd) `extends RefCounted` 但持有 `BattleInstance`(Node) 引用
- **影响**：RefCounted 生命周期不与 Node 绑定，若被引用的 Node 被 `queue_free` 后 RefCounted 仍调用其方法，会访问已释放节点。当前靠 `is_instance_valid()` 检查规避，但设计上不够健壮。
- **修复方案**：长期应改为 Node 挂到场景树，或用弱引用（WeakRef）。P0 阶段 `is_instance_valid` 检查足够。

### P0-9 🟡 资源系统完全未接入（中等，代码写好但没插电）

- **现象**：`modules/resources/` 代码完整（ResourceManager 168 行 + api.gd 119 行），API 与 [模块API契约.md](模块API契约.md) §三完全一致，`config/resources/resources.tres` 定义了 7 种资源。但整个系统**完全孤立**：

  - [game_root.tscn](file:///f:/VSCode/game-2/stick-world/modules/world/scenes/game_root.tscn) 无 ResourcesApi 节点
  - 模块缺 `.tscn` 场景文件（`data/` 只有 `.gdkeep` 占位），不符合模块标准结构
  - `api.gd.setup()` 无人调用
  - grep 全项目：无任何消费方模块（construction/combat/technology/expansion/organization）调用 `resource_id`
- **根因**：资源系统是早期独立开发的模块，写完代码后未接入 GameRoot 装配流程。后续 construction/combat 等模块开发时直接跳过了资源消耗（各自注释"P0 不实现资源消耗"）。
- **影响**：建造不消耗资源、建筑不产出资源、战斗不消耗物资、UI 不显示资源数量。资源系统是"代码写好了但没插电"状态。
- **设计矛盾（⚠️ 2026-07-18 确认，字段未实际更改）**：
  - [经济变量表.md](file:///f:/VSCode/game-2/docs/设计/平衡/经济变量表.md) 写"没有基础价格"，但 `resources.tres` 每个资源有 `base_price` 字段 —— **已确认**：`base_price` 是"初始价格种子"，建议改名为 `initial_price`，但实际代码中 **`base_price` 字段名仍未修改**（见 [config/resources/resources.tres](file:///f:/VSCode/game-2/stick-world/config/resources/resources.tres)）
  - GDD 列 4 种基础资源，`resources.tres` 定义 7 种 —— **已确认**：以 GDD 为准，P0 只实现 4 种基础资源，加工品/奢侈品待 GDD §2.2 补充
  - `.tres` 的 `base_price` 字段需重命名为 `initial_price`（**未完成**），`res_food`/`res_iron_ingot`/`res_silk` 标记为 P0 不接入
- **修复方案**：见 [场景与战斗/建筑与定居点.md](场景与战斗/建筑与定居点.md) §9.4.5「P0 接入步骤（最小可用）」-- 4 步即可接通最小资源循环
- **优先级**：P0 后期。不阻塞当前阶段 0.9，但 P0 完整循环（GDD §核心循环 第5层"资源层"）需要它
