> 进度条（Minecraft 式：上条 = 总阶段，下条 = 当前阶段内部细分）。
> 分支 `agent/loading-ux`，worktree `.temp/loading-ux`。

   `show_loading(message, ratio, sub_ratio)` / `set_sub_progress(ratio)`，

   新增会开窗口的探针在 `_ready()` 首行加 `DevQuiet.apply_if_requested()`。

## 二、实测数据（headless 纯工时，机器负载高时约翻倍）

启动阶段临时打点（已移除）得到的三处不可分块冻结源：

| 块 | 工时 |
| --- | --- |
| `_ready` 之前的引擎/场景启动 | ~15s（最大块，且当前完全无进度提示） |
| `_bootstrap.setup()` 装配界面与子系统 | 2.2~3.2s 一整块 |
| 子阶段「初始建筑」 | 1.2~3.3s |
| 子阶段「村庄设施」 | 1.2~2.7s |

`scene_loader.load_map()` 本体仅 72ms——卡的不是它，是它触发的那几块。

## 三、下一步（批次 2 候选，按实测性价比排序）

1. **`_ready` 之前那 ~15s** 是当前最大且最无提示的一块，尚未定位（引擎启动 /
   主场景 / autoload / 主题生成都有可能）。需先分点打时间戳定位，再决定能否
   给加载屏更早的可见反馈。
2. **stage 2 内最重的那一步**：分帧后最坏卡顿 = 单步耗时，需测出是哪一步
   （UI 根实例化？某面板？）再决定是否进一步细分。
3. 「村庄设施」子阶段（`spawn_initial_warehouse` 等）尚无逐项上报，可补。
4. 若观感验收要求「副条也覆盖装配段」，需给 stage 1/3~7 补细分步。

## 四、关键决策与约束

- **加载不同步化是已文档化的主动放弃**（见 `loading_screen.gd` 头注 2026-09-11：
  线程加载 game_root 会与主线程 preload 竞态，实测三次事故——死锁/资源风暴/
  场景切空壳）。因此本任务只做**分帧**（让帧），不做线程化。
- 分帧会把「一整块同步」拆成 N 块 + N 次等帧，**总时长略增**（每帧 ~16ms ×
  步数），换来转圈不断流。这是刻意的取舍。
