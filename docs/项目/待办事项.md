## 低优先级（P2+）

- [x] **发布导出排除战略图 json**（2026-08-31 完成，前提已被修正）：原条目假设"玩家运行时永远命中同名紧凑 bin"——**实测该假设不成立**。Godot 不把 `.bin` 识别为资源，`export_filter="all_resources"` 下 bin 从不进包，只有 json 进，玩家端实际一直在走 json 慢路径（此前"数据紧致化"的性能收益在发布版本完全失效）。
  正确做法分两步，已写入 `stick-world/export_presets.cfg`：
  1. `include_filter` 显式纳入 `config/strategic_map/**/*.bin` —— 让 bin 真正进包（运行时主路径，原样序列化 `var_to_bytes`，比 json 解析快）；
  2. `exclude_filter` 只排除**有同名 bin 兜底**的 json（l1_world/l3_world/l3_city/l3_l1、l1_packs/\*\*、l2_packs/\*\*）；
  `color_map.json` 与 `l1_data.json` **无对应 bin，是运行时唯一数据源，必须保留**。
  另排除 `assets/_raw/*`（AI 生成原图）、`tools/*`、`tests/*`、材质 `reference/*`。
  实测：pck 由 120MB 降至 75.7MB，bin 100 个全部在包内。
  ⚠️ 注意 Godot 的 `**` 不匹配目录直接子级，根目录文件须单独列出。

## 地图编辑器方案探讨（待决策）

> 触发原因：当前地图用 Godot 场景（.tscn）存储，手动编辑效率低，需要专门工具。
> 关联架构文档：[`场景与战斗架构.md`](../技术/架构/场景与战斗架构.md) §三 地图系统

**核心问题：地图用什么格式存储？编辑器如何工作？**

### 待选方案

1. **直接修改场景文件**（当前方式）
   - 优点：Godot 原生支持，所见即所得
   - 缺点：手动编辑繁琐，无法批量生成，易出错

2. **独立编辑器程序**（@tool 脚本 / 独立 Godot 项目）
   - 编辑器输出结构化数据（JSON/自定义格式），游戏运行时转译为场景
   - 优点：可控性强，支持程序化生成参数
   - 缺点：开发成本高，需维护转译层

3. **Godot 编辑器插件**（@tool + EditorPlugin）
   - 在 Godot 编辑器内提供自定义 Dock，辅助放置地形/装饰/建筑点位
   - 输出 .tscn 或 .json
   - 优点：复用 Godot 编辑器能力，无需独立项目
   - 缺点：插件 API 学习成本

### 待决策问题

- 地图数据是否应该从 .tscn 迁移到 JSON/Resource 驱动（与 xlsx 数据驱动一致）？
- 地形/装饰/建筑点位如何参数化存储？
- Chunk 流式加载（阶段 0.8，实际为地图间切换）与编辑器输出格式的兼容性？
- 是否需要支持程序化生成（如噪波地形）与手工编辑混合？

### 决策时机

P0 阶段现有 6 张场景图（village_a / village_b / road_a_b / battlefield / forest_zone / mega_interior），直接编辑 .tscn 足够。
当地图数量超过 10 张或需要程序化生成时，再启动编辑器方案设计。**不阻塞当前开发**。
