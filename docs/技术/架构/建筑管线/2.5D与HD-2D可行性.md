# 2.5D 与 HD-2D 可行性

> **一句话**：2.5D「3D 场景 + 烘焙建筑纸片卡 + 真 3D 光照」已由可复跑原型验证为**有条件可行**（2000 卡 + 200 点光仅 5.32 ms @ RTX 3050 Laptop）；创始人新提的 **HD-2D（2D 角色挂在 3D 场景里）** 路线判定**适配，但必须走"SubViewport 渲染 2D 火柴人 → 空间卡材质"这条路**，才能保住现有 2D 骨架/IK/批渲染/武器挂点/y-sort 全部遗产。

## 一、结论摘要

### 1.1 2.5D 原型：**有条件可行**

**判定**：可行。原型把 v3 建筑管线产出的真实 PBR 建筑，用 Blender 正交相机（yaw=0°、俯角 20°）烘成透明底 RGBA 纸片卡，贴进 Godot 3D 场景（正对相机的 quad），并让**真方向光 + 真点光源 + 真阴影**在卡上生效。三档昼夜出图与三级压力测试全部跑通。

**依据（实测数据，非推断）**：

| 依据 | 数值 | 出处 |
|---|---|---|
| 三级压力测试（2000 卡 + 200 点光） | 5.32 ms（188 fps），draws 1845 | `user://logs/godot2026-09-13T18.10.28.log` |
| 引擎侧零新增渲染框架 | 只用 QuadMesh + 1 个 spatial shader + OmniLight3D + WorldEnvironment | `proto_25d.gd` / `card.gdshader` |
| 资产零改造成本（卡路线） | 现有建筑库直接烘卡，无 UV 展开/贴图烘焙 | `blender_proto.py` |
| 昼夜三档 | 白天/黄昏/夜晚同一套卡 + glow 层 + 点光能量切换 | `proto25d_{day,dusk,night}.png` |

**「有条件」的三条前提**：
1. **卡路线可行** ≠ **glb 实模路线可行**。glb 导出的程序化材质不随 glTF 转移，只剩纯色回退（见 §3.5）——真模路线必须先补「UV 展开 + 贴图烘焙」工序。
2. **光照纪律**：卡里已含白天光照，场景环境光 + 太阳的总和必须 ≈1.0，否则光照算两遍直接过曝（见 §3.2）。
3. **伪法线是必选项**：平面卡法线处处相同，不做伪法线则点光只能整体调亮调暗，等于没有 3D 光照（见 §3.3）。

### 1.2 HD-2D（2D 角色 + 3D 场景）：**适配，但角色必须走 SubViewport 抬升**

**判定**：路线可行且方向正确，但「2D 角色如何进 3D 场景」有三条路线，**只有路线 ① 能保住现有 2D 火柴人管线**；若选路线 ②（3D 胶囊+骨架重做），则现有骨架/IK/批渲染/武器挂点全部作废重写（§5.1 重点论证路线 ①）。

**适配性依据**：
- 现有火柴人渲染是 **Skeleton2D/Bone2D + TwoBoneIK + 4× MultiMeshInstance2D 批渲染**，全部是 `CanvasItem`（2D 渲染域）——`SubViewport` 恰好是"2D 画布 → 纹理"的官方出口，**零改动即可整体搬入**。
- 现有建筑已是「贴图与占地解耦的 Sprite2D」（见 §4.5），与"烘卡贴 quad"同构，迁移成本低。
- 唯一真正贵的是**场景宿主**：现有 GameRoot 是 `Camera2D + Node2D` 的 2D 树（`y_sort_enabled` 排序），HD-2D 必须换成 `Node3D + Camera3D(正交)` 的 3D 宿主（§4.2）。

**一句话给创始人**：2.5D 这条路的资产（v3 PBR 建筑、昼夜光照标定）**不是白费**——它是 HD-2D 的**前置素材源**；HD-2D 相对 2.5D 原型，主要新增的是"角色怎么进 3D"这一件事（§5）。

## 三、实测数据

### 3.1 性能三级（最终有效跑，2026-09-13 18:10）

环境：Godot 4.7.2 stable(steam) / D3D12 12_0 / Forward+ / **NVIDIA GeForce RTX 3050 Laptop GPU** / 1920×1080 / vsync 关 + `Engine.max_fps=0`。出处 `user://logs/godot2026-09-13T18.10.28.log`：

| 档位 | 帧时 | fps | 窗口内 med | p95 | max | draws | prims |
|---|---|---|---|---|---|---|---|
| **200 卡 + 20 点光** | **3.77 ms** | 265 | 3.70 | 4.76 | 10.98 | 905 | 1410 |
| 800 卡 + 80 点光 | 4.46 ms | 224 | 4.17 | 6.67 | 8.38 | 1845 | 2690 |
| 2000 卡 + 200 点光 | 5.32 ms | 188 | 5.56 | 6.67 | 7.36 | 1845 | 2690 |
| 0 卡 + 0 点光（基线） | 2.38 ms | 421 | 2.35 | 2.78 | 13.49 | 5 | 10 |

**结论**：2000 卡 + 200 点光的成本约 2.94 ms 增量（5.32 − 2.38），完全在 16.6 ms 预算内；点光（含 1/5 投影）不是瓶颈。

**必须记录的两条测试纪律**：
1. **vsync 会让所有档位读数相同、完全无信息量**。18:05 那轮 vsync 未生效（被 144 Hz 刷新率钉死）：A/B/B2/C 四档**全部** 6.90 ms / 145 fps，连"0 卡基线"也是 6.90 ms（`godot2026-09-13T18.05.06.log`）；18:07 轮被钉在 10.00 ms / 100 fps（`godot2026-09-13T18.07.00.log`）。所以性能档必须在 `Engine.max_fps` 与 vsync 都关掉之后读。
2. **800 与 2000 两档 draws/prims 相同（1845/2690）**，提示上一档的 `queue_free()` 延迟释放 / 批合并影响了计数，**2000 档的 draws 数值应谨慎采信**；帧时趋势（4.46 → 5.32 ms）仍单调有效。

### 3.2 光照双计问题（2.5D 第一号坑）

**现象**：卡是"已经带光照的烘焙图"。如果场景再把环境光 + 太阳按正常强度照上去，等于把光照算两遍。实测把环境光能量 1.0 + 太阳 1.5 直接**过曝成灰白**，观感"不是 2D 那张图了"。

**纪律**（`proto_25d.gd:_apply_mode()` 顶部注释与代码）：
- 环境光能量 + 太阳能量**总和必须 ≈1.0**（原型白天档取环境光 0.45 + 太阳 0.70；黄昏 0.26 + 0.42；夜晚 0.10 + 0.05）。
- 色调映射必须 `TONE_MAPPER_LINEAR`（exposure=1.0 / white=1.0）。任何 filmic/ACES 都会把卡压灰——**2.5D 的第一原则是卡的像素别被二次改造**。

### 3.3 伪法线开关（`relief`）

**问题**：平面 quad 的法线处处相同 → 点光/太阳只能把整张卡**整体**调亮调暗，做不出"窗边亮、檐下暗"的逐像素明暗，等于没有 3D 光照。

**解法**（`card.gdshader`）：用 albedo 亮度的**一阶差分**现场伪造切空间法线——`lx/ly` 为中心差分，`n = normalize(vec3(-lx*relief, ly*relief, 1.0))`，经 TBN 变换后点光即可在卡上打出**浮雕式明暗**。代价：每像素多 4 次采样（±x/±y）。

**开关**：uniform `float relief : hint_range(0.0, 40.0) = 9.0`；原型取 `4.5`。`relief = 0` 即退化为平面法线（无 3D 明暗）。这是纸片路线的观感命门，也是**将来让 2D 角色卡吃 3D 光照的同一套机制**（§5.1）。

### 3.4 `depth_prepass_alpha` 消矩形影

**问题**：透明底 quad 若不加处理，**整张 quad（含透明区域）都会往地面投一个矩形黑影**——这是纸片路线最容易被忽略的坑。

**解法**：`render_mode cull_disabled, depth_draw_opaque, depth_prepass_alpha, ...`。`depth_prepass_alpha` 让深度/阴影 pass 也吃 ALPHA 裁剪（配合 `alpha_cut=0.4` + `discard`），剪影阴影才成立。原型白天图中建筑投在石板路上的阴影边缘是建筑剪影而非矩形，即此项生效。

### 3.5 glb 导出：能导出，但**不能交付可用带材质资产**

**事实**（`build_report.json` + `blender_proto.py` 头注 + Godot 侧 `GLB_COLORS`）：
- 导出**成功**：`proto25d_buildings.glb` 2.07 MB，30470 三角面，29 个"唯一材质"。
- 但**程序化材质（材质节点树/纹理烘焙链）不随 glTF 转移**：glb 里只剩纯色回退，材质名甚至出现 `flat_shadow_*` / `flat_fire` 这类**回退材质的名字**（`build_report.json` 的 `unique_materials` 诚实清单）。Godot 侧只能靠 `GLB_COLORS` 表按材质名硬映射近似色——`proto25d_glb_day.png` 里那排"糊成一块颜色"的房子就是该路线的真实水平。
- **导出耗时约 313 s**（原型会话记录；本仓库未保留 Blender stdout 原始日志，此条为**转录**）。
- 另有一个坐标坑：glb 的 `scale` 已烘进网格数据，但节点的 `translation.x` 仍是 Blender px——所以 Godot 侧**不信任 glb 的 translation，位置一律重设**（`proto_25d.gd:_spawn_model()`）。

**结论**：走 glb 真模路线，**必须先新增一道工序：UV 展开 + 程序化材质烘焙成贴图（basecolor/normal/roughness）**，否则只是"低模色块"。相比之下**烘卡路线零新增工序**，这是原型选卡为主验证对象的直接原因。

### 3.6 其他记录

- **一次自检报错**（`godot2026-09-13T17.56.09.log`）：`Parse Error: Cannot infer the type of "fps"`（`proto_25d.gd:672`），已修复；保留作"性能统计代码也要过类型推断"的教训。

## 四、改造盘点（现有系统 → 2.5D/HD-2D）

代价等级：**低** = 局部新增，不动现有语义；**中** = 需要新桥接层/接口改造；**高** = 架构级替换或重写。

### 4.1 火柴人渲染管线 — **代价：路线①低 / 路线②高**

**现状**（`modules/units/scripts/rig/`）：
- `stickman_skeleton.gd`：`Skeleton2D + Bone2D`，五链 z 栈描边/填充双表，z ∈ [−3, +6]，`OUTLINE_SCREEN_PX` 屏幕像素描边补偿。
- `stickman_batch_rig.gd`：4× `MultiMeshInstance2D` 批渲染（stroke_rects / stroke_caps / fill_rects / fill_caps），把 15 段肢体从 30 draws/单位压到 4 draws/单位；骨架/动画/IK/`ProceduralOverlay` 全程照旧；武器/盾 = 挂手骨的 `Sprite2D`；`ContactShadow` / `HealthBar` / IK markers 是 rig 下继承的 `CanvasItem`。
- 关键：**全部是 `CanvasItem`（2D 渲染域），且必须挂在 rig 下以继承"实体 y-sort + `rig.scale.x` 翻转"**。

**要改什么**：取决于路线（§5.1）。
- 路线 ①（SubViewport）：把整棵 2D rig 渲染进一个（共享）SubViewport，输出纹理贴到 3D 空间 quad 上，quad 挂 spatial 材质（albedo + 伪法线 + alpha）→ 3D 光照/阴影自然生效。**2D 代码零改动**。
- 路线 ②（3D 重做）：`Skeleton3D + Bone3`/胶囊网格重写，IK/五链 z 栈/批渲染/描边公式全部作废。

**能否保留**：路线 ① **全保留**（骨架/IK/多段批渲染/武器挂点/y-sort 全留在 2D 域）；路线 ② **零保留**。

### 4.2 场景宿主 — **代价：高**

**现状**（[场景宿主架构.md](场景与战斗/场景宿主架构.md)、[地图与场景图.md](场景与战斗/地图与场景图.md)）：
- 主场景骨架 `GameRoot`：`CameraRig(Camera2D)` 水平卷轴跟随/缩放/震屏（单脚本实现）+ `EntityHost`（`y_sort_enabled`，Y 越大越靠前）+ `BuildingHost` / `TerrainBuildings`（也 `y_sort_enabled`，按基线排序）+ `WalkBarrier`（`StaticBody2D`）+ `CanvasLayer` UI。
- 地图分五类 `MapInstance`（Village/Battlefield/Road/Indoor/MegaInterior）。

**要改什么**：HD-2D 必须把宿主换成 `Node3D + Camera3D(正交)` 的 3D 组合根（原型即最小示例）。`y_sort_enabled` 由 **3D 深度缓冲 + 显式 z 位置**取代；`CameraRig` 的 `set_ground_y` / `set_map_bounds` / `zoom` / `shake` 全部要在 3D 下重做语义（正交尺寸缩放、相机偏移、贴地平面）。

**能否保留**：`MapInstance` 数据契约、`y_sort` 的"排序意图"→ 保留；`Camera2D`/`Node2D` 宿主 → 替换。

**代价判断**：这是 HD-2D 的**最大工程**，也是"2.5D 原型 vs 正式引擎"的鸿沟所在。原型没做的事：地图分块流式加载、相机跟随、震屏、室内切换——这些都要在 3D 宿主上重建。

### 4.3 世界空间 UI — **代价：中**

**现状**（[UI.md](场景与战斗/UI.md) §10.6）：建筑头顶双进度条、火柴人头顶动作进度条、血条（`health_bar_indicator.gd`）、伤害/飘字（`procedural_overlay.gd extends Node2D`）、交互弹窗——都挂在实体下的 `Node2D`/`Control`，靠 2D 世界坐标显示。

**要改什么**：3D 宿主下有三条出口——① `Label3D` / `Sprite3D` 直接做世界空间；② billboard quad 贴 SubViewport 纹理；③ 留在 2D `CanvasLayer`，用"世界→屏幕"投影手动跟随（工程里 `DebugOverlay` 已有 `world_to_screen` 公式先例）。

**能否保留**：逻辑层（显示什么/何时显示）不动；**渲染出口**要按上述三选一改造。

### 4.4 战略图 — **代价：低 / 可不动**

**现状**（[战略图架构.md](战略图架构.md)）：`modules/world_map` 是**鸟瞰多边形领土**，玩家不在其中；`Control`/`Node2D` 的多边形渲染，8192×8192 三级粒度数据 + Shader 化渲染器。

**要改什么**：**原则上不动**。2.5D/HD-2D 作用于"玩家所在的场景图（world/combat）"，而战略图是另一类地图模式，继续 2D 多边形渲染即可。**建议把战略图明确划在本次引擎方向的范围之外**——这是省掉一大块风险的边界。

### 4.5 建筑资产 — **代价：卡路线低-中 / glb 路线高**

**现状**（[建筑与定居点.md](场景与战斗/建筑与定居点.md)）：`building_gen` 用 `Sprite2D` + `Polygon2D` + CPU 生成纹理（`make_thatch_layered` / `StoneBrickGen`）搭建筑；**贴图与占地解耦**（贴图可超出占地，如树冠）；占地走 32px 网格 `PlacementGrid`；碰撞走 `PassageBarrier` 下的 `CollisionShape2D`。

**要改什么**：
- **卡路线**（推荐过渡）：v3 烘的 `<def>_w<N>.png` 直接**替换现有建筑 Sprite2D 的贴图**——同构、低成本、保留 2D 占地/碰撞语义。
- **glb 路线**：先补 UV 展开 + 贴图烘焙（§3.5），再把碰撞从 2D `CollisionShape2D` 重建到 3D。

**能否保留**：卡路线保留占地网格/`PassageBarrier`/贴图-占地解耦全部约定；glb 路线需重建碰撞。

### 4.6 碰撞寻路与深度排序 — **代价：中**

**现状**（[寻路避障调研.md](寻路避障调研.md)、[战斗与AI.md](场景与战斗/战斗与AI.md)）：
- 移动 = `CharacterBody2D` + 每帧直线指向 + `move_and_slide`；碰撞 layer=2 / mask=3；脚部碰撞盒约 41.5×12 px。
- 障碍 = 两级 `StaticBody2D`（地图级 `WalkBarrier` + 建筑 `PassageBarrier`）。
- 寻路 = `NavigationServer2D` / `AStarGrid2D` **工程内零命中，纯绿地**；地图本质 **1.5D（9 条泳道）**；现行推荐"分期落 C"（P0 局部避障 + P1 AStarGrid2D 兜底）。

**要改什么**：核心决策是**角色的物理留在哪里**。
- 若角色继续走路线 ①（2D 域），则碰撞/寻路**可整体留在 2D**——3D 场景只做视觉，另起一个平行的 2D 物理世界承载 `CharacterBody2D`，或把 3D 几何投影回 2D 平面生成障碍。**代价中（是设计决策，不是代码量）**。
- 若追求真 3D 物理（z 轴命中判定），则 1.5D 泳道模型的假设全部推翻，代价高。
- **深度排序**：`y_sort`（Y 越大越前）→ 3D 深度。在 20° 俯角正交相机下，世界 z 会投影进屏幕 y，所以"前后排"依然可分（原型前排 z=0 / 后排 z=−26 层次分明）；但**卡与卡之间的透明排序**需要显式 `render_priority` 或 z 偏移，不能只靠 y-sort。

## 五、HD-2D 方案

### 5.1 「2D 角色如何进 3D 场景」三条路线

| 路线 | 做法 | 现有 2D 管线 | 观感上限 | 代价 | 判定 |
|---|---|---|---|---|---|
| **① SubViewport → billboard/quad** | 2D rig 渲染进 SubViewport，输出纹理贴在 3D 空间 quad 上，quad 用 **spatial 材质**（albedo + 伪法线 + alpha）吃 3D 光照 | **全保留** | 高（可吃到真光照/真阴影/景深） | 中 | **推荐** |
| ② 3D 胶囊 + 骨架重做 | `Skeleton3D` + 胶囊/网格，3D 骨骼动画 | 全部作废 | 最高（真 3D 阴影/布料/武器） | 高 | 仅在需要真 3D 命中判定时考虑 |
| ③ 逐帧烘焙角色图集 | 每动画每帧烘成雪碧图，`Sprite3D` 播放 | 2D 运行时逻辑作废，只留美术 | 低-中（不可 React 光/程序化叠加） | 中（制作）/低（运行时） | 作远景/LOD 备选 |

#### 重点论证：路线 ① 为什么能保住现有 2D 火柴人管线

1. **渲染域天然兼容**。现有 rig 的每一件东西——`Skeleton2D`/`Bone2D`、`TwoBoneIK` 修改器、`AnimationTree`、`ProceduralOverlay`、4× `MultiMeshInstance2D` 批渲染桶、挂手骨的武器/盾 `Sprite2D`、`ContactShadow`、血条——**全部是 `CanvasItem`**。`SubViewport` 的存在意义就是"把一棵 2D 画布渲成纹理"，**把根节点从场景树挪进 SubViewport 即完成迁移，业务代码一行不改**。
2. **骨架/IK 不被破坏**。`Skeleton2D` 的修改器绑定、`local_pose_override` 渲染时序、五链 z 栈、描边屏幕像素补偿——这些都在 2D 画布内结算，SubViewport 只是"换了一块更小的屏幕"，不改变任何结算语义。
3. **多段批渲染照旧**。4× `MultiMeshInstance2D` 仍挂在 rig 下、仍在 2D 画布内合并 draw call，SubViewport 不破坏 MultiMesh 的批语义。
4. **武器挂点照旧**。武器是挂手骨的 `Sprite2D`，随骨骼走；进 SubViewport 后同样只是画布内一个子节点。
5. **y-sort 语义可平移**。单位**内部**的层序由 rig 的树序/z 栈决定（不受影响）；单位**之间**的遮挡改由 3D 里 quad 的深度/z 位置决定——把"Y 越大越前"映射为"世界 z 越靠近相机"，排序意图完全保留。
6. **与已验机制同源**。`card.gdshader` 已证明"平面 quad + 伪法线 + spatial 材质 = 吃到真点光/真阴影"；角色卡只是把 albedo 从"静态烘焙图"换成"SubViewport 实时纹理"，**渲染机制不变**。

#### 路线 ① 的三个真风险（必须提前设计）

1. **每单位一个 SubViewport 会爆**。96v96 时不可能的。正解 = **共享图集 SubViewport**：把 N 个 rig 排布渲染进一张大图（网格排布），每个 3D quad 只采自己那一格（UV offset/scale）；再配 LOD 距离剔除、姿态不变帧跳过重烘（现有 `mark_dirty` 管线可复用）。
2. **3D 光照对 2D 角色的"接缝"**。SubViewport 里的 2D 角色不知道自己身处什么 3D 光照下。桥接方案：角色 quad 的 spatial 材质用**伪法线 + 环境色注入**（把角色所在世界位置的光照采样成 tint/ambient 参数传给材质），否则角色会"贴"在场景上、不融光。**这是 HD-2D 成立与否的关键工程**。
3. **透明排序与 alpha 边缘**。卡与卡、卡与 3D 几何的透明排序需显式处理（`render_priority` / 深度写入策略）；SubViewport 的 alpha 边缘在缩放时需 mipmap + 合适的 `alpha_scissor`。

### 5.2 HD-2D 后处理配方与观感增量

Godot `WorldEnvironment`（`Environment`）+ 可选 `CompositorEffect`/全屏后处理 shader。原型已启用其中的辉光与雾：

| 配方 | 做法（Godot） | 观感增量 |
|---|---|---|
| **辉光 Bloom** | `glow_enabled`（原型：intensity 0.8~1.0、bloom 0.10、HDR threshold 1.1） | **HD-2D 的第一观感来源**：夜里窗户/灯笼/炉火出光晕，冷夜 + 暖光斑的对比立刻成立（见 `proto25d_night.png`） |
| **景深 DOF** | `dof_blur_far/near_enabled`，焦距锁前排街 | 前排行清、后排渐虚 → 微缩景观/层次纵深，是"3D 场景"读感最强的线索 |
| **暗角 Vignette** | 全屏 shader / `Environment` + 后处理层 | 压暗四角、聚焦画面中心，抵消正交平铺的"无焦点"感 |
| **轻微移轴 / 上下渐糊** | 全屏 shader：屏幕顶部（天空）与底部（前景地面）各做渐入模糊 | 便宜的纵深线索，替代/补强 DOF；让"街排"有前后站位感 |
| **色调映射 Tonemap** | **必须 `TONE_MAPPER_LINEAR`**（§3.2）；色彩分级另用后处理 shader 做，**不要动 tonemapper** | 保住卡/角色的原始像素；任何 filmic/ACES 都会把 2D 资产压灰 |
| **雾 Fog（深度）** | 原型已用 `FOG_MODE_DEPTH` 60→420 | 纵深分层、后排退远；配合昼夜色可做"晨雾/夜色" |
| **粒子 + 体积光** | `GPUParticles3D`（尘埃/飞虫/落叶）+ `OmniLight3D` / 体积雾做窗光 God-ray | 让 3D 场景"活"起来，是静态卡最缺的动态层；体积光是 HD-2D 宣传图的标志元素 |
| **真方向光 + 真阴影** | `DirectionalLight3D` + 接触阴影（已验：`depth_prepass_alpha` 出剪影影） | 建筑/角色投剪影影 → 资产"坐"在地面上而不是飘着 |

**配方纪律**：全部后处理都要服从 §3.2——**资产像素优先，后处理只做"氛围叠加"，不做"重照明"**。

### 5.3 分阶段落地方案

| 阶段 | 内容 | 可交付验证物 | 风险 / 止损点 |
|---|---|---|---|
| **阶段 0（已完成）** | 2.5D 原型：离线烘卡 + 3D 街排 + 昼夜三档 + 性能档 | 本档 §七 六张图 + `cards.json`/`build_report.json` | — |
| **阶段 1：单场景垂直切片** | 3D 宿主最小版（一个村庄街排）+ 建筑烘卡上位 + **1 个英雄角色走共享 SubViewport 图集** + spatial 卡材质（伪法线+环境色桥接）+ 辉光/暗角/移轴 | 30 s 可玩片段：英雄在 20° 俯角街排里走动；1080p 下 130px 火柴人比例、26 px/格可读性不降 | 若"角色不融光、像贴上去"无法解决 → **止损：退回 unshaded + 烘死的环境色 tint**（接受"平面但干净"），或评估路线 ③ |
| **阶段 2：系统扩量** | 96v96 规模：共享图集 + LOD（远景走路线③烘焙帧/无阴影 billboard）+ GPU 粒子 + 雾 + DOF | 目标硬件 96v96 ≥30 fps；draws/带宽预算表 | 若 SubViewport 图集带宽顶爆帧预算 → 降图集分辨率 / 大规模单位降级到路线 ③ |
| **阶段 3：全量迁移** | 建筑 v3 产线接 `assets/buildings/gen/` + 碰撞重建（或 2D 物理平行世界）+ 世界空间 UI billboard + 存档/读档 | 完整游戏循环可玩 + 存读档通过 | 逐地图迁移（Village→Battlefield→Road→Indoor），一张地图一张地图上线，可随时停 |

**阶段划分原则**：每个阶段都**独立可看/可退**；阶段 1 的验证物是"观感是否成立"，阶段 2 的验证物是"规模化是否扛得住"——观感不成立就不进入扩量。

## 六、与既有硬约束的冲突检查

硬约束（交接档 §0.3）：**纯正面 + 俯角 20° 微俯视，禁水平偏航**；宽度 = 单位宽 4 格的整数倍；米制比例（1 格 0.42 m，火柴人 130 px）。

### 6.1 失效的 3D 手段

| 手段 | 为什么失效 |
|---|---|
| **视差（水平视差/多层视差）** | 视差依赖相机的水平位移或偏航改变投影；yaw 锁死 0°、正交投影下水平移动不产生新信息 → 水平视差无意义 |
| 转台/环绕展示（orbit / turntable） | 禁水平偏航 → 看不到建筑侧面/背面，3D 造型的三维信息只走"俯角"这一自由度 |
| 3/4 视角的斜向景深线索 | 无偏航 → 只有 y（纵深）一个深度轴可用，斜向的深度分离做不出 |
| 侧面/背面几何价值 | 相机永远只看正面；建模侧背面的投入在游戏内视角下零回报（鸟瞰配图另算） |

### 6.2 仍然有效的 3D 手段

| 手段 | 为什么有效 |
|---|---|
| **真方向光 + 真阴影** | 与偏航无关；`DirectionalLight3D` + 剪影阴影已验（§3.4），建筑"坐"在地面上 |
| **真点光/灯笼光** | 已验：2000 卡 + 200 点光 5.32 ms；夜里窗光/灯光在地面投暖色光池（`proto25d_night.png`） |
| **后处理全家桶** | 辉光/暗角/DOF/移轴/色调映射/雾，全部是屏幕空间或深度缓冲操作，与相机偏航无关 |
| **纵深（z 深度）** | 20° 俯角把世界 z 投影进屏幕 y → 前后排仍可分层（原型前排 z=0 / 后排 z=−26 层次清楚），只是**不能靠"换角度"增强** |
| **体积光 / 粒子** | 屏幕空间/体积渲染，不依赖偏航 |
| **程序化天空 + 昼夜光照** | 已验：三档昼夜天空/太阳/雾/glow 全切换（`proto25d_{day,dusk,night}.png`） |
| 地面反射/湿滑屏空 | 屏幕空间反射，与偏航无关 |

**一句话**：硬约束砍掉的是"**用相机运动换纵深**"这一类手段，砍不掉"**用光照/阴影/后处理/深度**换纵深"这一类——而后者恰好是 2.5D/HD-2D 的核心，所以方向不冲突。

## 八、HD-2D 场景重排结果（2026-09-13 晚，第二轮）

按创始人多轮纠偏后重排（提交 `1bb80d47`，场景 `tests/dev/proto_hd2d/`）：

- **地面语义**：下方 39%（ground_ratio 区间内）= 整体可行走区；横贯路肩带已删；地面一整片（街心石板→两侧夯土→外缘草皮）；每栋建筑自带落地裙边+门前踩踏径；建筑基线=地平线+96px（公式反解验证）。
- **站位抖动**：33% 回退 0.5~1.5 格（带门前径）、15% 凸前、其余贴线。
- **多样性**：cottage/shop/bakery/house/smithy1/townhouse/tavern 混排，四种屋顶；间距 1~3 格为主+空当摆 28 张道具卡（`bake_props.py` 只读烘自 props.py）。
- **背景**：三层稀疏建筑逐层模糊（1.6/4.0/9px，卡片 shader `blur_radius`，Environment DOF 已关——只有近/远两档不够用）+ 城墙塔楼 + 远山树线 12px，地平线盖死；主排与角色 0 模糊。

### ⚠ 待创始人拍板：零偏航与侧翼

「回退建筑的侧翼可见」在**零偏航约束下几何不可实现**（正对相机的平面卡没有侧面）。选项：①接受无侧墙；②只为回退建筑放开 ±几度偏航。

### 遗留

夜景树线/草皮偏亮；程序化云呈横向条带；地面分区边界偏直（占位手段，等分段素材整段替换）；2D 角色光照仍是 tint/加色近似（非逐像素耦合）；角色 `depth_draw_never` 在高深度背景前有 DOF 误糊风险（量产按场景校准）。
