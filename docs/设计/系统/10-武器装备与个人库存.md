# 武器装备系统与个人库存（正式设计）

> **状态**：架构设计定稿，待分期实施（分期见 §十）。实施前重读 §九模块结构与 §十依赖关系。

## 一、创始人原始需求（口述记录，2026-09-06）

> 「记载一下武器装备系统了，而且每个火柴人都要独立的特定记录了……就是每个角色现在
> 都有自己背包和穿戴的装备栏了。」

拆解为三条硬需求：

1. **武器装备系统**立项（此前仅 `StickmanState.equipment` 预留字段，无系统设计）。
2. **每个火柴人都有独立的特定记录**——个体不再是纯数值模板的实例，而是有独立档案的实体。
3. **每个角色拥有自己的背包 + 穿戴的装备栏**——库存（背包）与装备（栏位）是个体数据结构
   的一等公民，不是组织/仓库级的聚合资源。

## 二、设计总览

### 2.1 三个核心决策

| 决策 | 内容 | 为什么 |
|------|------|--------|
| **模板/实例分离** | `ItemDef`（Resource，Excel→.tres 管线）定义物品；个体只存轻量条目 `{def_id, 耐久, 数量}` | 照抄建筑模块成熟先例（`BuildingDef`/`ModuleDef` 共享配方、实例只存 `def_id`+运行时状态）；改模板全局生效、存档不膨胀 |
| **装备实例无全局 id** | 条目自包含值语义，转移 = 移动条目本身 | 没有任何系统需要"引用某一把具体的剑"；省去 10000 个体 × N 件的全局索引维护。传奇武器等引用需求出现时再给高品质条目加 `uid` 字段（缺省补 0，向前兼容） |
| **战斗动画层零改动** | 装备只通过 `ItemDef.weapon_type` 映射到现有 `weapon_mount` 六型，不改动画/弹道/挂点 | `weapon_mount.gd` 的 WeaponType（SWORD/SPEAR/BOW/PICKAXE/STAFF/MERIC）已深度绑定攻击动画表、射程、箭道、盾格挡——重写成本高且无收益，装备系统的职责是"决定挂什么"，不是"怎么挥" |

## 三、数据模型

### 3.1 ItemDef（物品模板）

`class_name ItemDef extends Resource`，实例存 `config/items/*.tres`（Excel 物品数据表导出，管线同建筑）。

| 字段 | 类型 | 说明 |
|------|------|------|
| `id` | String | 如 `wpn_sword_iron` |
| `display_name` | String | 显示名 |
| `category` | enum | WEAPON / ARMOR / TOOL / AMMO / CONSUMABLE / QUEST |
| `slot` | String | 可穿戴槽位（`main_hand`/`off_hand`/`body`/`head`/`trinket`/`back`）；不可穿戴物品为空 |
| `weapon_type` | int | WEAPON/TOOL 类必填，映射 `weapon_mount.WeaponType` 六型 |
| `attack_flat` / `max_hp_flat` / `defense_flat` | float | 数值加成（加法制，见 §4） |
| `speed_mult` | float | 移动速度乘数（护甲/盾惩罚，1.0 = 无影响） |
| `durability_base` | int | 满耐久；0 = 无耐久概念（消耗品/弹药） |
| `quality` | int | 1 普通 / 2 精良 / 3 上乘——制造时由材料配比决定，同 def 可出不同品质 |
| `stack_max` | int | 背包堆叠上限（弹药/消耗品 >1，装备 =1） |
| `ammo_id` | String | 远程武器的弹药 def_id（BOW→箭）；空 = 不耗弹 |
| `blocked_variants` / `allowed_variants` | Array[String] | 体型过滤（数据驱动，不写死代码） |
| `icon` | String | 图标路径预留（Demo 用程序化绘制/现成武器贴图） |
| `notes` | String | 描述文案（无厘头基调，见世界观 §3.2） |

### 3.2 装备槽位（开放问题 1 裁决）

| 槽位 | 内容 | Demo 期 | 说明 |
|------|------|---------|------|
| `main_hand` | 武器/工具（六型） | ✅ 实装 | 镐（PICKAXE）也是主手物品——工具与武器同槽互斥，换工具=换武器 |
| `off_hand` | 盾/副武器 | ✅ 实装 | 盾已有场景与格挡逻辑 |
| `body` | 身体护甲 | ✅ 实装 | 视觉走体色微调/线宽加粗（`visual_controller` 现成通道），不做新贴图 |
| `head` | 头盔/帽 | 结构就位，UI 隐藏 | 无美术资产，数据先行 |
| `trinket` | 饰品 | 结构就位，UI 隐藏 | 后期扩展 |
| `back` | 披风/背挂 | 结构预留 | 与翼人（WINGED）翅膀冲突，`blocked_variants` 处理 |

**种族/畸变差异化**：种族（平原/火山/…）**不**差异化槽位——种族是文化地域差异，属性差异走 Excel 种族基准值。畸变个体（巨人/半人马/翼人/多头）通过 `ItemDef.blocked_variants` 数据过滤（如 CENTAUR 不能穿人形 body 甲、WINGED 占用 back 槽），代码一套，差异化全在数据表。

### 3.3 背包（开放问题 2 裁决）

**固定格数 + 堆叠制，非重量制。**

- 默认 **8 格**；条目按 `stack_max` 堆叠（箭 50/组、食物 10/组、装备 1/格）。
- 容量扩展：GIANT +4 格（驮兽语义）、背包类 trinket、后期组织辎重队加成——全部走数据字段，不改结构。
- 不用重量制的理由：`weight_per_unit` 已是**物流运输成本**语义（资源表），复用会混淆"个体携带"与"载具运输"两套概念；格子制在侧视角 UI 呈现直观。

**与仓库/物流的存取规则**（详见 §五边界）：

- 个人背包**不进**物流网络、**不进**经济结算——它是"口袋"，不是库存节点。
- 个人 ↔ 仓库的转移是**就地交互**：个体站在仓库/工坊/前线补给站建筑附近才可存取，走 `EquipmentAPI.transfer()`。
- QUEST 类物品（剧情任务物）：不占格、不可丢弃、不可交易，面板单独一栏。

### 3.4 Loadout（个体的装备+背包容器）

`class_name Loadout extends RefCounted`——**一个数据对象，两个宿主**（StickmanState 与场景图 stickman_entity 持有同一实例引用，无双写一致性问题）。

```
Loadout
├── slots: Dictionary        # {slot_name: 条目} 穿戴中，键 = §3.2 槽位名
├── backpack: Array          # 最多 capacity 条，每条目一个槽格（堆叠合并）
├── capacity: int = 8        # 格数
└── 条目结构（背包装备通用）：
    {"d": String def_id,     # 引用 ItemDef
     "dur": int 耐久,        # durability_base=0 的物品恒 0
     "q": int 数量,          # stack_max=1 的装备恒 1
     "qual": int 品质}       # 1-3
```

纯函数库 `loadout.gd`（槽位校验/穿戴规则/增删/堆叠合并/容量检查）全部静态无状态，单测友好。

### 3.5 实例化程度（开放问题 3 裁决）

| 维度 | 裁决 | 理由/分期 |
|------|------|-----------|
| 耐久 | **有**（数据字段 Demo 就位，消耗与修理闭环在 E-4） | 耐久归零 = 损坏（属性衰减到 30% 不消失），修理走工坊消耗资源——闭环依赖经济实装 |
| 随机词条 | **不做** | 品质三档（材料配比决定）已提供制造差异；随机词条是刷子游戏钩子，与本作"设计系统而非刷数值"的支柱相悖 |
| 制造→领取→使用→修理→死亡掉落 | Demo 最小闭环 = **制造 + 领取 + 换装**；修理/掉落留字段分期 | 掉落 = 尸体背包条目落地为可拾取物（战场清洗复杂度，守城战后处理）；`E-4` 与经济系统联合排期 |

**仓库商品 → 个人实例的转换点**（关键语义）：武器在仓库里是 `ItemDef × 数量`（无耐久无品质，纯商品）；**领取/拾取瞬间实例化**（品质按制造记录或默认 1、耐久 = 满值），回存仓库则反实例化（按品质折算回商品堆或独立品质堆，实施时定）。这是经济系统与个人系统的唯一界面。

## 四、战斗数值入口（验收口径 2）

### 4.1 派生公式

```
attack   = base_attack(种族×年龄, Excel 基准) + Σ(已穿戴条目.attack_flat) + 品质系数(qual-1)×武器成长
max_hp   = base_max_hp(种族, Excel 基准)     + Σ(.max_hp_flat)
defense  = base_defense                      + Σ(.defense_flat)
speed    = base_speed × Π(.speed_mult)        # 护甲惩罚 × 盾格挡移动系数（block_move_mult 既有语义）
attack_range / 动画 / 弹道 = weapon_type 决定（装备不改）
```

- **加法制**为主：直觉可算、Excel 可查、上限由品质与材料档控制，避免乘法滚雪球破坏平衡框架。
- 数值真相源纪律不变：**基准值在 Excel 单位数据表**，装备只提供增量；平衡调优走数据表热改，不改代码。

### 4.2 消费路径

```
ItemDef (.tres) ── ItemCatalog 装载
                          │
StickmanEntity.loadout ── AttributeResolver.resolve(loadout, 种族基准) → {attack, max_hp, defense, speed}
                          │                                    （equipment 模块纯函数）
                          ▼
        stickman_entity 初始化 / equipment_changed 信号 → 刷新 weapon_mount.damage、自身 max_hp、speed
```

- **派生值不持久化**：存档只存 Loadout 条目，属性每次 resolve——避免"存档里的 attack"与"装备算出的 attack"双真相源打架。
- resolver 是纯函数：10000 个体批量 resolve（开局/读档后）也是毫秒级；平时只有装备变更的个体重算。
- 战斗侧现有单点喂值模式（`weapon_mount.damage = base_attack`）平滑升级：无装备时 resolve 输出 = base，与现状完全等价（向后兼容）。
- 弹药接线：`weapon_type == BOW` 且 def 设了 `ammo_id` 时，射击消耗背包箭条目；`ammo_id` 为空 = 免弹（Demo 期 BOW 先免弹，E-4 开消耗——数据开关，不改代码）。

### 4.3 信号

按 EventBus 纪律（不预占位、模块自建信号），`EquipmentAPI` 发射：

| 信号 | 载荷 | 消费方 |
|------|------|--------|
| `equipment_changed` | `(stickman_id: String)` | units（刷新属性）/ UI（面板刷新） |
| `loadout_mutated` | `(stickman_id: String, reason: String)` | 存档脏标记（§6.3） |

## 五、系统边界：谁管仓库、谁管口袋（验收口径 4）

| 系统 | 管什么 | 不管什么 |
|------|--------|----------|
| **经济系统（05）** | 资源与加工品的**仓库级库存**：生产、价格、交易。武器作为商品在仓库 = `ItemDef × 数量` | 个人口袋里的任何东西 |
| **物流系统（06）** | **仓库之间**的运输（载具容量/路线/损耗），含"武器弹药"类补给从前方仓库运到前线补给站 | 个人背包的运输——口袋不进物流网络 |
| **装备系统（本系统）** | 个人 Loadout 的穿戴/存取/属性派生；个人 ↔ 仓库的就地转移交互 | 仓库库存增减（转移时回调经济接口）、运输过程 |
| **组织（01）`equipment_template`** | **编制配额**（"该排应配 4 长矛 1 弓"）——想要的 | 个人实际拥有的（Loadout）；**缺口 = 后勤任务源**（对照配额与实况生成领取任务，后期 AI 化，Demo 玩家手动/面板一键配齐） |

补给链语义落地：06 文档"前线补给=武器弹药"→ 物流把武器商品运到前线补给站（仓库级）→ 士兵走到补给站**领取**（本系统的转移交互，商品实例化为个人装备）→ 战斗消耗耐久/弹药 → 缺口触发再领取。

## 六、个体档案、规模与存档（开放问题 4/5，验收口径 1/3）

### 6.1 个人档案边界（开放问题 4 裁决）

「独立的特定记录」= `StickmanState` 升级为个体档案，扩展字段：

| 字段 | 类型 | 说明 |
|------|------|------|
| `loadout` | Loadout | 装备+背包（本系统核心） |
| `title_epithet` | String | 诨名（"独眼"/"快腿"），命名生成器产出 |
| `birth_day` | float | 游戏内出生日（年龄事件计算） |
| `kills` / `battles_fought` | int | 战绩聚合计数 |
| `chronic_conditions` | Array[String] | 慢性伤病 id（断腿/旧伤复发）；**即时战斗状态不进档案**（status_effects 是战斗态，生命周期=一场战斗） |
| `memory` | Dictionary | 轻量记忆钩子（剧情/Demo 预留，结构后定） |

**不进档案**：完整战斗日志、移动轨迹历史（存档爆炸源）；详细战报是 `BattleState.tactical_data` 生命周期内的事。

**命名生成器**：接口 `NameGenerator.generate(race, variant, seed) -> {name, epithet}`，词库数据表驱动。⚠️ 需求档引用的「世界观 §3.2 描述法命名规范」在当前世界观文档中**不存在**（§3.2 现为「不严肃的基调」）——生成器只定接口与确定性种子规则（同 seed 同名，读档不漂移），词库待该规范成文后填充，列为 E-1 的外部依赖。

### 6.2 双宿主与读写路径（验收口径 1）

`StickmanState`（战略层预留）与 `stickman_entity`（场景图生产中）持有**同一个 Loadout 对象引用**：

```
写：EquipmentAPI.set_equipped / transfer / add_item ...   ← 唯一写入口（内部做槽位校验+发信号）
读：AttributeResolver.resolve()  → 战斗属性
    UI 面板                      → 展示
    序列化器                     → 存档
```

- 所有写操作必须走 `EquipmentAPI`，禁止直改 `loadout.slots`——校验（槽位合法/体型过滤/容量）与信号发射集中在入口。
- Demo 期实际宿主是场景图实体（战略层 StickmanState 未接入生产数据流）；未来接入时同一 Loadout 结构随行，**无需迁移**。

### 6.3 规模与性能方案（验收口径 3）

| 项 | 方案 | 论证 |
|----|------|------|
| 内存 | 条目 ~40B，10000 个体 × 平均 5 条 ≈ **2MB 上限** | Dictionary 按 id 索引 O(1)，无压力 |
| 存档写 | 走 `entities` 表既有 per-row UPDATE：`extra_data["loadout"]` 只写变更行 | **不建专用脏标记框架**——`loadout_mutated` 信号 → 记入待存集合，SaveManager 定时存档时批量 upsert；SQLite 单行更新事务毫秒级 |
| 存档读 | 反序列化纯数据、**不 resolve 属性**（惰性：进地图实例化/开面板时才算） | 读档后 O(n) 建 Loadout 对象即可 |
| 批量派生 | resolver 纯函数无状态 | 开局/读档 10000 次批量调用毫秒级；平时增量 |

战略层若走 `legacy_modules` JSON blob 通道（WorldState 整块），2MB 全量重写也可接受（SQLite 事务内），不构成瓶颈。

### 6.4 存档迁移（兼容既有档）

- 旧 `StickmanState.equipment: Dictionary`（`{weapon_id, armor_id, tool_id}` 口径）→ 新 `loadout`：迁移函数把旧 `weapon_id`/`armor_id`/`tool_id` 视作 def_id 装入对应槽（def 不存在的丢弃并告警）；`tool_id` → `main_hand`（与武器互斥，冲突时武器优先）。
- 迁移入口挂 `save_meta.version` 版本迁移框架（该框架本身是存储架构待做项，装备是第一个消费者，落地时一并实现）。
- `world_state_serializer.gd` 头注的 round-trip 约束照旧：改字段同步更新 `tests/unit/test_entity_states.gd`。

| 挂点 | 装备系统的角色 |
|------|----------------|
| **生产链节拍**（断外官道=输入 -30% 补给事件） | 武器工坊产出 → 仓库商品 → 守城战备领取——本系统提供"领取+换装"两步，生产/库存归经济系统（边界见 §五） |
| **「教学第一次」清单格式**（v6 §9） | 建议新增两行：首次领取（C3 简报句式 + 工坊交付演出）、首次换装（面板引导一次，误操作无惩罚）——按该清单格式入剧情工单 |
| **任务物品**（佚名碎片 / 火漆刀） | QUEST 类别：不占格、不可丢弃、专用任务栏槽——碎片收集进度（x/5）直接读任务栏 |

节奏约束：装备系统是 Demo「生产链解锁」节拍的承载系统之一，**不新增战斗机制**（耐久/弹药的消耗开关 Demo 期默认关，E-4 才开）。

## 九、模块结构

```
modules/equipment/
├── api.gd                      # EquipmentAPI：resolve / set_equipped / transfer / add_item
│                               #   + 信号 equipment_changed / loadout_mutated（唯一写入口）
├── scripts/
│   ├── item_def.gd             # class_name ItemDef extends Resource（Excel→.tres）
│   ├── item_catalog.gd         # def 注册表装载（照 BuildingCatalog + sanitized_rows 先例）
│   ├── loadout.gd              # 纯函数库：槽位校验/穿戴规则/堆叠/容量
│   └── attribute_resolver.gd   # 纯函数：Loadout+种族基准 → 战斗属性
└── ui/
    ├── unit_loadout_panel.tscn/.gd   # 选中单位装备面板（模板复制起步）
    └── inventory_grid.gd             # 背包格网组件

config/items/*.tres             # ItemDef 资源（Excel 物品表导出）
config/excel/物品数据表.xlsx     # 数值真相源
```

- 依赖方向：`equipment` ← `units`（stickman_entity 持 Loadout、订阅信号刷新属性）← `combat`（间接，经 units）；`equipment` → `core`（无反向）。模块间通信走 `EquipmentAPI` 信号，符合架构原则。
- 命名生成器**不放本模块**（跨系统关注点）：接口定义在 `core/utils/name_generator.gd`，词库数据后续与世界观命名规范对齐。

## 十、分期实施

| 期 | 内容 | 依赖 |
|----|------|------|
| **E-0 数据层** | ItemDef / ItemCatalog / Loadout 纯函数库 + Excel 物品表（首批：六型武器各一档 + 盾 + 布/皮/铁甲）+ 单测 | 无 |

| **E-2 战斗接线** | AttributeResolver ↔ stickman_entity/weapon_mount（def→weapon_type 映射、三属性刷新、热切换改背包驱动）| E-0/E-1 |
| **E-3 UI** | 选中单位面板 + 附身面板升级 | E-2 |
| **E-4 经济闭环** | 工坊制造→仓库→领取实例化→耐久消耗/修理→死亡掉落→弹药消耗开关 | 经济系统实装进度 |

Demo 需要 E-0 至 E-3；E-4 与经济系统联合排期。每期完成后：`check_godot_errors` 干净 + `run_all.sh` 全过 + 视觉类过创始人观感。
