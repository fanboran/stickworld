# 并行开发协调（多 AI 协作规范）

> 本文档管理多 AI 并行开发的**任务登记、域权属、冲突热点、冻结令与派活核验**。
> 为什么需要它：单 AI 工作流的文档体系里，任务依赖散落在各设计文档正文，没有结构化登记；
> 多 AI 并行时"读到过时信息就派活"会直接造成返工（先例见 §五）。协调者（主会话）负责维护本文档、
> 派活前执行 §二 核验清单、收线时统一合并。各并行线开工时必须先读本文档。

## 二、派活前核验清单（协调者强制执行，缺一不派）

0. **任务依赖图先行**：更新 [`任务依赖图.txt`](任务依赖图.txt)（新任务立项、前置、状态），
   跑 `python tools/deptask/gen.py --check`——退出码非 0 禁止派活。
   校验器直接拦截本项目的两类翻车：**前置未完成就开工**（环/悬空引用/派活违规）与
   **进行中任务文件域重叠**（合并冲突热点）。可视化：`python tools/deptask/gen.py` 生成 HTML 后浏览器打开。
   语法说明见源文件头注释；模块级（代码）依赖不写进任务图，去 [`../技术/架构/模块依赖关系.md`](../技术/架构/模块依赖关系.md)。
1. **读隔壁的实时计划**：主线 AI 的 `docs/项目/AI复刻执行计划.md`、`待办事项.md`、`CHANGELOG.md` 以**主工作区未提交版本**为准，不读自己分支里的旧提交版本。
2. **前置存在性核验**：任务依赖的类、场景、资产、零件逐个 grep/ls 验证存在。"设计文档里提过"≠"已实现"。
3. **数据源版本核验**：引用具体数据（label、json、配置键）前，以运行时/产物实测确认版本；待办正文可能滞后于设计文档纠偏（先例：出生 L1 的 label 219/4 城市已废弃，实测为 label 69/8 城市）。
4. **冲突热点比对**：任务写入文件集与 §三 热点、其他线权属逐一比对，有交集即改派或拆分。
5. **冻结令检查**：受 §四 冻结的任务不得派出。
