## 〇、一页结论

**两类室内怎么选**：绝大多数建筑走 **A 类（剖视内景）**——玩家不切场景，前墙透明时看见室内，成本 = 1 张带 alpha 的内景 PNG + 已接线的透明化状态机。只有**竖向体量大、必须真正在里面走**的少数地标走 **B 类（可进入室内场景 = MegaInteriorMap）**，成本 = 一张独立地图 + 家具 + 出入口 + 往返记录。

**三个关键数字**（详见 §2.2）：

| 数字 | 值 | 出处 |
|---|---|---|
| 建筑基线（= 室内地面线，建筑局部 y=0） | `ground_y + 96` px | `construction_project.gd:322`；`地图与场景图.md` §3.4 y-sort 约定 |
| 一层净高（地板面→檐口） | 200~207 px（2.6~2.7 m） | 交接档 §0.3 硬约束 3；`建筑生成管线v3-写实PBR.md` §3.1/§8.7 |
| 内景进深（取 12 格档为基准） | 196~210 px（净进深 ≈ 160~170 px ≈ 2.1~2.2 m） | `buildings.py` 各 `*_TIERS[12]["D"]`；`interiors.py` `_WIDTHS` |

**覆盖现状**：管线 def 宇宙共 31 项（26 装配器 + 3 别名 + 2 道具型），其中内景**已具备 7 项**（Blender 已出 `_back`/`_front`，见 §5）、**运行时程序化内饰已具备 6 个运行时 def**（`InteriorProps` 路径：`placeholder`/`smithy_lv1`/`timber_cottage`/`barracks`/`warehouse`/`grand_hall`，另有 `manor`/`stone_warehouse` 只有壳，见 §3.1 现状列）、**待做 22 项**、**需引擎侧确认 6 项**（§5.2）。

## 一、两类室内定义与取舍

### 1.1 A 类：剖视内景（TRANSPARENT，不切场景）

玩家走进建筑 `InteractionZone`，**前墙半透明 + 内景层显示**，角色仍在地图里（EXPLORE→INDOOR 子模式），不加载新场景。契约出处：`地图与场景图.md` §5.1 表、§5.2.1 透明化状态机、§5.3 建筑场景结构扩展、§5.4.1 INDOOR 复用 `ExploreHandler`。

- **可见的室内**：一层/多层剖面（`BackLayer` 后墙 + `Floor` + `Modules_Slot` 家具）。
- **玩家能做什么**：走到门前停下看内部（"师傅在打铁"）；`WorkSlots` 仍是 NPC 寻路目标（`地图与场景图.md` §5.3；`building.gd:226-270`）。
- **资产成本**：内景 `_back` PNG（按 def × 宽度档预渲）+ 外皮 `_front` PNG；**零新增地图、零存档字段**。
- **工程成本**：复用已接线的 `Building._set_transparent()` / `InteractionZone` / `EventBus.interior_entered|exited`（`building.gd:377-414`，`core/autoload/event_bus.gd:122-128`）。

### 1.2 B 类：可进入室内场景（TELEPORT / MegaInteriorMap）

玩家走进 `EnterTrigger`，过场淡出 → 加载 `MegaInteriorMap` → 室内有独立 `ground_y`/`ground_ratio`、可走动的完整空间；`ExitTrigger` 记录 `return_map_id` 返回原地图原位。契约出处：`地图与场景图.md` §5.1 表、§5.6.1 传送流程、§5.6.2 返回机制、§5.6.3 过场、§3.1 表（`MegaInteriorMap` 行）。

- **可见的室内**：完整地图，可做多房间/多层/纵深动线，`ground_ratio` 可上调（§3.1 注："室内可能 0.5"）。
- **玩家能做什么**：真正在室内走动、与室内物件/机关交互。
- **资产成本**：每个"要进去的门"一张独立地图场景（背景/地面/家具/光照/出入口），远高于 A 类。
- **工程成本**：`SceneLoader` TELEPORT 往返 + 过场 + `return_map_id`（`game_root.gd:158` `_return_map_id`、`setup/travel_handler.gd:31-90`、`travel/mega_interior_exit_trigger.gd`）。
  > **实现状态更正**：`地图与场景图.md` §5.6.2 写"缺 `return_map_id` 记录机制"为**旧口径**——该机制已在 `travel_handler.gd` 落地；但当前只有**一张通用** `modules/world/scenes/maps/mega_interior.tscn`，尚无 per-def 地图内容。

### 1.3 取舍结论

| 判据 | 选 A 类 | 选 B 类 |
|---|---|---|
| 竖向体量 | 1~2 层，剖视能看全 | 3 层以上或塔状（纵深感是卖点） |
| 占地 | ≤ 16 格 | ≥ 12 格且内部是多房间 |
| 玩法 | "看 NPC 干活"、供应/居住 | 需要玩家真的走进去（仪式/机关/多房间） |
| 数量 | 全谱系（主路径） | 少量地标 |

**结论（提案/待定，建议 Founder 圈选）**：

- **A 类 = 全 def 默认**。除下表地标外，所有 def 一律 `interior_mode = TRANSPARENT`。
- **B 类 = 4 个地标**：`cathedral`（大教堂）、`grand_hall`（议事厅）、`tower`（瞭望塔）、`lighthouse`（灯塔）。这 4 个的共同点：剖视看不到"纵深/多层"，且都是玩家会想"进去看看"的地标（`设计/系统/12-小镇生活与美术.md` §四.2「多层建筑」）。
- **A+B 并存**（先剖视、再走门传送）：**不建议 P0 做**。两套内景内容会双份维护（同一建筑既要 `_back` 内景、又要独立地图），且 §5.4.2 的模式切换规则限制严格（禁止从 INDOOR 直接到 BUILD/POSSESS），叠加传送切换的状态机分支成本高；P0 只做 A 类即可满足"能看见室内"。
- **`windmill` / `mage_tower` 暂定 A 类**（塔身用剖视竖向剖面表现传动/法阵，成本最低）——**提案/待定**。

## 二、结构分层与坐标契约（核心）

### 2.1 内景分层与 z 序

内景 = 建筑内部在"前墙之后、后墙之前"的一段可见空间，层序沿用 `建筑模块化设计.md` §三 的 `BuildingLayer` 分层，并对齐 `地图与场景图.md` §3.4 的地图级 z 约定：

| 层（建筑局部） | z_index | 内景内容 | 出处 |
|---|---|---|---|
| `Layers[n].BackLayer` | 0 | **后墙**（内景的背景面） | `建筑模块化设计.md` §3.1 |
| `Layers[n].Floor` | 4 | **地板**（含踢脚收边） | 同上 |
| `Layers[n].Modules_Slot`（= `Interior/Props`） | 5 | **家具模块**（炉/砧/床/桌/货架…） | 同上；`building_exterior.gd:245-249` |
| 火柴人（`EntityHost`） | 地图级 3 | 角色在室内行走 | `地图与场景图.md` §3.4 |
| `Layers[n].FrontLayer` | 10 | **前墙 + 门窗**（= `_front` PNG 的下段） | `建筑模块化设计.md` §3.1 |
| `Roof` | 11 | **屋顶 / 山墙 / 烟囱**（= `_front` PNG 的上段） | 同上 |
| 地图级 `ForegroundLayer` | 10 | 地图近景遮挡（内景**不用**这一层） | `地图与场景图.md` §3.4 |

**「天花」的处理**：§5.2.1 只要求"屋顶始终可见"，未要求内景自带天花。`interiors.py` 明确 `_shell()` 不建天花/顶梁（理由：最终合成里被屋顶完全遮住，只在"单看后层"时糊成黑块）。**契约**：内景 `_back` 不画天花；垂直封顶由 `Roof`/檐口承担。

**⚠️ 待引擎侧确认 #1（z_index 落地）**：上表是**目标契约**，但当前**运行时代码没有任何一处设置这些 z_index**——`building_exterior.gd` / `building.gd` / 各 `*.tscn` 均无 `z_index`（已实测 grep 为空），实际排序退化为**树序**（`Exterior` 的子层 L1→L5 靠 `add_child` 顺序）。而 `Interior` 是 `Exterior` 的**后添加兄弟节点**，按树序会画在 `L4_FrontWall`/`L5_Roof` **之上**，即内景会糊住前墙。
→ **必做前置**：把上表 z_index 显式写进建筑生成（`building_exterior.gd` 的 `_layer()` 或 `BuildingEntity` 构建器），否则"窗户透出内景"与"前墙遮挡火柴人"两个能力都不成立。这是室内一切视觉的前提，优先级高于内景内容本身。

### 2.2 内景地面线、净高与进深（三个关键数字）

**① 建筑基线 = 室内地面线 = `ground_y + 96`**

```
世界坐标（Godot 2D，y 向下为正）
  ground_y ────────────────────── 地平线（火柴人可走带上边界）
      │                                · 火柴人脚部可走区间 [ground_y, ground_bottom]
      │ 96px                           · 建筑基线落在这段带内，建筑因而"种"在地里
  ground_y + 96 ───────────────── 建筑根原点（Building.position.y）
                                    = 建筑局部 y = 0 = 室内地面线
```

- 出处：`construction_project.gd:322` `vis.position = Vector2(cell_x*32, ground_y+96)`；`construction_manager.gd:441/519` `building_baseline_offset` 默认 `96.0`；`地图与场景图.md` §3.4「建筑按基线排序（根位置 ≈ 地平线+96px）」；`建筑与定居点.md` §4.3.1「落地箱垂直范围 `ground_y ~ ground_y+96`」。
- **建筑局部坐标约定**：x 从建筑左缘起算 0→`width×32`；y=0 为地面线，**向上为负**（`building_exterior.gd:266`「Building 局部坐标，地面线 y=0」；`smithy_lv1.gd:177` `slab.position = Vector2(width*16, -12)`）。
- **玩家"进屋"= 在这一段带里向下走**：实体 Y 约束为 `[ground_y, ground_bottom]`（`stickman_entity.gd:568-570`），玩家踩到 `ground_y+96`（基线）即站在室内地板上。
- **「内景地面线相对建筑基线」= 重合（y=0）**。内景地板画在 y ∈ [−24, 0]（`InteriorProps.make_floor(w, 24, ...)` 的 24px 薄板 + 前缘暗线），家具锚点 = 脚底中心 = y=0（`interior_props.gd` 文件头）。

**② 一层净高 = 单层檐高 200~207px**

- 硬约束出处：交接档 §0.3 约束 3「单层檐高 200~207(2.6~2.7m)」；`建筑生成管线v3-写实PBR.md` §3.1「单层层高 195~215px = 门 150 + 楣梁 30 + 余量」、§8.7 米制换算（1 格=32px=0.42m、1px≈1.31cm）。
- **内景可用净高 = tier 表的 `plinth + wall`（或 `post_h`/`storey`）**，即檐口行 = 建筑局部 `y = −(plinth + wall)`。实测：
  - `house w12`：plinth 18 + wall 208 → 檐口 y = −226
  - `townhouse w12`：plinth 18 + storey 205×2 → 檐口 y = −428（二层各 205）
  - `smithy1 w8`：`post_h` 205（开放棚，无 plinth）→ 檐口 y = −205
  - `cathedral w16`：plinth + `nave_h` → 中殿高约 280~300
- **不要另定一套室内层高**：内景定尺**必须从 `buildings.py` 的 tier 表读**（`interiors.py` 文件头已立此纪律："本文件不复制任何尺寸数字——宽度/层高口径改动时内景自动跟随"）。这是防止"外墙改高、内景没跟"的唯一手段。

**③ 进深 = tier 表的 `D`；内景基准取 12 格档**

- `D` 是**含墙外皮**的总进深，分布在 ±Y 各半（`interiors.py` 文件头「建筑本体以原点为中心、进深向 ±Y 各半」）。
- **净进深 = D − 2×wt**（后墙 + 前墙厚度）。实测（`buildings.py` 各 `*_TIERS`）：

| def | w8 | w12 | w16 | 净进深（w12，减 2×wt） |
|---|---|---|---|---|
| house | 150 | **200** | 240 | ≈160 px ≈ 2.1 m |
| townhouse | — | **208** | 240 | ≈168 px ≈ 2.2 m |
| tavern / bakery / shop / smithy3 / stable | 156~180 | **196~208** | — | ≈156~168 px |
| smithy1 | 176 | — | — | ≈144 px（w8，减 2×post 16） ≈ 1.9 m |
| cathedral | 176 | 200 | **232** | — |

- **基准档取 12 格（不是 8 格）**：`interiors.py` `_WIDTHS` 注释已给理由——"8 格档内净深只 ~1.5m，摆不下床 + 桌 + 炉三件（真去 8 格档会互相穿模），12 格档净深 ~2.2m 才立得住"。**契约**：内景资产默认按 **12 格档**出图（smithy1 因只有 6/8 档取 8 格；cathedral 取 16 格）。
- **实际建造宽度 ≠ 基准档时**（玩家拉宽建造，`建筑与定居点.md` §4.3.4 拉伸模型 / `construction_manager.gd`）：内景按"基准档 PNG 居中 + 两侧补地板/踢脚"处理，**不做水平拉伸**（拉伸会让家具变形）。**提案/待定**：补缝件（地板条/踢脚线/货架延长段）由管线另出一张 `_back_filler` 平铺条，或由运行时 `InteriorProps.make_floor()` 程序化补。

### 2.3 家具模块槽位 / WorkSlots / InteractionZone / 交互位置

四者关系（一张图）：

```
InteractionZone（Area2D，程序化生成）
  size = (width×32, 390)，center = (width×16, −190)
  → 世界覆盖 y ∈ [ground_y−289, ground_y+101]
                                     ↑ 室内地面线 ground_y+96 只比下沿低 5px  ⚠️ 见待确认 #2
  ├── Modules_Slot / Interior/Props    家具（纯视觉，`InteriorProps` 或 `_back` PNG）
  ├── Interior/WorkSlots (Node2D)      Marker2D[] —— NPC/工人寻路目标（逻辑锚点）
  └── 交互位置规则                      横向中间 (width−2) 格、垂直在建筑范围内
```

- **`WorkSlots` 契约**（已实现）：路径兼容 `Building/WorkSlots` 与 `Building/Interior/WorkSlots`（`building.gd:182-188`）；`get_work_slot_positions()` 返回 **`Marker2D.global_position`**（`building.gd:254-258`）；消费方为 NPC 职业寻位（`modules/town_life/scripts/profession_registry.gd:88-95`、`behavior_harvest.gd:136`）与建造派工（`construction_project.gd:130`）。
- **交互位置规则**（已实现）：玩家按 E 与工人工作位都要求角色在**横向中间 `(width−2)` 格**（左右各内缩 1 格）且垂直在建筑范围内——出处 `建筑与定居点.md` §4.3.1「交互位置规则」、§4.3.3；实现 `modules/units/scripts/entity/interaction_controller.gd:161/176/189`、`behavior_work.gd:120-129`、`behavior_haul.gd:168/191`。
- **对齐规则（本节的工程契约）**：
  1. **家具必须落在中间 `(width−2)` 格之外侧或之内皆可，但 `WorkSlots` 必须落在中间区内**——因为玩家只能站中间区，NPC 工位应贴着"玩家能看到且能站到"的位置；让 NPC 站在边缘 1 格里会导致玩家按 E 交互不到。
  2. **`WorkSlots` 的 x 与家具的"操作点"重合**：铁匠铺的工位 = 铁砧前的地面点（`interiors.py` 炉 `x=−xh+70` → 砧 `x=fx+16`，玩家站砧前）；酒馆 = 吧台内侧地面点；面包房 = 烤炉前；仓库 = 货架前。
  3. **高度**：`WorkSlots` 的 y 恒为室内地面线（局部 y=0，世界 `ground_y+96`）——工位是"站在地板上的点"，不悬空。现有 Marker2D 是否满足未核（缺 Marker 的 y 值断言）→ **待引擎侧确认 #5**。
- **家具与 `InteractionZone` 的关系**：`InteractionZone` **只由建筑尺寸驱动**（`width` + 固定 `ZONE_HEIGHT=390`，`building_exterior.gd:223-225/274-302`），**不随家具数量变化**。所以新增家具不需要改 zone；但 zone 必须完整覆盖"玩家能看到并想站的位置"。

**⚠️ 待引擎侧确认 #2（zone 下沿余量）**：`ZONE_CY=−190 / ZONE_HEIGHT=390` 使 zone 底边落在建筑局部 `y=+5`（世界 `ground_y+101`），而室内地面线在 `y=0`（`ground_y+96`）——**只有 5px 余量**。玩家踩到地板线上时若脚步再往下 1~2px 的抖动就可能 exit 触发区 → 透明化闪烁。**建议**：把 zone 下沿锚到地板线下方 ≥ 1 格（32px），并把 `ZONE_HEIGHT`/`ZONE_CY` 从"魔法数字"改为"由基线 + 檐高推导"。

### 2.4 门/窗与内景的对应关系（两个独立的透明度来源）

创始人诉求「窗户要能透过看到室内」需要**两个透明度来源同时成立**，二者不可互相替代：

| 来源 | 载体 | 触发 | 数值 | 出处 |
|---|---|---|---|---|
| **来源 1：整层前墙半透明** | `WallFront` / 所有 `FrontLayer.Walls_Front` + `Pillars_Front` | 玩家进 `InteractionZone` | `modulate.a: 1.0 → 0.3`（Tween 0.2s） | `地图与场景图.md` §5.2.1、§5.2.2；`建筑模块化设计.md` §九（模块化后改为遍历所有前景层） |
| **来源 2：窗玻璃像素真透明** | `_front` PNG 的窗格像素 | 常驻（不进交互区也生效） | 像素 alpha ≈ 0.226（每面 0.12 × 双面） | `interiors.py:55-95` `thin_glass()`；探针 `probe_interiors.py` 的 `_over(mul)` |

- **来源 2 是"站在建筑外就能从窗看见内景"的唯一途径**——来源 1 只在玩家进交互区时生效。两个来源的合成是乘法：窗格最终 alpha = 玻璃像素 alpha × 前层 `modulate.a`（进交互区后 0.226×0.3=0.068，更透，可接受）。
- **门洞**：§5.1 说玩家"走进建筑交互区"，不是走出门洞；`InteractionZone` 是覆盖整栋的无形矩形，所以门洞是**视觉开口**而非碰撞入口（`建筑与定居点.md` §4.3 + §4.3.1 明确 PassageBarrier 决定能否穿过）。`Interior` 与门洞的对位要求：**门洞应落在内景的可视区间内（中间 `(width−2)` 格内至少 1 个门）**，否则玩家在交互区里看不到"入口"与内景的关系。
- **窗洞**：窗台 69 / 窗高 92~100（交接档 §0.3 约束 3、`建筑生成管线v3-写实PBR.md` §3.1）。内景家具的**"可读高度带"必须落在窗洞垂直区间内**——窗台 69 以上、窗顶 169 以下。所以在窗后摆家具时，**台面高度 70~160px 的家具（桌/吧台/砧/货架）最容易被看见**，落地矮件（桶/煤堆）在窗外读不出来。这是内景布局的硬约束，内景 agent 已按此把桌/柜台放在窗洞高度带。

**⚠️ 待引擎侧确认 #3（`Interior.visible` 是否该常驻）**：§5.2.1 状态机把 `Interior.visible` 与前墙 alpha **同门控**（进区才可见）。但**窗玻璃是常驻真透明的**——若 `Interior` 默认 `visible=false`，玩家站在外面从窗里看到的将是"天空/后景"，而不是家具。"窗户能看到室内"要求 `Interior` **常驻可见**（可见性不与交互区绑定），门控只驱动前墙 alpha。代价：内景每帧都在画（可用"只在前墙有窗的建筑常驻 + 相机可见范围裁剪"缓解）。**这是本任务最需要拍板的一条**。

**⚠️ 待引擎侧确认 #4（`_front` 是否拆成 `_front` + `_roof`）**：§5.2.1 明写"`Exterior.visible = true`（屋顶仍可见，保持空间感）""只调 `WallFront` 的 alpha，不调整个 `Exterior`"。但 `interiors.py build_front()` 交付的 `_front` PNG **把前墙 + 屋顶 + 山墙 + 烟囱打在一张图里**（`crop_back_half` 只切掉"檐口以下的后半栋"），探针 `pbr_int_layers.png` 第 3 格可见**屋顶也被 0.3 加权**；程序化外壳 `building_exterior.gd:221` 同样把 `L5_Roof` 列入淡出层（注释自认是"等价视觉"）。
→ **建议**：管线把外皮拆成两张——`_front`（前墙 + 门窗，可被 alpha 0.3 加权）与 `_roof`（屋顶 + 山墙 + 烟囱，**不参与淡出**）。这正好实现"娃娃屋剖视"：屋顶留着、前墙化掉、内景露出。成本 = 管线多一次"隐藏屋顶渲一张"。

### 2.5 坐标映射契约（Blender 世界 ↔ 建筑局部 ↔ PNG）

三套坐标必须写明换算，否则管线产物无法落到运行时：

| 坐标系 | 定义 | 出处 |
|---|---|---|
| **Blender 世界**（管线内部） | 正面 = **−Y**；+Z 向上、地面 z=0；建筑以原点为中心，进深向 ±Y 各半；X 关于 0 对称（±W/2） | `interiors.py` 文件头；`buildings.py` 装配器 |
| **建筑局部**（Godot 运行时） | x ∈ [0, width×32]（原点 = 建筑左缘）；y = 0 为地面线，向上为负 | `building_exterior.gd:266`；`interior_props.gd` 文件头 |
| **PNG** | 交付图内的像素坐标 | `probe_interiors.py` `_place_cam()`（同机位渲 back/front，天然对齐） |

**换算（F = Flatten，把三维世界投到正视图）**：

```
建筑局部 x = Blender 世界 x + W/2          (W = width_cells × 32)
建筑局部 y = − Blender 世界 z
世界坐标   = 建筑根位置 + 建筑局部 = (cell_x×32 + 局部 x, ground_y + 96 + 局部 y)
```

**PNG 对位**：back 与 front **同一相机、同一取景**各渲一张（`probe_interiors.py` 文件头"两张图天然像素级对齐（前层叠后层不需要任何对位）"）。因此 PNG 只需在 `meta` 里声明 **`pivot_px`（建筑局部 (0,0) 在图中哪一像素）**，运行时用 `Sprite2D.centered=false` + `position = pivot` 即可精确落位。

> **不要沿用 v2 的 meta 坐标约定**：v2 `gen_buildings.gd:135-142` `_shift_meta()` 会把 `barrier/front_wall/workslots` 的 x **平移到含出血的图坐标**（`MARGIN_X`）。新契约建议统一用**建筑局部 px**，避免"坐标含出血 vs 不含出血"两套口径混用。

## 四、交付管线对接

### 4.1 内景资产的产出（现状 + 缺口）

**已跑通的产出（`tools/blender_buildings/interiors.py` + `probe_interiors.py`，在研未提交）**：

```
pbr_int_<def>_{back,front}.png    # 7 个 def：house/townhouse/smithy1/tavern/bakery/shop/cathedral
                                  # 均带 alpha（film_transparent=True），yaw=0 / tilt=20（硬约束 §0.3-2）
pbr_int_window.png                # 窗洞特写（验证"透过真透明窗格看到内景"）
pbr_int_layers.png                # 3 格：back / front 不透明 / front@0.3 over back（模拟游戏合成）
pbr_int_sheet2x.png               # 7 套内景 back 的 2x 拼页
```

- `build_back()` → `_back`（后墙 + 地板 + 二层楼板 + 家具 + 暖光）；`build_front()` → 复用 `buildings.ASSEMBLERS[def]` 成品，`crop_back_half(y_cut=0, z_cut=eave_h)` 切掉"檐口以下的后半栋"，再把清水玻璃换成 `thin_glass()`（真 alpha 混合）。
- **管线侧缺口**：`materials.py` 的 `glass_clear` 是"纯透射"，在 `film_transparent` 下渲染出来的 alpha = 255（不透明），窗格会把内景整块挡住。`interiors.py` 用了一个**文件内临时替身** `thin_glass()`（alpha 混合）绕过。**正式落地前必须改 `materials.py`**（把窗玻璃材质改为 Alpha Blend 变体），否则每次都得依赖临时件（`interiors.py:31-35` 已列最小改动清单）。
- **管线侧缺口 2（发光物）**：`fire` / `ember` 不是 `materials.py` 的注册 key（现有 57 key 列表内无），但 `buildings.forge()` 与 `interiors.py _hearth()/_bakery()` 都在用它们 → 当前渲染落回退色、**无自发光**。室内壁炉/炉火是内景的"暖点"，不补这两个 key，"空盒感"消不掉（交接档 §0.2 #17 标"火光待做"）。

### 4.2 meta 字段建议（新增契约，v3 目前无 per-def meta）

v3 现在只出 PNG + 城市摆放 JSON（`probe_city_scene.py:511`），**没有 per-def 元数据**。建议每个 def×宽度档带一份 `<def>_w<W>_int.json`：

```jsonc
{
  "def": "smithy1",
  "width_cells": 8,
  "variant": 0,
  "unit": "building_local_px",        // 本文件内除 *_px/canvas 外一律建筑局部 px（y 向上为负）
  "canvas": { "w": 1024, "h": 768 },  // PNG 像素尺寸
  "pivot_px": [512, 640],             // 建筑局部 (0,0) 在图中的像素位置（Sprite2D 定位用）
  "layers": {
    "back":  { "file": "smithy1_w8_back.png",  "pivot_px": [512, 640] },
    "front": { "file": "smithy1_w8_front.png", "pivot_px": [512, 640] },
    "roof":  { "file": "smithy1_w8_roof.png",  "pivot_px": [512, 640] }   // 可选，见待确认 #4
  },
  "interior": {
    "floor_line_y": 0,                // 室内地面线（建筑局部 y；恒 0）
    "eave_y":       -205,             // 檐口/天花行（来自 tier 表，内景上边界）
    "depth_px":     176,              // tier 表 D（含外皮）
    "depth_net_px": 144,              // 净进深 = D − 2×wt
    "daylight":     "warm_dim"        // 光调（warm_dim / cold_dim / holy_dim）
  },
  "windows": [ { "rect": [x, y, w, h], "alpha": 0.226 } ],   // 真透明窗格（引擎核对用）
  "workslots": [ { "x": -72, "y": 0, "role": "anvil" },
                 { "x":  12, "y": 0, "role": "bench" } ],     // → Marker2D，对齐 §2.3
  "lights": [ { "x": -110, "y": 96, "color": [1.0,0.66,0.36], "radius": 76 } ],
  "barrier":    { "x": .., "y": .., "w": .., "h": .. },       // 沿用 v2 契约（gen_buildings.gd:137）
  "front_wall": { "x": .., "y": .., "w": .., "h": .. }        // 沿用 v2 契约
}
```

**字段纪律**：

- `pivot_px` 是唯一以"图像像素"计的字段；其余坐标一律**建筑局部 px**（避免 §2.5 末尾的 v2 出血平移坑）。
- `workslots` 的 `role` 用字符串枚举（`forge`/`anvil`/`counter`/`shelf`/`bed`…），供 UI 提示与职业匹配；**不写死索引**，运行时按 `role` 排序后建 `Marker2D`。
- `windows` 让引擎能校验"窗格 alpha < 1"（门禁项，防回归到不透明白窗）。

### 4.4 与现有运行时内饰的关系（两套内容库，必须收口）

现在**并存两条内景实现路线**，它们是**同一件事的两种做法**，必须二选一或明确分工：

| | 路线 α：运行时程序化内景 | 路线 β：Blender 烘焙内景 |
|---|---|---|
| 载体 | `InteriorProps` 家具工厂（Godot 画 Sprite2D/Polygon2D） | `_back` PNG（写实 PBR 预渲） |
| 使用方 | `building_exterior.gd::_furnish_interior()`（已 ship，8 个 def 有内容） | `interiors.py`（7 def 已出图，**未接入**） |
| 宽度自适应 | 天然（按 `width` 摆件） | 需按档预渲 + 补缝 |
| 画质 | 程序化矢量风（`设计/系统/12-小镇生活与美术.md` §四.3 要的是"笔触手绘但不糊"） | 写实 PBR（交接档 §0.3 约束 5 定的现行风格） |
| `WorkSlots` | 由场景/代码放 Marker2D | 需从 meta `workslots` 生成 |
| 与 §0.3 风格约束 | **冲突**（现风格已定写实 PBR，2D 程序化被创始人否掉） | 一致 |

**结论（提案/待定）**：**β 为目标态**（§0.3 约束 5「禁止 2D 手绘笔触路线」），α 降级为**过渡/补缝/无资产 def 的兜底**。迁移期路由规则建议：有 `_back` PNG 的 def 走 β；没有的走 α；两者都有时以 β 为准（可用 `def_id`+`width` 表驱动，便于滚回）。**需 Founder/架构拍板**，因为它决定 `InteriorProps`（一份已 ship 的代码）的去留。
