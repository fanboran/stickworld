# 存储架构设计

> 本文档定义 stick-world 项目的数据存储分层、格式选择与最佳实践。
> 关联：`docs/技术/架构/场景与战斗架构.md`、`docs/技术/架构/数据流全景.md`

---

## 一、设计原则

1. **静态/动态分离**：只读资源打包进游戏，可写数据独立存档
2. **模板/实例分离**：建筑/单位定义是模板（.tres），游戏内建造是实例（存档）
3. **版本化存档**：存档带版本号，支持升级迁移
4. **数据驱动**：平衡数据走 xlsx->.tres 流水线，地图元数据走 .tres，运行时状态走存档

---

## 二、存储分层

### 层 1：静态资源层（打包只读）

| 数据 | 格式 | 说明 |
|------|------|------|
| 地形/装饰场景 | `.tscn` | Godot 原生可视化编辑 |
| 地图元数据 | `.tres` (MapDefinition) | ground_y/ratio/bounds/出生点/建筑槽位 |
| 建筑/单位模板 | `.tres` (从 xlsx 生成) | BuildingDefinition/StickmanDefinition |
| 平衡数据 | `.tres` (从 xlsx 生成) | balance_resource.gd |
| 动画/纹理 | `.tres`/`.png` | 美术资源 |

**原则**：打包后**只读**，运行时**绝不修改**。

### 层 2：存档层（运行时读写，玩家专属）

| 数据 | 格式 | 说明 |
|------|------|------|
| 游戏内建造状态 | SQLite | 建筑实例数据（def_id/cell_x/width/state/health） |
| 建造中项目 | SQLite | 未完工项目进度 |
| 实体状态 | SQLite | 火柴人位置/朝向/附身状态，entity_type+extra_data 支持扩展 |
| 资源点状态 | SQLite | 城内有限资源点位置/类型/剩余量 |
| 地图边界状态 | SQLite | 动态边界 cell 坐标/城内范围 |
| 战略层实体 | SQLite (JSON blob) | WorldState 的 stickmen/organizations/regions 等，存入 legacy_modules 表 |

**原则**：独立于地图场景，换地图/多周目可保留。

### 层 3：配置层（用户偏好，独立于存档）

| 数据 | 格式 | 说明 |
|------|------|------|
| 用户设置 | `settings.json` | 音量/键位/语言 |

## 三、存档格式：SQLite（godot-sqlite）

### 技术选型

| 项 | 值 |
|----|----|
| 插件 | godot-sqlite（2shady4u）v4.8 |
| 许可证 | MIT |
| 实现方式 | GDExtension（C++ 包装 SQLite3，预编译二进制） |
| 安装位置 | `addons/godot-sqlite/` |
| 数据库路径 | `user://saves/save_<slot>.db`（每槽一库） |

### 选择理由

1. 关系查询（按 map_id 查建筑、按 entity_type 查实体）
2. 增量更新（单建筑状态变更只改一行，不必重写整个存档）
3. 事务原子性（godot-sqlite 高层方法自带事务管理）
4. 扩展性：成百城市 × 大几十建筑 × 几千 NPC，SQLite 轻松处理

### 注意事项

- godot-sqlite 的 `insert_row`/`delete_rows`/`update_rows` **内部自带事务**，不要在外层手动包 `BEGIN TRANSACTION`/`COMMIT`，否则报 "cannot start a transaction within a transaction"
- `ClassDB.class_exists("SQLite")` 用于检测插件是否加载
- `ClassDB.instantiate("SQLite")` 创建实例，比直接 `SQLite.new()` 更安全（插件未加载时不崩溃）

## 四、数据库表结构

### 设计原则

1. **按 map_id 分区**：天然支持成百城市，每城市独立存取
2. **实体表可扩展**：`entity_type` + `extra_data`(JSON) 支持未来各种实体类型
3. **WorldState 兼容**：`legacy_modules` 表存 JSON blob，WorldState 零改动
4. **外键级联**：所有表通过 `slot_id` 关联 `save_meta`，删槽位自动清理

### 表一览

| 表 | 用途 | 主键 |
|----|------|------|
| `save_meta` | 存档元数据（时间/游玩时长/当前地图） | slot_id |
| `maps` | 地图运行时边界状态 | (slot_id, map_id) |
| `buildings` | 建筑实例（完工+地形建筑） | (slot_id, building_id) |
| `construction_projects` | 建造中项目 | (slot_id, project_id) |
| `entities` | 实体（玩家+NPC+未来扩展类型） | (slot_id, map_id, entity_id) |
| `resource_nodes` | 资源点状态 | (slot_id, map_id, node_id) |
| `legacy_modules` | 兼容旧模块（WorldState JSON blob） | (slot_id, module_name) |

### 扩展性

| 未来需求 | 扩展方式 |
|---------|---------|
| 新实体类型（动物/载具） | `entities.entity_type` 加新值，特有字段存 `extra_data` JSON |
| 新建筑类型 | `buildings.def_id` 引用模板，无需改表结构 |
| 资源经济系统存档 | 新加 `resource_stocks` / `resource_prices` 表 |
| 增量存档（程序化城市） | `maps` 表加 `layout_seed` 列，初始内容用 seed 重建，只存差异 |
| 多地图并发 | 按 `map_id` 独立存取，离开城市时存该城市，进入城市时读 |

## 五、存档/读档流程

### 保存流程

```
SaveManager.save_game(slot)
  ├── open_db(save_<slot>.db)
  ├── _ensure_schema()
  ├── _upsert_save_meta()
  ├── _save_legacy_modules()           ← WorldState.get_save_data() -> legacy_modules 表
  ├── emit game_saving(slot)           ← GameRoot 回调中用 get_db() 写表
  │     ├── VillageMap.save_to_db()         -> maps 表
  │     ├── ConstructionManager.save_to_db()-> buildings + construction_projects 表
  │     ├── GameRoot._save_entities()       -> entities 表
  │     └── VillageMap.save_resource_nodes  -> resource_nodes 表
  ├── close_db()
  └── emit game_saved(slot)
```

### 读档流程

```
GameRoot.load_game_from_slot(slot)
  └── SaveManager.load_game(slot)
        ├── open_db(save_<slot>.db)
        ├── _load_legacy_modules()       ← legacy_modules -> WorldState.load_save_data()
        ├── emit game_loaded(slot)       ← GameRoot 缓存 current_map_id
        │   （DB 保持打开）
        ▼
  GameRoot._load_map_for_save() -> scene_loader.load_map(map_id)
        ▼
  _on_map_loaded -> _restore_from_save(map, map_id)
        ├── VillageMap.load_from_db()
        ├── ConstructionManager.load_from_db()
        ├── GameRoot._restore_entities()
        ├── VillageMap.load_resource_nodes_from_db()
        └── SaveManager.end_load()  ──── close_db()
```

### 自动存档

- **启动时**：检测槽位 0 是否有存档，有则自动读档，无则新游戏
- **初始加载后**：新游戏初始化完成后立即存档一次（`_initial_auto_save`）
- **退出时**：`NOTIFICATION_WM_CLOSE_REQUEST` 触发存档
- **定时**：SaveManager._process 定时存档（默认 60 秒，可通过 ConfigManager 配置）
- **手动**：F5 快速保存、F9 快速读取、Ctrl+S 打开存档面板

## 六、常见毒点排查

| 毒点 | 后果 | 正确做法 |
|------|------|---------|
| 运行时修改 .tres | 打包后只读失败，数据丢失 | .tres 只读，运行时状态写存档 |
| 建造状态存进 MapDefinition.tres | 存档与地图绑定，换地图丢失 | 建造状态存存档层 |
| 手动 BEGIN TRANSACTION 包高层方法 | "cannot start a transaction within a transaction" | godot-sqlite 高层方法自带事务，不要外包 |
| game_saving 信号在 DB 打开前 emit | get_db() 返回 null，场景图数据全丢 | 必须在 DB 打开后 emit |
| 无版本号的存档 | 升级后旧存档无法加载 | save_meta.version 字段 |
| 建筑实例复制模板数据 | 存档膨胀，改模板不生效 | 实例只存 def_id + 运行时状态 |
| 存档与场景节点混存 | 加载顺序耦合 | 存档是纯数据，加载时实例化场景 |

## 七、行业最佳实践

1. **Save/Load 分离**：存档是纯数据，加载时根据数据实例化场景节点
2. **ID 引用**：实例引用模板 ID，不内联模板数据
3. **增量存档**：大地图可按 Chunk 增量保存（减少写入量）
4. **存档校验**：加载时校验 version + 数据完整性
5. **异步加载**：大存档分帧加载，避免卡顿
6. **存档隔离**：每个存档独立数据库文件，避免交叉污染

## 九、地图编辑器插件需求（待设计）

### 目标
在 Godot 编辑器内提供自定义 Dock，辅助地图设计。

### 功能需求
1. **地图参数面板**：可视化设置 ground_y/ground_ratio/map_left/map_right/ground_bottom
2. **建筑槽位编辑**：在地图上放置/移除建筑槽位（预定义可建造位置）
3. **出生点编辑**：标记玩家/实体出生点
4. **Chunk 划分**：可视化 Chunk 边界，设置 Chunk 触发器
5. **导出**：生成 `MapDefinition.tres` + 修改 `.tscn`

### 技术方案
- `@tool` 脚本 + `EditorPlugin` + 自定义 Dock
- 复用 Godot 编辑器场景编辑能力
- 输出 `.tres` 资源（静态数据）+ `.tscn`（地形）

### 不做独立编辑器程序的理由
- 维护成本高，需独立项目
- 与 Godot 资源管线脱节
- 无法复用 Godot 编辑器能力
