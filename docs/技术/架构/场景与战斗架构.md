## 〇、文档目的

GDD 定义了"做什么"，本文档定义"怎么搭才不变屎山"。

P0 阶段三件事必须同时上线：
1. 火柴人行为 AI（特别是战斗 AI）
2. 小队级战斗（10-30 人）
3. 定居点建设基础逻辑

这三者高度耦合：工人建造时被袭击要切战斗 AI、战斗需要建筑作为掩体、建设需要建筑网格、战斗的编队直接复用组织系统的 L1 节点。本文档定义统一的场景骨架与模块边界，让三者各自开发但接口对齐。

## 一、设计原则（三条铁律）

### 1.1 逻辑层 ≠ 表现层

所有系统状态放在 `core/entities/` 的 State 对象里，**场景节点只是 State 的视图**。

- 火柴人 HP/位置/动画状态 → `StickmanState`
- 建筑血量/等级/占地 → `BuildingState`（新建）
- 战斗进度/参战双方 → `BattleState`（已有）
- 编制关系/指挥链 → `OrganizationState`（已有）

**场景卸载时 State 不丢**，挂载到新场景就能继续。这是支持"城镇就地变战场"、"快速旅行后状态延续"的基础。

### 1.2 常驻宿主 + 动态子场景

`GameRoot` 主场景常驻，村落/战场/室内都是动态加载的子场景。

- 环境、相机、UI、时间、输入分发跨场景保持
- 地图切换 = 替换 `WorldChunkHost` 的子节点

### 1.3 接口契约

模块间通信一律走 `api.gd` 或 EventBus。**任何 `get_node("../...")` 跨模块引用视为 Bug**。

依赖方向严格单向（见 §二 模块依赖图）。

## 二、模块依赖图（防循环依赖）

```
                    ┌──────────────┐
                    │  GameRoot    │ (常驻容器)
                    └──────┬───────┘
                           │
        ┌──────────┬───────┼────────┬──────────┐
        ▼          ▼       ▼        ▼          ▼
   Environment  Camera  SceneLoader  InputDispatcher  UIRoot
                           │
                           ▼
                    ┌──────────────┐
                    │  MapInstance │ (村落/战场/室内)
                    │  ├─PlacementGrid
                    │  ├─Buildings
                    │  └─StickmanEntities
                    └──────┬───────┘
                           │
        ┌──────────────────┼──────────────────┐
        ▼                  ▼                  ▼
   construction        combat             organization
        │                  │                  │
        └──────────┬───────┴──────────────────┘
                   ▼
                units (StickmanEntity + AI)
                   │
                   ▼
               StickmanRig (已有渲染)
```

**单向依赖规则**：
- 上层依赖下层，禁止反向
- `units` 不直接调 `combat`，由 `combat` 通过 `units/api.gd` 拉数据+下令
- `combat` 不直接调 `construction`，通过 EventBus 通知（如建筑被破坏）
- 跨模块引用 → 走 `api.gd` 或 EventBus

## 六、已知问题与技术债

> 按严重程度排序，每项含：现象、根因、影响、修复方案。
> 编号规则：以本文档为准；其他文档引用时指向本文档编号。
> 已解决批次的修复过程记录见 [CHANGELOG.md](../../CHANGELOG.md)「架构契约回写与已知问题清理」节；下文仅保留未决技术债与已解决项的现状。

### P0-1 🟡 Chunk 流式加载为空壳（中等）

- **现象**：`SceneLoader.preload_chunk()` / `unload_chunk()` 只有 TODO 注释，直接 emit 信号不实际加载（见 [scene_loader.gd](../../../stick-world/modules/world/scripts/loading/scene_loader.gd)）。实际实现的是"地图间出口触发器切换"（`ChunkTrigger.target_map_id` → `travel_to_map`），每张地图整张一次性加载。
- **影响**：P0 阶段单张地图足够小，性能可接受；"Chunk 流式加载"名不副实。
- **修复方案**：需要大地图时补全 `preload_chunk` / `unload_chunk`；可加 `push_warning("Chunk 流式加载未实现")` 避免静默失败。

### P0-6 🟡 ConstructionManager 部分数值硬编码（中等）

- **现象**：footprint_w / base_work / cost 已从 `config/buildings/buildings.tres` 按 `def_id` 读取；`total_work` 仍硬编码 `8.0`（construction_manager.gd:213）。
- **修复方案**：由 Excel build_time 驱动。

### P0-7 🟢 GdUnit4 未引入（规范冲突，决策已定）

- **现状**：项目使用自研 `TestRunner`（零断言守卫 + async 内建 + 断言扩充，见 [tests/README.md](../../../stick-world/tests/README.md)）；GdUnit4 列为 P1 引入项，待稳定后一次性迁移。**待办**：更新 rule.md 措辞为"建议"而非"必须"。

### P0-8 🟢 RefCounted 持有 Node 引用的生命周期风险（轻微，架构隐患）

- **现象**：[battle_ai_director.gd](../../../stick-world/modules/combat/scripts/battle/battle_ai_director.gd) `extends RefCounted` 但持有 `BattleInstance`(Node) 引用。RefCounted 生命周期不与 Node 绑定，节点 `queue_free` 后仍调用会访问已释放节点。
- **现状**：靠 `is_instance_valid()` 检查规避。
- **修复方案**：长期应改为 Node 挂到场景树，或用弱引用（WeakRef）。

### P0-12 🟢 延后 战斗结束判定（规划延后，不在 P0 范围）

- **现象**：战斗以全灭即结束，无胜负收束能力（溃散判定/尸体处理/溃兵回场）。
- **现状**：P0 战斗基础已可用，收敛能力依赖战斗与碰撞系统稳定后实施，列为低优先级待办（见 [待办事项.md](../../项目/待办事项.md)）。
