## 二、架构合规

### P1-1 依赖审计工具结论不可信

`tools/audit_deps.py` 存在两个缺陷，导致它输出的依赖环结论**不可用**：

1. **注释与字符串未剥离**（第 59 行）。在文件全文里正则匹配 `class_name`，
   注释里提一句就算一条依赖边。实例：`player_control/scripts/input_dispatcher.gd:18`
   的注释「Building 不再直调 dispatcher」被识别成 `player_control → building_gen` 依赖。
   它所报的两个环（`player_control↔building_gen`、`combat↔world`）**均为误报**。
2. **环检测不稳定且不全**。用 `set` 聚合邻接表，遍历顺序随机，每次运行得到不同结果
   （两次运行分别报 `player_control↔building_gen` 与 `units→units`）；
   且 `find_cycle` 找到第一个环即返回，不枚举其余。

后果：修正前仓库里"看起来"有 2 个环，实际有 38 个，且**没有一个重合**。
依赖图同样失真——`world` 被标为依赖 13 个模块（注释虚高），
而只按类名建边时又只剩 6 个（漏掉 29 条 preload 边），真实值是 12 个。

本轮已同步修正该工具（剥离注释/字符串、`core/` 下统一归并、有序聚合、
枚举全环并按二元/三元/更长分组输出），并为其装配器 `system_setup.gd` 的
29 处 preload 建立豁免——composition root 需按具体类型注入，不属越界违规。
以下数据均为修正后实测。

### P1-2 真实依赖环 38 个

实测 38 个环：**7 个二元环（根因）+ 10 个三元环 + 21 个更长环**。
修掉二元环，由其组合出的长环会一并消失。

| 二元环 | 中介类 | 性质 |
|---|---|---|
| `fx ↔ world` | `WorldZ` ← → `FxPool`/`FxLibrary` | `WorldZ` 是纯常量类 |
| `construction ↔ world` | `WorldZ`（build_progress_indicator:33 等） | 同上 |
| `units ↔ world` | `WorldZ`（health_bar_indicator:27 等） | 同上 |
| `debug_GUI ↔ world` | `WorldAPI.PATH_*`（debug_drawers:39/111/116） | 调试绘制器直读世界路径常量 |
| `ui_global ↔ world` | `WorldAPI`（settings_menu_panel:358） | 设置面板直调 world API |
| `player_control ↔ ui_global` | `StickKit` ← → `PlayerControlAPI` | UI 工具与业务 API 互引 |
| `ui_global ↔ ui_placeholder` | `UIPlaceholderPanel` ← → `StickScreen`/`UIKit`/`UIModalStack` | ui_placeholder 实为 ui_global 的附属 |

**`WorldZ` 是 3 个二元环的共同根因**（fx、construction、units 均通过它指向 world）。
它是纯 z 序常量表，不属于 world 模块语义，下沉到 `core/` 一次即可断开 3 个环——
这是全部架构整改中性价比最高的一项。

其余拆解优先级：

- **`ui_global ↔ ui_placeholder` 次之**：ui_placeholder 只有 4 个脚本、无独立业务语义，
  合并进 `ui_global` 后环自然消失。
- **`debug_GUI ↔ world`、`ui_global ↔ world`**：均经 `WorldAPI` 路径常量，
  可考虑将路径常量下沉或改由装配注入。
- **`player_control ↔ ui_global`** 需接口反转或事件解耦，改动面较大，建议排期。

### P2-1 `fx` 模块缺少 `api.gd`

15 个模块中 14 个有 `api.gd`，唯独 `fx` 没有。而 `fx` 对外暴露了 `FxPool`、`FxLibrary`
两个全局类并已被 `system_setup.gd`、`health_component.gd` 跨模块使用，
属于事实上的公共接口却无契约文件。

### P2-2 跨模块越界 preload 32 处

按"只走 `api.gd`"契约统计，其中 **29 处集中在 `system_setup.gd`**（装配器，
出于依赖注入需要必须知道具体类型，属设计使然，建议在工具里加白名单），

```

modules/world/scripts/game_root.gd:27             → modules/ui_global/scripts/overlays/world_loading_overlay.gd
```

### P3-1 EventBus 6 个信号零订户

30 个信号中 6 个只有 `emit` 无 `connect`：`balance_changed`、`selection_changed`、
`squad_created`、`order_issued`、`chunk_loaded`、`chunk_unloaded`。
`event_bus.gd` 头注释已将其标注为"单向广播（UI/外部接入时连接）"，属有意保留。

**仓库中不存在 `export_presets.cfg`**，即项目从未配置过导出。后果是以下三类内容
会在首次打包时被原样打进玩家包：

| 内容 | 体积 | 是否应入包 |
|---|---|---|
| `config/strategic_map/**/*.json` | 99.2 MB | 否（运行时命中同名 `.bin`，json 仅作烘焙输入与回退网） |
| `assets/_raw/`（AI 生成原图） | 28 MB | 否（参考素材，未入库但本地存在） |
| `modules/*/materials/*/reference/` | 数 MB | 否（调参参考图） |

仅排除战略图 json 一项即可减少约 **100 MB** 包体。
待办事项中"发布导出排除战略图 json"一条已记录但前提（配置导出预设）从未成立。

### P2-5 战略图数据入库 171.8 MB


或移出 `config/` 单独的烘焙输入目录（如 `tools/worldgen/output/`），从源头分离。

## 附：审计方法

机械指标通过一次性脚本扫描（`.tmp/` 下，未入库），关键结论均经过人工抽样复核：

- 依赖分析：剥离 GDScript 注释与字符串后，按 `class_name` + `preload`/`load` 建边，DFS 枚举全部简单环
- 死代码判定：`class_name` 零引用 **且** `res://` 路径与 `uid://` 均无引用，排除 autoload/tests/tools
- 资源孤儿：`.import` 与源文件配对检查；引用检查覆盖 `.gd`/`.tscn`/`.tres`

**复核要点**：死代码判定必须按 `class_name` 而非文件名。按文件名初判时
`world_map/data/` 下 12 个类看似全部零引用，按 class_name 复核后实为 2 个
（`PoliticalData`、`WorldMapData`），误报率 83%。
