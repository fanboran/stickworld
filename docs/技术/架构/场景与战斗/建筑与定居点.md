## 四、建筑系统

### 4.1 资产分层（型号 vs 等级）

**核心规则**：建筑**型号**决定 `.tscn`，**等级**决定 `.tres` 数据。同型号不同等级 = 同场景 + 不同 Resource。

```
assets/buildings/
├── components/                    # 通用组件素材
│   ├── walls/                     (墙、屋顶、门的贴图集)
│   └── props/                     (桌椅、火炉等装饰)
└── templates/                     # 一种型号一个 .tscn
    ├── house/house.tscn
    ├── blacksmith/blacksmith.tscn
    ├── blacksmith/blacksmith_interior.tscn   # 内部场景
    ├── barracks/barracks.tscn
    └── ...

config/buildings/                  # 数据驱动（已有 buildings.tres 基础上扩展）
├── house_tier1.tres               # 等级配置：贴图变体、占地格、容量、HP
├── house_tier2.tres
└── ...
```

**贴图尺寸 vs 占地尺寸（解耦）**：
- **占地尺寸**（`footprint_w`/`footprint_h`）= 格子数 × 32px，决定 PlacementGrid 占用
- **贴图尺寸**任意，可以比占地大或小
- 例：一棵树占地 1×1（32×32px，树根），贴图 96×192px（树冠很宽很高），Sprite2D 用 `offset = (-32, -160)` 让树冠向上向左展开
- 贴图超出占地范围不冲突，PlacementGrid 只校验占地格子

**程序化建筑扩展点（架构已就绪，P0 不实现）**：
建筑场景根节点可挂 `procedural_building.gd` 脚本，`_ready()` 中根据 `variant_seed` + `terrain_context`（地形类型、周围建筑、海拔）调用 `RandomNumGenerator` 选择 sprite 子集拼接。
- 建筑数据表（xlsx）新增字段：`procedural: bool`、`variant_seed: int`、`terrain_adaptive: bool`
- 地标建筑：地图设计时放置 `procedural=true` 实例，每个 `variant_seed` 不同 -> 每个地区天然不一样
- 玩家建筑：建造时传入 `terrain_context`，建筑脚本根据 context 生成不同造型
- 当前建筑场景文件设计为"可挂脚本"就为以后留好了口子，无需改架构

### 4.2 占地网格（32px 高精度）

```
modules/world/placement_grid/
├── placement_grid.gd              # 网格管理
├── grid_cell.gd                   # 单元格
└── placement_validator.gd         # 校验是否可建
```

每个 Map 持有一个 `PlacementGrid`：
- `cell_size = 32px`
- 每个建筑占据 N×M 个 cell（小屋 2×2、兵营 3×3、宫殿 8×6）
- **一块地只能建一个建筑** = cell 占用检查
- 选址预览 = ghost 建筑半透明 + 网格高亮（绿=可建/红=冲突）

**BuildMask 不可放建筑区域（地形限制）**：

PlacementGrid 新增 `blockage_mask: PackedByteArray`（与 grid 同尺寸），标记"地形上不可放建筑"的格子：

```gdscript
# PlacementGrid 新增字段
var blockage_mask: PackedByteArray  # 1=不可放建筑（大石头/山坡阶梯处/装饰物占地）

func is_blocked(x: int, y: int) -> bool:
    return blockage_mask[y * grid_width + x] == 1

func is_occupied(x: int, y: int) -> bool:
    # 原有建筑占用 OR blockage_mask = 1
    return _cells[y * grid_width + x] != "" or is_blocked(x, y)
```

**设计时操作**：地图场景的 `BuildMaskLayer` 节点下加 `ColorRect`（红色半透明，仅设计时可见），运行时 `_ready()` 读取这些 ColorRect 的位置尺寸，注册到 `PlacementGrid.blockage_mask`。

**与"路障建筑"方案对比（已否决）**：
- 路障建筑方案被否决，原因：污染建筑系统、调试显示乱、拆除逻辑需特殊处理
- BuildMask 是纯数据，不会误删、不会出现在建筑列表、与 PlacementValidator 自然集成
- 玩家尝试在 BuildMask 区域放建筑 -> PlacementValidator 返回冲突，提示与"建筑占用"相同的错误信息

**调试显示**：DebugOverlay 开启时，BuildMask 格子显示为红色半透明（详见 [UI与环境.md](UI与环境.md) §10.5）。

### 4.3 建筑节点结构

```
Building (Node2D)                   ← 运行时实体
├── Footprint (CollisionShape2D)    ← 占地碰撞，对应 PlacementGrid 占用
├── Exterior (Node2D)               ← 屋顶 + 前墙（默认可见）
│   └── WallFront (Sprite2D)        ← 进入交互区时 modulate.a → 0.3
├── Interior (Node2D)               ← 内部空间 + NPC + 工作位
│   └── 默认 visible=false，进入交互区时 visible=true
├── InteractionZone (Area2D)        ← 玩家进入触发"室内模式"
├── PassageBarrier (StaticBody2D)         ← 建筑级通行障碍（见 [战斗与AI.md](战斗与AI.md) §7.1.2）
│   └── CollisionShape2D[]          # 矩形障碍区域，火柴人不可穿越
├── HealthComponent (Node)          ← HP/伤害
├── WorkSlot (Node2D)[]             ← 工作位（工人 AI 寻路目标）
└── CoverMarker (Node2D)[]          ← 掩体标记（战斗 AI 查询）
```

**建筑级 PassageBarrier（建筑本体不可通行区域）**：

建筑场景设计时，在 `PassageBarrier` 节点下加 `CollisionShape2D`（RectangleShape2D），划定建筑本体哪些区域火柴人不可穿越。与地图级 `WalkBarrier` 共用同一套碰撞查询（详见 [战斗与AI.md](战斗与AI.md) §7.1.2）。

**典型用例**：

| 建筑类型 | 通行规则 | PassageBarrier 配置 |
|---------|---------|---------------------|
| 雕像（小） | 角色从上下两侧都可绕过 | 本体一小块矩形（仅雕像基座） |
| 房屋 | 角色只能从房屋下方通过 | 覆盖房屋上半部分（墙体），下方留空 |
| 兵营 | 角色可从下方过，正门交互进入 | 覆盖建筑上半部分 + 左右两侧 |
| 矿山（地形建筑） | 角色完全不能穿过 | 整个占地范围全覆盖 |
| 树木（装饰） | 角色可绕过 | 仅树根一小块 |

**设计原则**：
- PassageBarrier 形状可与占地不同（占地是水平条带宽度，PassageBarrier 是物理碰撞）
- 例：房屋占地 3 格宽（96px），PassageBarrier 只覆盖上半部分 96×64px，下方 96×32px 留给角色通行
- 设计时在建筑场景编辑器直接绘制 CollisionShape2D，所见即所得
- 调试显示：DebugOverlay 开启时，建筑 PassageBarrier 显示为紫色半透明（与地图级 WalkBarrier 蓝色区分，详见 [UI与环境.md](UI与环境.md) §10.5）

#### 4.3.1 工地临时障碍

建造中的建筑在 `ConstructionProject._start()` 时创建临时障碍，阻挡通行直到完工：

- 障碍挂在 `MapInstance.WalkBarrier` 下（与地图级障碍同层）
- **尺寸和位置从建筑场景模板读取**：实例化 `building_scene`，读取 PassageBarrier CollisionShape2D 的 size/position，确保与完工后建筑的 PassageBarrier 完全一致
- 障碍世界坐标 = `(cell_x*32 + offset_x, building_origin_y + offset_y)`，其中 `building_origin_y = baseline - collision_bottom_local`
- 完工时 `_complete()` 移除临时障碍，建筑自身的 PassageBarrier 接管

> **之前的问题**：硬编码 `width*32` 和 `ground_y + baseline_offset - 190` 导致与建筑实际 PassageBarrier 有 5px 偏移（`collision_bottom_local`），且非标准宽度建筑尺寸不匹配。

#### 4.3.2 仓库建筑

- `bld_warehouse`：复制兵营素材改棕黄色调，作为搬运系统的取货点
- `ConstructionManager.get_nearest_warehouse(pos)` 查找最近的已完工仓库
- 仓库预置在 cell 15（土路区内），NPC 生成在仓库右侧（x=1050+）避免卡在障碍内

#### 4.3.3 玩家交互检测

玩家附身时按 E 与仓库/工地交互：

- **检测范围**：从建筑 PassageBarrier CollisionShape2D 读取真实世界边界（`_get_building_barrier_bounds`），+ 80px margin，不再用 `distance_to(global_position)` 球形检测
- **交互弹窗**：挂到 `foreground_layer`（z_index=10），显示在目标建筑上方（`ground_y - 280`），带 StyleBoxFlat 暗色圆角背景
- **交互逻辑**：
  - 仓库 + 未搬运 -> 拿起建材（`set_carrying(true)`）
  - 仓库 + 搬运中 -> 放回材料（`set_carrying(false)`）
  - 工地 + 搬运中 -> 交付材料（`project.deliver_material()`）
  - 工地 + 未搬运 + 材料充足 -> 敲击建造（`project.add_build_progress()`，播放 build 动画 1.8s）
  - 工地 + 未搬运 + 材料不足 -> 无操作（等待搬运工）

> **🔄 模块化重构后（B0+ 阶段，详见 [建筑模块化设计.md](../建筑模块化设计.md)）**：
> 上面的 `Exterior + Interior` 双层结构将被**分层 + 模块化结构**取代：
> ```
> BuildingEntity
> ├── Layers[0..N-1]
> │   └── BuildingLayer
> │       ├── BackLayer z=0     # 后景墙/柱
> │       ├── Floor z=4         # 每层地板（始终可见）
> │       ├── Modules_Slot z=5  # 本层模块（锻造作坊/住所/仓库...）
> │       └── FrontLayer z=10   # 前景墙/柱（模块格处自动挖洞，让模块外可见）
> ├── Roof z=11                 # 屋顶（材质决定形状）
> ├── InteractionZone
> └── PassageBarrier / Footprint
> ```
> §4.3 本节描述的 `Exterior + Interior + WallFront` 为 P0 阶段简化版，重构后仅为兼容旧接口保留路径。**新增建筑请走 [建筑模块化设计.md](../建筑模块化设计.md) 的 BuildingDef + BuildingGen 路径**。

### 4.4 村落差异化（抹除单调感）

每个 `VillageDefinition.tres`：

```
village_id: "north_pass"
biome: PLAINS                       # 决定环境基调
wall_height: 4                      # 城墙高度（影响防御）
ground_tint: Color(0.9, 0.85, 0.7)  # 地面色相微调
unique_buildings: ["windmill"]      # 独有建筑（独有贴图）
ground_props_density: 0.6           # 装饰物密度
chunk_count: 8                      # chunk 数
ambient_sfx: "village_plains"       # 环境音
```

七八个村落 = 七八个 `.tres`，**复用同一套 building templates**。独有建筑单独建 `.tscn`。

**不同城镇类型的地面贴图差异化（创始人确认）**：
- 不同类型的城镇应有**不同类型的硬化地面贴图**（不只是色相微调）
- 例：矿业城镇地面有碎石/矿渣纹理，农业城镇地面有泥土/草皮纹理，军事城镇地面有夯土/石板纹理
- `VillageDefinition.tres` 新增 `ground_texture_type` 字段，决定使用哪套地面贴图
- 当前 `VillageMap._load_ground_texture()` 按 biome 加载地面纹理，后续扩展为按 `ground_texture_type` 加载
- 与 `ground_tint`（色相微调）正交：`ground_texture_type` 决定贴图内容，`ground_tint` 决定色调

### 4.5 建筑三层架构（地形 / 初始 / 玩家）

游戏内有三种建筑来源，它们**和平共存**，通过同一套独立场景文件加载，但存储位置和可修改性不同。

#### 4.5.1 三层对比

| 层 | 存储格式 | 可破坏 | 加载时机 | 示例 |
|---|---|---|---|---|
| **地形建筑层** | 地图场景 `.tscn` 中 `TerrainBuildings` 节点 | 否 | 随场景实例化 | 矿山、遗迹、大石头 |
| **初始建筑层** | 地图场景 `.tscn` 中 `InitialBuildingsList` 列表（def_id + cell_x + width） | 是 | 地图加载后写入存档 | 关卡设计放的民居 |
| **玩家建筑层** | 存档 `.json` | 是 | 存档加载时实例化 | 玩家新建的农场 |

#### 4.5.2 为什么不会冲突

三者都使用**同一套建筑场景文件**（`modules/buildings/scenes/<building_id>.tscn`），只是加载时机不同。`PlacementGrid` 是统一占位登记表，三层建筑都向它注册，避免格子被重复占用。

```
地图加载流程：
1. SceneLoader 实例化 map.tscn
   └── TerrainBuildings 下的建筑自动随场景创建（静态，注册到 PlacementGrid，标记 is_terrain=true）
2. VillageMap._ready() 读取 InitialBuildingsList
   └── 首次进入该地图：将列表写入存档 JSON 的 buildings 数组
   └── 非首次：跳过（存档已有）
3. SaveManager 读取存档 JSON
   └── 对每个动态建筑实例（初始 + 玩家）：
       ├── 加载对应场景文件
       ├── 实例化后 add_child 到 BuildingHost
       └── 注册到 PlacementGrid
```

### 4.6 Tilemap 适用性分析

> 触发原因：当前建筑是程序化可调整大小的，需评估是否适合用 Tilemap 替代。

**结论：建筑不适合 Tilemap，地面资源/障碍物用独立 Node2D。**

#### 建筑为何不用 Tilemap

| 维度 | 程序化建筑（当前方案） | Tilemap |
|------|----------------------|---------|
| 宽度可变 | ✅ width 参数（N×32px）灵活 | ❌ 固定格子，需拼 Tile 凑宽度 |
| 多层节点结构 | ✅ Exterior/Interior/WallFront/PassageBarrier/InteractionZone 等复杂子节点 | ❌ Tile 只有 sprite + collision，无法表达交互区/触发器/工作位 |
| 贴图与占地解耦 | ✅ 贴图可超出占地（树冠向上展开） | ❌ Tile 固定在格子内 |
| 程序化生成 | ✅ BuildingGen 按 BuildingDef 生成 | ❌ 需预绘制 TileSet |

**建筑占地不需要垂直分格子**（创始人确认）：建筑只占水平条带（width 个 32px 宽条带），不关心垂直方向占地。现有 PlacementGrid 水平条带方案已满足需求。

#### 地面资源/障碍物：独立 Node2D + 垂直随机

自然形成的障碍物和资源点需要**垂直方向上随机生成**（创始人确认），例如：
- 树木在山坡不同高度
- 石头散布在地面各处
- 铁矿脉在特定深度

**方案：独立 ResourceNode（Node2D）**
- 水平 X 坐标对齐到 32px 网格（与 PlacementGrid 兼容）
- 垂直 Y 坐标在 `ground_y ~ ground_bottom` 范围内随机
- 每个 ResourceNode 含：`resource_type`、`amount`、`regen_rate`、`PassageBarrier`（碰撞）
- 不用 Tilemap，因为垂直随机不适合固定网格

**为何不用 TileMap custom data layer**：
- TileMap 的 cell 是固定网格，垂直随机需 cell 内偏移 Y，不直观
- ResourceNode 需要独立碰撞体（Area2D）+ 交互逻辑，TileMap collision 无法满足
- 独立 Node2D 更灵活，可直接挂脚本处理采集逻辑

> **TileMap 适合的场景（未来）**：地面纹理重复渲染（草地、道路、水面）、纯装饰性网格元素。当前 `GroundPolygon` 已满足 P0 需求，未来大面积地形可考虑 TileMap。

### 9.2 建造流程（耦合点明示）

```
玩家选择"建造铁匠铺"
  ↓
placement_system 启动选址模式（InputDispatcher.set_mode(BUILD)）
  ↓
玩家移动 ghost 预览 → placement_grid.is_valid() 校验
  ↓
确认 → construction_project 创建（占用 grid cell）
  ↓
work_crew_assigner 从组织系统拉施工队
  ↓
工人 AIController 切换到 behavior_work（走过去+施工动画）
  ↓
进度推进 → 工程量 = base_work × difficulty / (worker_count × efficiency)
  ↓
完成 → 实例化 building.tscn 到 Map → 触发 building_completed 事件
```

### 9.3 工程量系统（非固定建造时间）

```gdscript
remaining_work = base_work  # 例如铁匠铺 = 100 工时

# 每帧推进
func _process(delta):
    var worker_count = _get_assigned_workers().size()
    var efficiency = _get_crew_efficiency()  # 受组织水平影响
    var work_done = worker_count * efficiency * delta
    remaining_work -= work_done
    if remaining_work <= 0:
        complete()
```

**与战斗的耦合**：工人被袭击 -> `behavior_work` 中断 -> 切到 `behavior_flee` 或 `behavior_attack`。施工暂停。这就是为什么必须一起设计。

### 9.5 双进度条建造系统（创始人确认）

> **设计决策**：建造进度条分两层--材料进度 + 建造进度，建造进度不能超过材料进度。

#### 9.5.1 设计动机

当前建造系统是"工程量驱动"（`remaining_work` 单一进度），工人直接推进工程量即可完工。但实际建造应有两个阶段：
1. **材料运输**：材料从资源点/仓库运到工地
2. **施工建造**：在工地用材料施工

没有材料不能建造，因此建造进度受限于材料进度。

#### 9.5.2 双进度模型

```
ConstructionProject
├── material_progress: float (0.0 ~ 1.0)   # 材料运输完成度
├── build_progress: float (0.0 ~ 1.0)       # 施工完成度
└── 约束: build_progress <= material_progress  # 建造不能超过材料
```

**推进逻辑**：
```gdscript
func tick(delta: float):
    # 1. 搬运工推进材料进度
    var haulers = _get_haulers()
    material_progress += haulers.size() * HAUL_EFFICIENCY * delta
    material_progress = clamp(material_progress, 0.0, 1.0)
    
    # 2. 建造工推进建造进度（受材料进度限制）
    var builders = _get_builders()
    var build_delta = builders.size() * BUILD_EFFICIENCY * delta
    build_progress += build_delta
    build_progress = min(build_progress, material_progress)  # 建造 ≤ 材料
    
    # 3. 完工判定
    if build_progress >= 1.0:
        complete()
```

#### 9.5.3 工人角色分配

| 角色 | 职责 | 推进 | 行为 |
|------|------|------|------|
| 搬运工（Hauler） | 从资源点/仓库搬运材料到工地 | `material_progress` | 前往资源点 -> 搬运 -> 走到工地 -> 卸货 |
| 建造工（Builder） | 在工地施工 | `build_progress`（受 material_progress 限制） | 在工地待命 -> 施工动画 |

P0 简化：工人自动分配角色（`WorkCrewAssigner` 按 1:1 比例分配搬运工和建造工）。

#### 9.5.4 UI 显示

建筑头顶双进度条：
```
┌─────────────────────────┐
│ ████████░░░░  材料 60%  │  ← 蓝色
│ ██████░░░░░░  建造 40%  │  ← 绿色（不超过材料条）
└─────────────────────────┘
```

- 上方蓝色条：材料进度（material_progress）
- 下方绿色条：建造进度（build_progress）
- 建造条永远不超过材料条长度
- 材料条满后，建造条可继续推进到满

P0 阶段可简化材料运输环节：

- 不需要物理运输动画，只需时间推进 + 进度条显示
- 后续阶段加入真实运输路径 + 物流系统
