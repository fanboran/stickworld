## 〇、本文档要解决的问题

P0 各环节（村庄建设/编队/战斗引擎/跨图行军/出城交互）均已存在且测试通过，但**循环没有扣上**：战斗没有目标（世界里无敌据点）、没有出口（打赢无占领/无收益）、没有下一个理由（无难度阶梯）。本文定义把循环扣上的**最小技术方案**——全部复用现有件，新增一个 `modules/expansion/` 模块（世界地图数据流 §8.5 早已预留）做流程编排。

**核心原则**：expansion 模块是**流程编排者**，不是新引擎——战斗归 combat、行军归 world/SceneLoader、单位归 units、渲染归 world_map，expansion 只持有领地数据与状态机，通过 EventBus 与各系统对话。

## 一、模块结构

```
modules/expansion/                        # 新模块（world_map 数据流 §8.5 预留位）
├── api.gd                                # 对外契约（详见 §五）
├── scripts/
│   ├── territory_registry.gd             # 领地清单（读 territories 配置）+ 状态查询 + 存档序列化
│   ├── conquest_manager.gd               # 征服流程状态机：出征 → 战斗绑定 → 占领 → 奖励 → 通关判定
│   └── garrison_spawner.gd               # 守军生成（复用 UnitsApi spawn + behavior_profiles 兵种档案）
└── (UI 复用 world 侧 siege_gate_prompt，征伐面板 conquest_panel.gd 挂 modules/world 或 expansion/ui/)
```

**装配**：`SystemSetup` 动态挂载（与 SaveHandler/TravelHandler 同模式，见 `system_setup.gd`）——GameRoot 启动时创建 `ConquestManager` 节点、注入 SceneLoader 引用、`TerritoryRegistry.load_config()`。

**为什么挂 GameRoot 常驻**：领地状态跨图存活（出征途中/回村途中都要查询），且要监听全局 `battle_ended`。

## 二、数据契约

### 2.1 领地配置（静态，Excel 管线）

`config/expansion/territories.tres` —— 与现有 `regions.tres`/`factions.tres` 同管线（`config/excel/扩张数据.xlsx` 增 `territories` sheet 自动导出）。首版字段：

| 字段 | 类型 | 说明 |
|---|---|---|
| `id` | String | 如 `ter_bandit_camp_01` |
| `name_zh` | String | 据点名（出城选项/通告显示） |
| `map_id` | String | 对应场景图（`SceneLoader.register_map` 的 id） |
| `settlement_key` | String | 战略图聚落关联（L1 世界包聚落 id，占领后染色的目标） |
| `garrison` | Array | 守军条目：`{profile: 兵种档案id, count: 数量, tier: 档位}`（复用 `config/combat/tactics.tres` + `behavior_profiles`） |
| `commander` | Dictionary | 敌将：`{profile, retreat_thresholds: {casualty_rate, loss_ratio, timeout}}` 撤仗评估参数 |
| `rewards` | Dictionary | `{resources: {wood: n, stone: n, coin: n}, unlocks: [unlock_id]}` |
| `entry_side` | int | 玩家进入方位（守军布阵参考） |

首版 3 座据点，守军 3→5→8 人递增；数值为 AI 提案，实测定稿。

### 2.2 运行时状态（WorldState 新域）

```gdscript
# core/autoload/world_state.gd 新增（与 regions/battles 平级）
var territories: Dictionary = {}   # {territory_id: {state: int, garrison_losses: int}}
# state: TerritoryState.HOSTILE / CAPTURED
# garrison_losses: 车轮战累计战损（守军持久化，见 §六-体验设计）
```

存档走 WorldState 现有序列化（`_SQL_WS_SELECT` 路径），无需新表。

### 2.3 敌据点场景图

- **来源**：优先改造现有 `l1_settlement_02/03/04.tscn`（已注册、已可进入），挂 `ConquestAnchor`（Node2D，标记守军刷区/敌将位/敌营装饰）；不满足玩法再从 VillageMap 模板派生。
- **Anchor 契约**（对齐 `MapInstance.BattleAnchor` 先例）：`GarrisonSlots`（守军出生点数组）+ `CommanderSlot`（敌将位）+ `RallyX`（守军集结线）。`GarrisonSpawner` 读 Anchor 布阵，不写死坐标；据点图未挂锚点时程序化布阵 fallback（右侧半区横排），不阻断玩法。
- **车轮战扣减语义**：剩余守军 = 配置 count 之和 − `garrison_losses`；剩余配额从 garrison 条目**头部起填满**（前排主力优先满编，后排先缺），条目结构保留（count 归零不删行）；`commander`（敌将）不受扣减，每次进图均在位。`GarrisonSpawner.spawn_garrison(map, territory_id)` 返回守军实体名单（含敌将），供 ConquestManager 开战传 defenders。
- 已占领据点再次进入：不刷守军（`TerritoryRegistry.is_captured` 短路），据点图以友化形态运行（P0 即"空图可巡视"，旗帜装饰变化属润色）。

## 三、数据流总图

```
┌─ 出征（玩家发起）──────────────────────────────────────────┐
│ 村A 城门出城选项(siege_gate_prompt)                        │
│   └─ 动态项「⚔ 征伐 <据点名>（守军N）」← api.list_targets() │
│      └─ 选择 → ConquestManager.launch(territory_id)        │
│         └─ SceneLoader.travel_to_map(map_id)（带队跨图已有）│
└────────────────────────────────────────────────────────────┘
                         ▼
┌─ 接敌（到达据点图）────────────────────────────────────────┐
│ map_loaded(map_id) → ConquestManager 匹配 territory        │
│   └─ GarrisonSpawner 按 Anchor+garrison 配置刷守军          │
│      （数量扣减 garrison_losses——车轮战持久化）             │
│   └─ CombatApi.start_battle(map, attackers=玩家队,          │
│        defenders=守军, player_faction=玩家侧)               │
└────────────────────────────────────────────────────────────┘
                         ▼
┌─ 战斗与收束（combat 侧，详见 §四）─────────────────────────┐
│ BattleInstance 逐时判定：守军全灭 或 敌将撤仗（RETREAT 撤离）│
│   └─ EventBus.battle_ended(battle_id, victory=玩家阵营胜)  │
└────────────────────────────────────────────────────────────┘
                         ▼
┌─ 占领与收益（expansion 侧）────────────────────────────────┐
│ ConquestManager._on_battle_ended → 匹配 territory：        │
│   1. 状态 HOSTILE→CAPTURED，WorldState.territories 写入     │
│   2. 奖励发放：资源入账(ResourcesApi) + unlock_granted 信号 │
│   3. EventBus.territory_state_changed(id, CAPTURED)        │
│      └─ 出城选项刷新（显示"已臣服"）                        │
│   4. EventBus.region_owner_changed(settlement_key, 玩家)   │
│      └─ 战略图 L1/L2 政治模式聚落染玩家色（接收端已有染色   │
│         骨架，见 world_map 数据流 §7.3）                   │
│   5. 若全部 CAPTURED → conquest_completed → 通关结算        │
│      （victory_overlay 复用，统计：占领数/用时/累计伤亡）   │
└────────────────────────────────────────────────────────────┘
                         ▼
回村 → 出城选项里的下一个目标 → 循环
```

**败仗路径**：玩家侧全灭 → `battle_ended(victory=false)` → ConquestManager 记录 `garrison_losses`（守军战损持久化）→ 玩家传回村A（复用现有重生/传送处理）→ 不判负、可再征。

## 四、战斗侧改造（combat 模块，与出征循环互赖）

### 4.1 victory 语义修正（破坏性契约变更，一次到位）

`battle_ended(battle_id, victory)` 的 `victory` 从 **attacker_wins** 改为 **玩家阵营胜**：

- `BattleInstance` 新增 `player_faction: int`（`start_battle` / `add_unit` 链路传入；未传时回退 attacker 语义保旧测试兼容）
- `_end()` 中 `victory = (result 对应胜方 == player_faction)`
- **监听方适配**：`demo_quest.gd`（第四阶段重写后按新语义）、`global_hud.gd`（通知文案）、`audio_manager.gd`（胜负音效）——三处现按 attacker 语义消费，随本次一并修正

### 4.2 敌将撤仗判定（人机 AI，TeamAi 接线）

TeamAi（阵营姿态机，`enable_team_ai` 现仅测试调用）在**据点战自动启用**，并扩展战役评估输入：

```gdscript
# team_ai.gd 新增评估（周期 = stance_decision_interval，参数来自 territory.commander）
# 触发条件（满足其一即判定"这仗不能打了"）：
#   - 伤亡率 = losses/garrison_total > retreat_thresholds.casualty_rate
#   - 战损比 = 敌我击杀比 > retreat_thresholds.loss_ratio（打不动对面）
#   - 相持超时 > retreat_thresholds.timeout（拿不下据点）
# 判定后：stance → ROUT，对全军发 OrderType.RETREAT（号令已有，接
#   behavior_retreat 有序后撤——GDD §2.2 撤退纪律：有序后撤而非溃逃）
```

**撤离判定**：RETREAT 状态单位行至地图边缘 `x < map_left + ε`（或 `> map_right - ε`）记为"离场"；**守军全部离场或全灭 = 据点攻陷**。BattleInstance 的 `_count_alive` 需把"离场"计为非存活（单位加 `departed` 标记，不销毁实体以便溃兵视觉）。

**接线开关**：据点战（有 commander 配置）才启用撤仗评估；普通测试战斗维持全灭判定——TeamAi 头注释"注册制零回归闸门"的设计意图在此兑现。

### 4.3 旧遭遇战退役

`battlefield` 图及 `game_root.gd:637` 的专属刷敌逻辑退役为 dev 验证用途（`tests/dev/verify_battle.gd` 保留直达调用）；正式流程从注册表移除其可达性（村A 左出口的注册保留给据点图复用或摘除）。

## 六、EventBus 新增信号（3 个）

| 信号 | 载荷 | 发射方 → 监听方 |
|---|---|---|
| `territory_state_changed` | `(territory_id: String, new_state: int)` | ConquestManager → 出城选项/征伐面板刷新 |
| `region_owner_changed` | `(region_id: String, new_owner: String)` | ConquestManager → **战略图政治模式聚落变色**（世界地图数据流 §7.3 早已定义此契约，本设计落实发射方；接收端在 world_map L1/L2 POLITICAL 染色逻辑挂钩） |
| `unlock_granted` | `(unlock_id: String)` | ConquestManager → 建筑系统/装备系统（P0 实装 1 个示例解锁，如箭塔建筑型号；其余解锁项各系统自听此信号） |

现有信号复用：`battle_started/battle_ended`（战斗生命周期）、`map_loaded`（到达据点触发接敌）、`travel_requested`（出征行军）、`quest_advanced`（演示目标链）。

## 九、P1+ 预留钩子（本期不实装，设计不堵死）

- `territories` 配置预留 `retaliation`（反扑事件→守城战接线）、`neighbors`（邻接解锁树）、`growth`（敌将增兵成长）字段位
- 战略图双击敌聚落=出征（入口二）：依赖 `settlement_key ↔ map_id` 映射（本设计已建立）
- 附庸/外交合并：TerritoryState 枚举预留位

### 9.1 P 社化演进预留（P0 与 GDD §一~五 的对齐声明）

P0 循环切片的是前期基因（合战忍者村/RTS：即打即得、离散据点、零管理代价）；GDD 扩张系统 §一~五 的 P 社要素（宣战理由/控制度/扩张代价/政权演化）归 P1+。以下三条是**现在就要对齐的数据语义**，避免 P 社化阶段重构 P0：

1. **`region_owner_changed` 的 region_id 语义对准地块（tile），不按据点存归属**。P0 的 3 座据点是"点"，但战略图归属数据（states/owner 体系）必须按"面"（L1 地块/tile）建模——据点只是地块的入口。为此：`territories` 配置的 `settlement_key`（聚落）旁边预留 `tile_key`（所属地块 id）字段位；C1 实装时 `region_owner_changed` 发 tile 级 id（P0 一座据点占一个 tile，语义等价），聚落染色作为 tile 变色的表现形式。P1 引入"占领聚落→辐射 claimed 周边地块"的桥时，只需把一格 tile 扩成多格，归属数据结构与信号契约不动。
2. **控制度（扩张系统 §2.2，0-100%）以字段扩展而非新状态**：`WorldState.territories[id]` 预留 `control_progress: float`（P0 恒 100%；占领即满值）。P1 引入时 `CAPTURED` 拆为"军事占领（occupied，控制度爬升中）→ 完全控制（100% 纳入版图）"，状态机枚举追加不替换，`HOSTILE→CAPTURED` 两态的消费者（出城选项/染色/通关判定）不受影响。
3. **宣战/代价/政权演化不进 ConquestManager**：P0 的 ConquestManager 只编排"出征→战斗→占领→收益"。P1 的宣战理由（GDD §3.1）、管理代价（§四）、AI 政权互相吞并（§五）属战略层势力 AI，将来落 `modules/expansion` 内独立子域（或独立模块）与 ConquestManager 并列，通过同一套 `region_owner_changed` / 新增 war 类信号对话——P0 的 api.gd 面向玩家征伐，不为战略层 AI 预埋接口。

## 十、决策记录

| 决策 | 结论 | 依据 |
|---|---|---|
| 循环正轴 = 主动出征（非守城） | 已确认 | 创始人确认合战忍者村式扩张；GDD §6.3 |
| 守军持久化允许车轮战 | 采纳 | 合战忍者村手感；自然难度曲线，免败负惩罚的状态管理 |
| victory 语义改玩家阵营胜（破坏性） | 采纳 | 守方/攻方双场景下 attacker 布尔不可用；一次改齐三监听方 |
| 敌将撤仗 = TeamAi 战役评估 | 采纳 | 创始人定性"敌方指挥官觉得这仗不能打了，是人机 AI 设计"；有序后撤符合 GDD §2.2 |
| 据点图复用 l1_settlement 改造 | 采纳 | 8 图已注册已可进；Anchor 契约避免写死坐标 |
| 出征 P0 直达 travel（不走道路步行） | 采纳 | 与"开守城战"同模式；道路串联行军属 P1（walk_legs 已有底子） |
| 据点数 3 座、守军 3/5/8 | AI 提案待定 | Excel 可调，实测定稿 |
