# 审计

审计类文档的归口目录。

**审计回答"实际怎样"**，与"规范"（应该怎样）、"设计"（打算怎样）分开放置——
三者混放会导致写规范的人不知道该往哪塞，也会让审计结论被误读为约定。

## 目录约定

| 子目录 | 用途 | 命名 | 更新方式 |
|---|---|---|---|
| `专项/` | 局部功能或主题的审计、对账、差异分析 | `<主题>.md` | 按需追加，可更新 |
| `总账/` | 某领域的持续缺口清单 | `<领域>缺口总账.md` | 长期维护 |

**快照生命周期**：全量审计（架构合规 / 代码质量 / 资源资产 / 文档与测试）完成后，
快照按 `YYYY-MM-DD` 命名直接存入 [`../项目/归档/`](../项目/归档/)（如
[`审计快照-2026-08-30.md`](../项目/归档/审计快照-2026-08-30.md)），
本目录不长期保留快照——历史记录归归档，在役文档归本目录。

## 三条原则

1. **快照不回改**。全项目审计记录的是审计当时的状态。整改进度交给 git 提交历史，
   不在快照里补记，避免同一份文档既是历史记录又假装是当前状态。
2. **总账唯一**。同一领域只允许一份缺口总账；新发现的缺口先补进总账再立项。
   总账以链接形式挂在 [`../项目/待办事项.md`](../项目/待办事项.md) 下，不自立第二套待办。
3. **规范与审计分离**。`docs/技术/规范/` 放"应该怎么做"，
   审计结论"实际做得怎样"放本目录。
