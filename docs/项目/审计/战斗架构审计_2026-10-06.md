## 三、确定性专项（P4 回放的前置债，五处泄漏）

sim 内核本身满足确定（物理定步长、strike 按 sid 序结算、帧号节流、常量单一真相源化）；以下五处使"同输入同输出"目前不成立：

1. **behavior_attack 墙钟**：`Time.get_ticks_msec()/1000.0` ≥5 处（behavior_attack.gd:349/420/432/511/515——post_block/burst_gate/burst_wait/aim）。与 ai_decision_clock.gd:55 自家明文规范（"不用实时钟，避免暂停/hitstop 期时钟空转"）**直接冲突**，且 hitstop 期间该时钟照走（decision_clock 正是为此改的累积钟）。两套计时体制并存于同一 AI 域。
2. **全局 randf 散布**：behavior_attack.gd:185/187/277/282/356-358/389/432/472/624-625（闪避/犹豫/游走/爆发/漂移掷骰全走全局 RNG）；ai_controller.gd:297/358/687 同款残留。对照同文件已做的 `_jitter_rng`/`_retreat_mod_rng` 种子化隔离（ai_controller.gd:105/113），**两套 RNG 体制并存**——回放需要"每单位可注入种子"全覆盖。
3. **HP/死亡权威在 Node**：HealthComponent 是血量权威（battle_sim.gd:17-20 明示"不迁移"），sim 的 `_sid_alive` 回读 `e.is_dead()`（battle_sim.gd:296）——sim 不是闭环状态机，胜负/死亡时序取决于 Node 侧事件链。
4. **EventBus 战斗信号无序**：battle_started/ended/settled、squad_created、order_issued 等（event_bus.gd:44-75）发射顺序=调用方到达序，P4 需帧内排序队列。
5. **sim↔单位 AI 相对顺序=场景树序隐式契约**：battle_instance._physics_process 先 `sim.tick` 再让各单位 AI 读位置写意图（battle_instance.gd:212 注释声明了意图），但 BattleAnchor 与单位节点的处理顺序由树序决定，无断言/顺序测试钉死——场景结构调整即静默改变时序语义。

**判断**：①②是行为域存量债，越晚治理迁移面越大；~~建议 P1 动 behavior_attack 刷新段时**同步**把墙钟→累积钟、全局 randf→单位种子 RNG 一并收口~~ **已执行（随 P1 同批）**：①墙钟五处→行为累积钟（post_block/burst）＋物理帧钟（arrow_threat_time 账本全线换基：weapon_ranged 写入、team_ai_snapshot/squad_phase_plan 消费同源）；②全局 randf→单位种子 RNG（behavior_attack 命运骰／ai_controller 三处：间隔方差归 `_jitter_rng`、闲逛与看门狗归新增 `_dice_rng`／weapon_mount 命中暴击掷骰顺带收口）。③④⑤属 P4 本体（⑤树序契约已随本批钉死：battle_instance 固化负 `process_physics_priority` ＋ integration/test_sim_tree_order 断言）。

## 四、解耦审计

### 4.1 依赖图与环（audit_deps.py 实跑）

- 战斗域出向边：combat→{formation, stick_rig, tactics}（全走 api.gd）；units→{combat, formation, fx, items, player_control, stick_rig, tactics, town_life}；formation→{tactics, ui_global}；tactics→{}（零出向✓，共享词汇表定位达成）；hd2d→{environment, stick_rig, ui_global, units}。
- 依赖环 3 个全在册（organization↔world / town_life↔units / world↔world_map），**棘轮 PASS 无新增**。
- 战斗五模块间**无环**：tactics(零出向)←formation←units/combat，单向。

### 4.2 违规扫描

- `get_node("../")` 上溯：**零命中**。
- 跨模块 preload 非 api：全仓 6 处（hd2d_world→ui_global sketch_cloud；world 装配面 5 处场景/展示件），均在册、无新增。
- ~~**hd2d→units 边为假阳性**：三处落点全是注释（char_sprite_3d.gd:276/730/750 提及 UnitLodDirector/WeaponMount）。audit_deps 自述"剥注释"对 `#` 行未生效——工具侧待修~~ **纠正（实证复查）**：strip_comments 对 `#` 行剥离正常（隔离单测验证）；该边是**真代码**——char_sprite_3d.set_weapon_type 直引 `WeaponMount.WeaponType.NONE`/`WEAPON_SCENE_PATHS`（数据真身本在 stick_rig api，units 侧仅 const 转发）= L1→L2 越层残留。**已修**：hd2d 直读 `StickRigAPI.*`，边消除（audit_deps 复跑确认 hd2d→仅 environment/stick_rig/ui_global，棘轮 PASS）。

### 4.3 契约缺口（~~唯一实质项~~ 已收口）

units 四文件（stickman_entity/entity_motion/weapon_mount/weapon_ranged）经 **class_name `BattleSim`** 直连 combat 内部实现，未经 combat/api.gd。combat/api.gd（113 行）只导出战斗生命周期门面。修法照 stick_rig/api.gd 导 `ANIMS_SCRIPT` 先例：api 导出 `BATTLE_SIM_SCRIPT` 常量，units 改 preload api——class_name 全局可见性恰是这类隐式依赖的温床（重命名即静默断四处）。
**已执行**：api 导出 `BATTLE_SIM_SCRIPT`；实引类型注解仅 stickman_entity/weapon_mount 两处（entity_motion/weapon_ranged 为注释提及），均已改走 api。

### 4.4 范本（保持）

镜像链解耦是全仓最优实践：hd2d 不 import units/stick_rig 之外的战斗域任何东西，feed 走 duck-typing Dictionary，由 L3 组合根（hd2d_map_base.gd:309）从 units.visual_controller 拉 `get_mirror_anim_state()` 推给 hd2d——L1 互不相识，切换 2D/HD-2D/无头纯 sim 三形态零侵入。

## 八、设计文档对齐轴（02-战斗系统 / 12-游戏AI / 01-组织 / 命名与数值口径）

### 8.1 总评

### 8.2 硬冲突：士气→mood→命中/冷却乘子，穿透 2026-09-29 创始人裁决（已裁决：士气系统整体删除，见文末）

裁决原文（02-战斗系统 §2.2）：「士气只影响行为决策（犹豫、撤退纪律、避战倾向），**不作伤害或属性乘子**——士气高的部队敢打敢冲、士气低的犹豫易退，但一刀砍出去的威力不随士气变。」

代码全链（逐环实证）：

- `HealthComponent.get_morale_ratio()` → `battle_ai_director.gd:81 _decide_mood`（士气<0.25 → 60% PANICKED；<0.5 → 40% HESITANT；>0.75 → 15% EXCITED——掷骰输入就是士气）；
- `weapon_mount.gd:1307 _get_effective_hit_chance`（HESITANT ×0.7 / PANICKED ×0.5 / EXCITED ×1.1）＋ `:1320 _get_effective_cooldown`（EXCITED ×0.85）；
- 12-游戏AI §7 机制开关总表（自称"唯一真相源，新增开关必须在此登记"）**三张表均无 mood 条目**；`set_mood` 注释引的"§7.4"实为开闸纪律节，非登记处。

定性：命中率与攻速是属性乘子，士气经 mood 中转后"士气低→打不中/士气高→出刀快"，恰是裁决禁止的语义（裁决允许"犹豫易退"的行为表达，禁止属性面）。机制亦未按开闸纪律登记。出路二选一（创始人裁决）：①若 mood→命中/攻速有 SWL dump 真值 → 12 号补登记＋02 裁决加例外注记；②无真值 → mood 改纯行为面（HESITANT＝瞄准犹豫拉长、PANICKED＝避战阈值下调），命中/冷却乘子退役（同族先例：ANIM_SPEED_MULT 1.4 无档出处复位 1.0）。

### 8.3 验收口径漂移：观察场默认档高于设计观感标定

02 二-B #1/二-A.1：观感标定基准＝**每侧最多十几~二十几人**（原作常态 10~25，单位大而少撑画面尺度），96 档封存。`battle_arena.gd` 预设＝遭遇战16/标准战役48/大军压境96，**默认 `_preset_idx=1`（48）**——近几轮观感验收全在 48 档跑，密度高于设计标定 2~3 倍（单位大而少的设计语义在 48 档天然失真，部分观感问题可能被密度放大）。~~建议：观感验收主档＝16（设计口径），48 改名"密度压力档"、96 极端压力档~~ **已执行**：默认 0=遭遇战·16（设计口径主档），48→密度压力·48、96→极端压力·96（battle_perf 标签/性能量测规范/战斗与AI.md 同步）。
