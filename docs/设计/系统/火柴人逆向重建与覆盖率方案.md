# 火柴人逆向重建与覆盖率方案

> **用途**：创始人拍板「从火柴人战争解包标准火柴人、从头逆向重建」后的实施总纲。
> 数据事实部分由解包数据直接推导（一手实测）；实施批次、阈值、取舍项属 **AI 提案，标「提案/待定」**，创始人可逐项改判。
> 配套交接档：`docs/项目/交接/火柴人视觉修复-进度与交接.md`（批次 4h 缺陷清单 D1~D11 在本文 §5.4 复验）。

## 一、真相源（是什么）

- **唯一权威数据源 = 游戏 APK 内嵌的 Spine 3.8 骨架 JSON**：
  `external/decompiled/legacy/spine_raw/核心单位骨架/[skeleton].txt`
  （游戏内部资产名叫 `zombie`——开发者占位名；同目录 `giant.txt`/`menuarcher.txt` 等是菜单/商店/巨型单位的独立小骨架，核心兵种全部在本文件）。
- **规模**：56 骨 / 93 槽位 / 22 皮肤 / 93 动画 / 内嵌事件 5 类（Hit、Sound、Drawn、Mine、Cast）/ IK 约束 2 条（`rein`/`rein2`，只挂 Leader 缰绳骨；**核心动画 0 使用**）。
- 配套图集：`[universal.atlas].txt` + `textures/universal.png`。
- 再生成工具（若真相源再次丢失）：`tools/swl_extract_spine.py`（UnityPy 扫 APK `bin/Data` 的 TextAsset/Texture2D）。
- 分析工具：`tools/analyze_spine_skeleton.py`（全量清单 JSON）、`tools/render_spine_bones.py`（真值骨骼线渲染）、`tools/dump_spine_pose.py`（真值姿态数值基准）。

## 二、骨架结构与变换语义（原理）

### 2.1 变换链

Spine 逐骨递推（y-up、角度逆时针、rotate 通道为**增量**）：

```
child_world = parent_world · T(x,y) · R(setup_rotation + rotate(t)) · S(scaleX,scaleY)
世界角 = 链上各骨局部角之和；length 沿骨 +x 轴
```

Godot（y-down、顺时针）映射：`position=(x,-y)`、`rotation=-角度`、offset 保持在父骨本地系——整条链形状不变，仅镜像。

### 2.2 核心肢体骨链（真实数值，Spine 单位）

| 链 | 骨（setup 旋转） | 长度 |
|---|---|---|
| 脊柱 | root(地面) → `bone`(髋, y=183) → `minertorso1`(90°) → `bone2` → `bone3`(-3.15°) | 30.53 / 29.68 / 28.04 |
| 颈头 | `minerhead1`(-39.58°)，head 附件 130×130 挂其上 | 32.4 |
| 臂外 | `minerarm1`(162.81°) → `minerarm2` → `Arrow1`(盾/手) | 67.71 / 71.68 |
| 臂内 | `minerarm3`(-169.73°) → `minerarm4` → `pickaxe1`(武器/手) | 71.84 / 69.83 |
| 腿外 | `minerleg2`(-82.83°) → `minerleg1` → `minerfoot1` | 79.52 / 81.41 / 27.15 |
| 腿内 | `minerleg4`(-97.24°) → `minerleg3` → `minerfoot2` | 71 / 84.16 / 26.3 |

装饰/杂件骨：`helm`、`minerbag`、`legdangle`、`bone4`(Backarmor/披风挂点)、Leader 副肢（`Dead-Leader/*` 12 骨）、剑节链（`bone20`~`bone28` 挂 pickaxe1）、鞍座（`Giant-Rider/saddle`）。

### 2.3 附件尺寸（肢体矢量重标的依据）

head 130×130、四肢 30×98（臂）/30×114（腿）、foot 51×30、weapon 86×310（剑）、torso 为 mesh（**无任何 deform 动画使用，实证**，可按线段降级零损失）。

## 三、旧管线失真机制（为什么重建）

旧提取器 `spine_import.gd` + 手搓 `SKELETON_DATA` 六条失真（均已实证）：

1. **旋转基准与几何脱节（总根因）**：动画按「Stand1 t=0 重基准」补偿，而几何表是另一套手搓偏移 → rest 不是任何真实姿态（缺陷 D1~D11 之源）。
2. **通道覆盖 1/3**：只译 rotate；translate（Stand1 里 17 骨全有）与 scale 全丢。
3. **骨骼覆盖 17/56**：头盔/背包/披风挂点/Leader 副肢/剑节链全丢。
4. **曲线全线性化**：93 动画主体是 bezier 非线性（如 Stand1：60 轨道全非线性），旧管线全按直线插。
5. **洗稿污染**：`KEYFRAME_FIXES` 手改 walk/run 起步帧；`wash_anims.gd` 对整库做扰动——现库 .tres 非忠实版。
6. **IK 装置无源之水**：自装 4×TwoBoneIK + Marker，实测从不解算（批次 4h 实锤）；原版核心动画 0 使用 ik 通道，该装置在原数据里就不存在。

## 四、两版模型内容对比

| 维度 | APK 核心骨架（zombie.txt） | 2021 units-pack（`swl_extracted/*.nodes`） | APK 菜单骨架（menuarcher 等 8 个） |
|---|---|---|---|
| 骨骼 | 56 | 不可读（无名二进制） | 7~24 |
| 动画 | 93（全兵种+死亡/受击池） | 0 | 1~5 |
| 皮肤 | 22（含 _Red 变体/Zombie 系） | — | 1 |
| 事件 | 5 类全 | — | — |
| 结论 | **唯一真相源** | 私有格式无对账价值，弃用 | 仅菜单展示，不采用 |

`.nodes` 查证：非 Unity 序列化文件（UnityPy 零对象）、无 ASCII 骨骼名、无动画段；2021 年第三方产物，无法与本管线对账。

## 五、覆盖率方案（怎么设计）——「提案/待定」

**忠实复刻口径**：同一时刻、同一骨骼，世界位姿数值一致（RMS 阈值内）+ 真值骨骼线并排观感一致。

### 5.1 数据覆盖

- **骨骼 56/56**：全量入库。核心肢体 17 队骨渲染矢量肢体；装饰骨建模但按兵种档案显式决定"渲染/不渲染"；任何骨不允许静默丢弃（表中登记理由）。
- **动画 93/93** 全量入库（含 Death/Hit 池、Zombie 系、Giant-Rider 系）；.tres 保持 Spine 原名，游戏内映射表（现 `stickman_anims.ANIM_MAP` 机制）单独维护。
- **通道覆盖**：
  - rotate：全量，bezier/stepped **精确求值**（禁全线性近似）。
  - translate：全量（含非 root 骨）；行走位移 x 分量的处理口径（应用/丢弃）在导入器单独开关，默认丢弃防漂移。
  - scale：全量。
  - shear：仅 Giant-Rider 系 4 动画使用；Godot Bone2D 无 shear——「提案：弃用并登记」，不为 4 个动画引入自定义变换。
  - deform：0 动画使用（实证）→ 无需实现。
  - attachment 切换（461 处，如拉弓搭箭/死亡掉武器）：映射为对应渲染节点显隐。
  - ik：核心动画 0 使用（实证）→ 不实现；约束表留档。
- **事件覆盖**：Hit/Sound/Drawn/Mine/Cast 全量写入 Animation 元数据（消费端 `animation_event` 信号已就绪）。
- **皮肤 22**：矢量渲染按兵种档案映射附件；Zombie 系/Giant-Rider 系登记远期——v1 只做 6 正规兵种+Miner（「提案」）。

### 5.1.1 武器覆盖（添加方法）

武器 = `weapon` 槽的**贴图附件**，挂武器手骨 `pickaxe1`（本项目 23 号 weapon_hand），随该骨 rotate 通道甩动（原版 attack 对它有 -109°~+34° 大摆幅）。每兵种 skin 自带同名 `weapon` 附件、指向各自图集区域，几何(x/y/rot)从 skin 表直读：

| 兵种 | 武器 | 附件区域尺寸 |
|---|---|---|
| Swordwrath | 剑 | 86×310 |
| Spearton | 矛 | 46×782 |
| Magikill | 杖 | 42×520 |
| Miner | 镐 | 176×297 |
| Giant | 剑（复用剑区域） | 86×310 |

- **弓是唯一例外**：Archidon skin 无 weapon 附件、全库无 bow 图集区域——原版弓是运行时另加的 Unity 贴图，不在骨架数据里。弓沿用现有 `extract_weapons` 裁图 + WeaponMount 管线（weapon_bow.tscn 已在用）。
- 添加方法（批次 B）：按兵种档案从 `universal.png` 裁 weapon 区域 → WeaponMount 挂 weapon_hand 骨 → 动画直接驱动；现役武器贴图管线不重写，只补"区域几何从 skin 表直读"。
- 盾有专属槽：`Arrow1` 槽（挂盾手骨，本项目 24 号 shield_hand）带 `sparshield0001/0002` 盾 271×483（Spearton 持盾形态组）。

### 5.1.2 附加装备覆盖（添加方法）

装备 = 槽位**贴图附件直接渲染（不矢量化**——装备是原版贴图而非火柴人肢体；武器已是贴图先例）。几何(x/y/rot/区域)从 skin 表直读，批次 B 按「槽位→挂骨→贴图件」逐条入库：

| 装备 | 槽位 | 挂骨 | 正版区域 | 升级变体（登记远期） |
|---|---|---|---|---|
| 矛士头盔 | helm | helm 骨 | spartanHelmet0002 233×235 | gold/leaf 盔等 |
| 法师帽 | helm | helm 骨 | （Magikill skin 覆写） | magikillhat1~3+leafhat |
| 矿工袋 | bag | minerbag 骨 | minerbag (2) 134×103 | 金袋/叶袋等 ×5 |
| 箭袋 | Quiver1 | bone3（背部） | Quiver 148×154 | 升级箭袋 ×7 |
| 矛士盾 | Arrow1 | Arrow1（盾手骨） | sparshield0001/0002 271×483 | gold/leaf/mad/native 盾+zombieshield |
| 背甲/披风 | Backarmor | bone4 | （Zombie-Leader 系） | — |
| 搭弦箭 | Arrow1/Arrow2 | Arrow1/Arrow2 骨 | Arrowskn/Arrow 214×25 | — |

- `_Red` 变体：附件名与正版完全相同、tint 全空——差异在**同名附件指向红版图集区域**（贴图另画）。贴图裁切跟随附件 path 字段即可，无需矢量染色机制。
- Leader 形态：`Dead-Leader/*` 12 根副肢骨 + `bone20`~`bone28` 旗/剑节链（挂 pickaxe1），由 `Swordwrath-Leader` 等动画驱动；v1 登记远期（「提案」）。

### 5.1.3 任务/动作映射覆盖（添加方法）

93 动画全量入库之外，游戏侧「动画→任务语义」映射表（现 `stickman_anims.ANIM_MAP` 机制）按此对账扩容：

| 游戏动作 | 原版动画 | 原生事件（结算帧） |
|---|---|---|
| 待机（各兵种） | 各兵种 Stand1/Stand | — |
| 行军/奔跑 | 各兵种 Walk / Run | — |
| 攻击 | 各兵种 Attack、Spearton-Block-Attack1~3、Archidon-Draw | Hit@（逐动画入元数据） |
| **挖矿** | Miner-Mine | **Mine@1.2**（敲击结算帧，原生） |
| **建造** | Miner-Attack1（循环） | 无原生事件，「提案：取挥击最低点自定结算帧」 |
| **搬运行走** | Miner-Walk（walk_carry） | — |
| **到达庆祝** | Cheering（arrive） | — |
| 伐木/耕作等缺口 | **原版无对应动画**——「提案」：伐木暂复用 Swordwrath-Attack1（挥砍）/Miner-Mine（敲击），登记远期自制 | — |
| 彩蛋/备用 | Pushup（剑/矛士）、Jump/Jump2、CastleArcher-Sit、Swordwrath-Leader | 全量入库备用 |

原版没有、游戏侧新增的任务态，一律以映射表加行扩容，不改编动画数据。

attachment 切换通道的落地口径（细划 §5.1 的 461 处）：**仅 NULL（隐藏）切换有语义**，共 6 处（Archidon-Draw 搭弦箭显隐、Death-Headshot 系爆头箭矢、Zombie 系碎肢隐去）→ 映射为对应渲染节点/武器件显隐；其余 ~455 处为"同槽同名附件重设"（无视觉效果），导入器可安全忽略——此口径登记进覆盖矩阵对账。

### 5.2 渲染映射（attachment → 矢量件）

- 比例全部从真实数据重标：肢厚 30、肢长=骨长、脚=51×30 矢量长条+端圆、头径从 head 附件 130×130 区域实测圆径。
- 武器/装备走贴图附件件（§5.1.1/§5.1.2），肢体仍纯矢量。
- 现有描边机制（开口/链式 z 表/头圆动态裁剪）语义保留，常量按新几何重标。
- 尺度归一：新旧骨架整体高度差较大（真值 setup 高 203.6、Stand1 高 456 世界单位 vs 现库 264），RIG/BASE 缩放常量在批次 B 以「现役屏幕观感尺寸」为锚定落定。

### 5.3 验证覆盖（验收链）

1. **数值链**：`dump_spine_pose.py`（真值，全动画 15fps 采样）× 新 Godot 侧 dump（改造 `dump_rig_pose.gd` 适配新骨架）逐骨世界位姿对比。「提案阈值：位置 ≤0.5px、角度 ≤0.5°」。
2. **视觉链**：`render_spine_bones.py` 真值骨骼线 vs 游戏内截图并排（标准站姿场景 `tests/dev/stickman_relaxed_pose.tscn` + 画廊）。
3. **覆盖矩阵**：`analyze_spine_skeleton.py` 产物入库本目录，逐动画核对通道数/事件数。
4. **缺陷复验**：批次 4h 缺陷清单 D1~D11 在新几何上逐条复验归零。
