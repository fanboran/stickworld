## 〇、问题定义

待办登记的原始表述：「火柴人直线移动遇障碍硬弹回导致卡死，需实现局部避障或 A* 网格寻路」。拆开是三个子问题：

1. **直线移动无绕行**：AI 行为层向目标点发方向向量，遇墙后仍持续朝目标推，没有"沿墙走"的次级策略；
2. **卡死的机制**：目标点在障碍另一侧时，移动行为永远达不到到达阈值、永不 finish，决策层又把命令原样保持——形成死循环；
3. **"硬弹回"的词源**：设计稿（`docs/技术/架构/场景与战斗/战斗与AI.md:81`）原方案是"进入 PassageBarrier 区域 → 回退到上一帧位置"；现行实现已改为 StaticBody2D 物理碰撞，无显式弹回代码，观感上的"弹回"来自持续推墙 + 分离推挤的叠加。

| 移速 | entity:24-26, 590-621 | WALK 160 / RUN 208 px/s × 地形倍率（土路 1.0/非土路 0.8，`village_map.gd:329-332`）× 兵种倍率 |

AI 侧决策频率：

- `AIController.DECISION_INTERVAL = 0.3`（`modules/units/scripts/ai/ai_controller.gd:30`），决策层每 0.3s 检查一次；行为 `update` 每物理帧执行（ai_controller.gd:200）。
- `BehaviorMove.update` **每物理帧**重算 `dir = (target - pos).normalized()` 直线指向目标（`behavior_move.gd:150-153`），到达阈值 `ARRIVAL_THRESHOLD = 20px`（behavior_move.gd:21）。

### 1.2 通行障碍系统：两级 StaticBody2D

- **地图级 WalkBarrier**：`VillageMap.WalkBarrier` 容器下的 StaticBody2D 子节点，由 `MapBase.get_walk_barriers()` 收集（`modules/world/scripts/map/map_base.gd:118-126`）。当前 `village_a.tscn:42`、`road_a_b.tscn:38` 的 WalkBarrier 均为**空容器**——地图级障碍尚未实际布置。
- **建筑级 PassageBarrier**：每个建筑场景内的 StaticBody2D（默认 layer 1），如仓库 512×390（`modules/building_gen/buildings/placeholder.tscn:6,20-22`）、城墙 32×64（wall_tier1.tscn:5,22-24）。工地临时障碍按建筑模板同参创建（`modules/construction/scripts/construction_project.gd:258-259`），完工时由建筑自身 PassageBarrier 接管（construction_project.gd:336）。
- 设计稿中的 Area2D + 回退上一帧方案（战斗与AI.md:81-83 伪代码）**未在现行代码中实现**；现行全靠物理碰撞自然阻挡。
- 调试可视化已就位：WalkBarrier 蓝 / PassageBarrier 紫（`modules/debug_gui/scripts/debug_drawers.gd:86-95`）。

**障碍几何的关键事实（决定方案难度）**：建筑基准线 = `ground_y + 96`（`village_map.gd:45`，村落 ground_y=810 → 基准线 906）；仓库 PassageBarrier 覆盖 Y≈[521, 911]，而可行走地面带是 [810, 1080]（`map_base.gd:17,25`）。即**建筑只挡住行走带的上半段约 100px，脚下留有约 169px 高的通行走廊**（放置校验同样按此几何，`construction_manager.gd:501-506`）。绝大多数障碍在几何上"绕半步就能过"，这是评估三方案的重要前提。

| 9k 群体避让 | 无 RTS 让路、友军遮挡、避战扎堆 | 单位间避让缺失，规划「移动绕行分量」（`AI复刻执行计划.md:71`）——与方案 A 是同一块拼图 |

结论：**已证实的"全员卡死"案例是决策逻辑级而非障碍寻路级**；障碍卡死目前主要表现为单单位推墙（行为永不完成）与密集建筑区的搬运绕路失败。这也解释了为什么方案 A 的"卡住升级检测"价值不低于绕行本身——它把不可达从"无限推墙"变成"有限尝试后上报失败"。

### 1.5 引擎能力盘点

- Godot 原生可用：`NavigationServer2D`/`NavigationRegion2D`/`NavigationAgent2D`、`AStar2D`/`AStarGrid2D`。工程内 grep 零命中——**纯绿地，无历史包袱**。
- `move_and_slide()` 自带沿墙切向滑动：斜向碰墙时单位已经会滑，真正卡死的是**正对面墙 + 每帧重归一化指向目标**造成的角点振荡/顶死。

## 二、方案对比

### 方案 A：局部避障（steering 切向滑动 + 短时绕行意向）

**原理**：不改全局寻路。移动方向在遇障时做两件事：
1. **切向滑动**：读取 `move_and_slide()` 的碰撞结果（`get_slide_collision`/`get_last_slide_collision`），把期望方向投影到墙面切线上，得"沿墙分量"——监狱建筑师 / RimWorld pawn 的 wall-slide 模型；
2. **短时绕行意向**：滑动分量不足以推进时（角点/正对面墙），注入一段 0.3~1s 的沿墙回避力（随机选侧 + 冷却防左右抽搐），期间压制"指向目标"的原始方向；
3. **卡住升级检测**：复用 wander 的 0.2s/<3px 检测，超时后大角度掉头或直接判定"目标不可达"、finish 行为上报。

**实现落点**：entity `_handle_ai_input` 之后或 BehaviorMove 内插入方向修正层；wander 的卡住检测/掉头抽成公共 steering 模块两边共用。

| 维度 | 评估 |
|---|---|
| 工作量 | 约 200~400 行 + 单测，1 个开发轮次内 |
| 性能 | 碰撞结果读取零成本（move_and_slide 已算）；偶发 1~2 条 raycast。当前量级（同屏 2~50 单位）无感；向 10000 量级扩展需隔帧节流（工程已有"分离扫描隔帧"先例，entity:487-489） |
| 契合度 | 高。① `move_and_slide` 已提供切向滑动物理，只需补"绕行意向 + 升级检测"；② wander 已实现卡住检测/掉头/冷却三件套；③ 9k 的「移动绕行分量」即本方案子集，做了 A 等于顺手消掉 9k 的一半 |
| 风险 | 凹形陷阱（U 形建筑群、城墙门洞内）绕不出去，只能靠升级检测兜底（掉头重试/报失败）；角点振荡需阻尼参数调校（wander 的冷却机制已验证可防） |

### 方案 B：A* 网格寻路

> 前提修正：现有 PlacementGrid 是 **1D 竖条网格**（placement_grid.gd:1-20），不能直接当 2D 导航网格用；但 32px 水平粒度 + resource_gen 的 32px 垂直泳道（270px 带 ≈ 9 行）给出了天然的 2D 格子模型：起步约 256 列 × 9 行 ≈ 2300 格，随 expand_map 增长。

#### B1. 自研轻量 A*（推荐用 Godot 内置 `AStarGrid2D` 承载）

**原理**：新建 2D 占据层（建筑/工地/BuildMask → 实心格；按单位半宽 41.5px 膨胀 1~2 格），移动行为起点→终点一次求解，得到路径点队列逐段走向；局部推进仍交给 move_and_slide。

| 维度 | 评估 |
|---|---|
| 工作量 | 约 500~800 行（占据层 + 建拆/工地/存档恢复 4 处同步点 + 路径跟随 + 膨胀策略），约 2 个轮次 |
| 性能 | 2300 格 A* 单次求解微秒级；10000 单位分帧求解（每帧预算 N 条）也远够。内存可忽略 |
| 契合度 | 中。粒度与 PlacementGrid/泳道一致、概念容易对齐；但**占据层是第二份真相**——PlacementGrid 只登记 X 条带，2D 层要自己跟随建筑落位/拆除/工地创建移除/存档恢复（construction_project.gd:336 已有 clear 钩子可挂） |
| 风险 | 占据同步漏标（4 处写入点 + 未来城墙缩放/破坏）；32px 格 vs 41.5px 单位：膨胀策略决定 169px 脚下走廊是否判可走（≈5 格，余量充足）；对角穿墙需关 slice 模式 |

#### B2. NavigationServer2D

**原理**：每张地图挂 NavigationRegion2D 烘焙可行走多边形，单位挂 NavigationAgent2D 取路径，可选启用引擎自带 RVO 避让。

| 维度 | 评估 |
|---|---|
| 工作量 | 约 600~900 行 + 场景改造（每地图挂 Region/每实体挂 Agent） |
| 性能 | 烘焙异步；动态障碍（工地频繁建拆）需 obstacle 节点或反复 rebake，是主要开销点 |
| 契合度 | 低-中。① 地图本质 1.5D（9 条泳道），导航多边形烘焙大材小用；② NavigationAgent 的速度合成与现有 `_apply_movement`/分离系统功能重叠，双推力系统打架风险高；③ 建筑频繁建拆导致 rebake 抖动 |
| 风险 | 引擎黑盒调试成本最高；避让参数与既有分离系统互相干扰难定位 |

### 方案 C：混合（局部避障为默认 + 全局路径兜底）

**原理**：移动请求先做**直连可达性乐观检测**（1~2 条 raycast，或"起点终点连线上无实心格"）；可直连 → 纯方案 A；直连被挡、或 A 的升级检测判定卡死 → 向寻路服务请求**一次**全局路径（缓存，终点/占据变化才重算），拿到路径后逐段 A 推进。

| 维度 | 评估 |
|---|---|
| 工作量 | ≈ A + B1 之和 + 约 100~200 行调度（请求门控/路径缓存/失效） |
| 性能 | 全局求解被"仅卡死/仅被挡"门控，实际求解频次远低于纯 B；最省的形态 |
| 契合度 | 高。分层恰好映射行为树：局部避障住在 move 行为内，卡死升级在 AIController/behavior 层触发路径请求；与设计文档已登记的方向性结论一致（战斗与AI.md:99-103「局部避障 + 简单 A* 兜底」） |
| 风险 | 两套系统边界 bug（乐观检测假阳性 → 该走路径却走 A）；代码面比纯 A 约多一倍，需一次性把 B1 的占据层立起来 |

### 对比总表

| | A 局部避障 | B1 AStarGrid2D | B2 NavigationServer2D | C 混合 |
|---|---|---|---|---|
| 工作量 | 1 轮 | 2 轮 | 2~3 轮 | 2.5~3 轮 |
| 性能上限 | 单位数百级（隔帧可上千） | 万级（分帧） | 万级（引擎承载） | 万级（分帧） |
| 凹形陷阱 | 处理不了（只报失败） | 解决 | 解决 | 解决 |
| 与现有代码摩擦 | 最低 | 占据层同步义务 | 与移动/分离系统重叠打架 | 同 B1 |
| 主要风险 | 复杂地形绕不出 | 4 处占据同步点 | 动态 rebake + 双避让系统 | 边界判定 bug |

## 三、推荐与分期

### 推荐：分期落 C——P0 只做 A，P1 补 B1 兜底

**一句话理由**：村落级地图的障碍几何（建筑只挡上半带、脚下留 169px 走廊）决定了"切向滑动 + 绕行意向 + 卡住上报"就能通过当前绝大多数场景；而地图的 1.5D 泳道结构（9 行 × 数百列）让 AStarGrid2D 兜底在需要时几乎免费——不必为还不存在的凹形地形提前付 B 的占据同步成本。

**为什么不是 B2**：1.5D 地图用导航多边形大材小用；工地频繁建拆与 rebake 模型冲突；NavigationAgent 速度合成与现有 `_apply_movement`/分离系统重叠，双避让打架的调试成本超过收益。如未来出现真正开放 2D 的地图类型（大世界俯视），再重议。

**分期**：

- **P0（村落阶段，当前）**：方案 A。
  1. 抽 `behavior_wander` 的卡住检测/掉头/冷却为公共 steering 组件（两边复用）；
  2. BehaviorMove（及 haul/follow 共用路径）接入切向滑动 + 短时绕行意向；
  3. 卡住升级检测：有限次绕行失败 → 行为 finish 并上报不可达（号令层给反馈，AI 层换目标/回 idle）——直接回应 9h 的复验诉求；
  4. 绕行分量与 9k「移动绕行分量」共用同一实现，P0 顺手消掉 9k 一半。
- **P1（扩张/多村落/城墙防线）**：B1 AStarGrid2D 占据层 + C 的调度门控。
  触发条件（满足其一）：出现凹形障碍布局（城墙 + 门洞防线）；常驻单位稳定 >100；搬运路线穿越建筑群成为常态（WorkCrew 任务板上线后大概率触发）。
  实施要点：占据层与 PlacementGrid 同点同步（落位/拆除/工地建拆/存档恢复 4 处）；膨胀按单位半宽 1 格；直连检测用占据层查询而非 raycast，避免边界假阳性。
- **持续**：`escape_stuck` 保留为最终兜底；AI 侧在升级检测连续失败 N 次后也可调用同一机制（当前仅玩家，entity:987-1018）。

**验收口径建议**：P0 完成后，单位从仓库一侧被派到另一侧工地、以及穿越两栋相邻建筑的搬运路线，均应在有限时间（<3s 额外开销）内到达或显式报不可达，不允许出现 >5s 的持续推墙。

## 四、遗留问题（留待实现期拍板）

1. 卡住检测阈值（0.2s/3px 直接沿用 wander 还是放宽到 0.5s）需在观察场校准——9h 复验时一并定。
2. 绕行方向选择（固定左手 vs 随机侧 + 记忆）影响角点通过率，实现时做 A/B 观察场对比。
3. P1 占据层是否反哺 PlacementGrid（合并为 2D 真相源、1D 条带视图化）——涉及建筑选址 API 契约，届时单独评审。
