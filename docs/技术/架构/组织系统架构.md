## 一、现状底座

### 1.1 模块结构（现状 + 本任务新增预览）

```
modules/organization/
├── api.gd                        # 唯一公共入口（信号 + Result 方法）
├── scripts/
│   ├── organization_manager.gd   # 纯逻辑 CRUD/层级/人事/预设/补位（RefCounted）
│   └── command/
│       ├── org_command_dispatcher.gd  # [批次3新] 逐层命令分解器（纯数据，§4.1）
│       └── transport_layer.gd          # [批次3新] v1 抽象传播（三 provider 注入，§4.2）
└── ui/
    └── org_panel.gd              # [批次2新] 组织管理面板（StickWindow FLOATING）
```

依赖方向：organization **零出向依赖**（L2 玩法层）；combat、ui（OrgPanel 经装配注入 api 引用）、
world（装配）为消费方。批次 3 的分解器只查组织树数据、传输层只做除法，不碰单位——
combat 调它拿投递计划与每跳秒数后自己执行。

### 1.2 数据层现状

- 状态对象 `core/entities/organization_state.gd`（字段语义见 §二）；
- 集中制：manager `set_world(WorldState)` 注入 → 创建/删除同步容器 → 存档走 WorldState 统一序列化；
- api 三信号 `org_created / org_restructured / org_disbanded`——至今零消费方，批次 2 的 OrgPanel 是首个消费方。

### 1.3 战斗侧既有等式（不可破坏）

**L1 小队 = organization 的 L1 组织节点**：FormationSystem.create_squad 内部调
`_org_api.create_organization(name, tag, SQUAD_TIER=1, "")`，squad_id 即 org_id；指挥官任命经
EventBus `commander_assigned` 已被战斗侧消费。批次 3 在此之上叠加 L2+ 层级，不改写该等式。

### 1.4 批次 1 修正案（回看结论，零消费方窗口内破坏性升级）

批次 1 已落地的部分（回滚机制、挂接校验「预设顶层 level = parent.tier−1、不平移」、按 level 降序
稳定创建、单根校验）**判定正确，保留**。以下三项推翻修正：

| # | 问题 | 修正 |
|---|------|------|
| F1 | 导出预设条目 id 用运行时 org_id，蓝图数据携带运行时标识，不可 diff/合并 | export 时条目改用**语义键**（"n1","n2"...，先根序重编号），parent 同步映射；回灌用 key 关联，与运行时 org_id 彻底解耦 |
| F2 | 导出只含骨架（name/level/tag/parent），丢模板配置 | 条目补**模板字段**：personnel_template / equipment_template / autonomy / default_behavior（透传回灌）；实例字段（personnel、commander_id、location、current_project、state）不导——模板 vs 实例二分 |
| F3 | `load_preset(Variant)` 双形态牺牲类型安全，与 api.gd 全强类型风格冲突 | 拆双方法：`load_preset(preset_name: String)`（查官方母本）+ `apply_preset(data: Dictionary)`（蓝图直灌）；export 产物直接喂 apply_preset |

零消费方（信号、预设格式均无外部消费）是破坏性格式升级的唯一窗口，**不留旧格式兼容层**。

另修一个批次 1 之前就存在的信号缺口（批次 2 上消费方后会咬人）：
`api.insert_tier` 成功后补发 `org_created` + `org_restructured`（新节点 + 父结构变化）；
`api.remove_tier` 成功后补发 `org_restructured`（子组织上挂）。

## 二、数据契约

### 2.1 OrganizationState 字段语义（现状冻结，新增字段须过本文档）

| 字段 | 语义 | 批次消费 |
|------|------|---------|
| id / name / tag / tier | 唯一标识 / 名称 / 七类标签 / 层级 1-5 | 全部 |
| parent_org / child_orgs | 树结构（child.tier = parent.tier − 1 恒成立） | 全部 |
| commander_id | 指挥官 stickman 实例 id。**中间层（L2~L4）不变量：节点即某人的统辖事实，ACTIVE 必有指挥官**；空仅见于 L1 招兵期（FORMING）与中间层伤亡空缺过渡态 | 批2/批3 |
| succession_rule | **补位原则**（创始人设定）：指挥官伤亡时的自动补位规则——军衔最高者顶上（P0 以指挥属性代理）/ 玩家指定 / 不补位。默认军衔最高 | 批3 |
| personnel / *_template | 实例成员列表 / 编制模板（角色→数量、装备） | 批2 |
| autonomy_level | HIGH/MEDIUM/LOW——批次 3 决定上报粒度 | 批3 |
| default_behavior | 无指令时自动行为（Dictionary，P0 透传） | 批3 |
| supply_priority / morale_threshold / current_project / location / state | 预留/低频字段 | 后续任务 |

### 2.2 预设数据格式 v2（export_as_preset 产物 = apply_preset 输入）

```jsonc
{
  "name": "第一师",            // 蓝图名（默认 = 根组织名，UI 可改）
  "tag": "MILITARY",
  "entries": [
    { "key": "n1", "name": "师",   "level": 5, "tag": "MILITARY", "parent_key": "",
      "personnel_template": {"rifleman": 4}, "equipment_template": {},
      "autonomy": "MEDIUM", "default_behavior": {} },
    { "key": "n2", "name": "团",   "level": 4, "tag": "MILITARY", "parent_key": "n1" }
    // 模板字段可省略 = 空配置；实例字段永不出现
  ]
}
```

- `presets.tres` 官方母本沿用 BalanceResource 行格式（id/preset/name/level/parent_id/tag），
  manager 装载时映射为 v2 条目（母本的 id 即 key）——官方数据不迁移，运行时归一。
- 往返不变量：`apply_preset(export_as_preset(x).data)` 产出的树与 x **结构同构 + 模板字段逐项相等**（测试锁死）。

## 三、批次 2：组织管理面板（OrgPanel）

### 3.1 装配与形态

- 照 FormationPanel 先例：`modules/organization/ui/org_panel.gd` extends StickWindow，
  `Behavior.FLOATING`（无遮罩可拖动，与游戏交互不冲突）；SystemSetup 装配挂 UIRoot ModalOverlay 槽；
  `game_root.get_org_panel()` / `toggle_org_panel()` 访问器；入口 = GlobalHUD「组织」按钮
  （顶栏与「编制」并列，P0 无快捷键——避免与既有 O/J/K/L 冲突）。
- 窗口 ~820×520：顶部标签栏 + 快捷条 + 左树右详情双栏（详情区 ScrollContainer）。

### 3.2 标签栏 = 树过滤器 + 工作区雏形【提案/待定】

复用 workspace_template 已验证的 TabBar 交互。P0 语义收敛为**过滤**而非完整工作区切换：
军事/科研/工程/行政/运输/劳工/商业 七标签 + 「全部」；选中标签 → 树只显示该 tag 的组织
（根为匹配节点）。右侧快速操作区按标签摆位，P0 仅军事组接真实操作，其余标签按钮禁用态（"未实装"）——
避免造一堆 toast 假交互。完整工作区（快捷操作随标签换装）留 GDD §5.2 演进。

### 3.3 树构建与刷新

- 数据流：`list_root_orgs()` → 递归 `get_child_orgs()` → Tree 控件（item metadata = org_id）；
  节点文案 `[L{n}] {name} · {tag中文} {人数} {▲指挥官}`。
- 刷新策略：消费 `org_created / org_restructured / org_disbanded` 三信号 → **全量重建**。
  P0 组织规模 <100，全量重建可接受；性能红线：>500 节点时改增量更新（登记调优杆，不预做）。

### 3.4 详情区与操作映射

选中节点 → 右侧详情（字段只读展示）+ 操作按钮组：

| 操作 | API | 交互 |
|------|-----|------|
| 新建子组织（L1） | create_organization（tier=1）——叶层编制，可 FORMING 招兵 | 名称输入弹窗 |
| 插入上层/下层 | insert_tier(position) | 直接执行 |
| 删除层级 | remove_tier | 危险确认框（StickKit 确认族） |
| 解散组织 | disband_organization | 危险确认框 |
| 更换指挥官 | assign_commander（从 personnel 列表选；空组织禁用）——任命=换人，节点因人而生不空转（§4.3） | 列表选择弹窗 |
| 移除成员 | remove_stickman | 成员行内按钮 |
| 自主权限 | set_autonomy（三档 OptionButton） | 即点即改 |
| 改名 | set_org_name | 行内编辑 |
| 从预设创建 | load_preset（挂到选中节点；顶层衔接校验由 manager 把关） | 预设名下拉（list_preset_names） |
| 导出为蓝图 | export_as_preset → 内存持有（后续接构筑谱系/UGC） | 结果 toast |

FormationPanel 分工保持：战斗侧快捷位（L1 小队/派工），OrgPanel 是通用组织树管理；FormationPanel
不加"跳转 OrgPanel"入口（避免跨面板状态同步，玩家各自打开）。

实施落定（批次 2，细节补充）：
- 「插入上层/下层」进**插入流程态**（详情区切换视图）：命名 + 统辖人选下拉一次完成；
  新层级 >1 时人选必选（候选 = 本组织 personnel ∪ 直接下级指挥官，同 §4.3.1 补位池口径），
  无候选时禁用确定并提示；确认 = insert_tier + assign_commander（任命在先节点随之）。
- 「新建子编制(L1)」仅 L2 组织可用（child.tier = parent.tier − 1 恒成立，L3+ 挂 L1 非法）；
  L1 叶层创建后 FORMING 招兵，无需指挥官。
- 标签过滤 = 层级压缩：非匹配节点不生成 TreeItem，子代挂靠最近匹配祖先（保持树连通）。
- 导出蓝图内存持有（面板生命周期内 name -> v2 data），文件化挂 UGC 任务。

## 四、批次 3：逐层指挥 AI（抽象命令链）

### 4.1 命令分解模型：OrgCommandDispatcher（3-P 定稿，Flash 可照做）

核心规则（GDD §4.1）：**每层 AI 只直接指挥向下一层**——对 L(n) 组织下令，命令沿树逐层下降到 L1，
由 L1 小队执行。P0 分解语义 = **同令透传**（每跳转发的 order 字典不变，延迟由各跳传输层
物理传播累积，见 §4.2）；
"拿下这个区域"→"攻这个方向"的语义改写是玩法级 AI，登记开放问题（§七）不在本批。

**职责三分**（实施红线，勿混）：

| 组件 | 职责 | 不做 |
|------|------|------|
| dispatcher（organization） | 查组织树出**结构**（hop 序列） | 不算时间、不碰单位 |
| transport_layer（organization） | 算**每跳传播秒数**（距离÷速度） | 不执行、不解单位 |
| CommandChain（combat） | **执行**：逐跳计时接力 + L1 送达时 set_order | 不出计划、不算距离 |

#### 4.1.1 接口与输入 schema

```gdscript
# modules/organization/scripts/command/org_command_dispatcher.gd（RefCounted，纯逻辑）
# api 增量（§2.3）：build_dispatch_plan(org_id: String, order: Dictionary) -> Dictionary

# order 入参 schema（TacticalOrders.issue_to_org 构造后传入；organization 不解释字段，只透传）：
# {
#   "order_type": int,        # TacticalOrders.OrderType 枚举值
#   "target_pos": Vector2     # 世界坐标（ADVANCE/RALLY 用；HOLD/RETREAT 等忽略）
# }
```

#### 4.1.2 输出 schema（hop 序列）

```jsonc
{
  "ok": true,
  "data": {
    "root_org": "org_x",            // 目标组织（= 入参 org_id）
    "leaf_orgs": ["org_a", "org_b"],// 全部 L1 叶（执行层清单，供测试断言/UI 展示）
    "hops": [
      // hop 0 恒为「玩家跳」：from_org="" 表示玩家源（from_tier=0），送达根组织指挥官
      { "from_org": "",     "to_org": "org_x", "from_tier": 0, "to_tier": 3,
        "order": { "order_type": 0, "target_pos": Vector2(500, 300) } },
      // 之后 BFS 层序展开：先根后叶、同层按 child_orgs 注册序（稳定，测试可断言）
      { "from_org": "org_x", "to_org": "org_y", "from_tier": 3, "to_tier": 2, "order": { ...同令透传... } },
      { "from_org": "org_y", "to_org": "org_a", "from_tier": 2, "to_tier": 1, "order": { ... } },
      { "from_org": "org_y", "to_org": "org_b", "from_tier": 2, "to_tier": 1, "order": { ... } }
    ]
  }
}
```

- **展开规则**：从 root_org 起 BFS 沿 child_orgs 递降到 L1 截止；目标组织本身是 L1 时 hops =
  玩家跳单条（送达即执行——issue_to_org 统一覆盖对 L1 直令，行为等价旧 issue 玩家路径）。
- **玩家跳语义**【提案/待定】：命令需物理到达根组织指挥官手里（玩家≠附身该指挥官时吃传播距离）；
  玩家位置 = 附身实体坐标，未附身时 = 相机视野中心。附身目标指挥官时距离≈0 自然无延迟（§4.5 联动
  P0 就有此退化，无需特判代码）。裁决点：玩家对 L1 的**框选微操**（旧 issue 路径）是否也吃传播
  ——P0 定为不吃（「命令面板=现场电台」游戏性抽象），见 §4.2 末。
- **DISBANDED 防御**：BFS 跳过 state == DISBANDED 的子树（不报错、不投递）。
- **错误**（Result 风格）：`{"ok": false, "error": "org_not_found"}`（org_id 不存在）/
  `{"error": "no_subordinate"}`（目标 tier > 1 但无有效子组织——脏树防御，正常运行不可达）。
- 纯数据操作：不持有单位引用、不进场景树、可单测。
- 放 organization 模块（不放 combat）：'每层只指挥下一层'是组织学通用规则，科研/工程组织同样适用；
  combat 只是 L1 执行域之一。依赖图保持 organization 零出向。

### 4.2 延迟 = 传输层物理传播（撤换旧抽象公式）

**延迟的唯一来源是消息在两个指挥官之间物理传播的时间**（GDD §4.4）：`延迟 = 传播距离 ÷ 媒介速度`。
层级数本身不产生延迟——同层远距离的两节点延迟可以大于跨层的相邻两节点，这才是真实。
战斗与AI.md §8.5 的 `base_delay × tier_diff × modifier` 是 P0 遗产简化，批次 3 起退役，由传输层取代。

传输层设计为**可替换实现**（同一接口两代实现）：

| 代际 | 实现 | 语义 |
|------|------|------|
| v1（批次 3） | 抽象传播 | 距离按两跳指挥官的**实际位置**取：同图 = 实体坐标直线距离；跨图 = 驻地区域间距离（注入式 provider，见下）。速度 = 媒介速度表（BalanceConfig：v1 传令兵跑步速度） |
| v2（信使任务，边界外） | 信使实体 | 命令由信使单位真实跑动传递——沿道路、占行军时间、可被截杀、信使阵亡则命令丢失（部门因此瘫痪，GDD §4.4） |

#### 4.2.1 传输层接口（3-P 定稿，Flash 可照做）

```gdscript
# modules/organization/scripts/command/transport_layer.gd（RefCounted，纯逻辑可单测）
# 装配层（system_setup）注入三 provider——organization 保持零出向依赖

var _position_provider: Callable        # (org_id: String) -> Variant
                                        #   返回 Vector2 = 该组织指挥官实体坐标（同图）
                                        #   返回 Vector2.INF = 不在当前图 / 无指挥官实体
var _player_position_provider: Callable # () -> Vector2（玩家附身实体坐标；未附身 = 相机视野中心）
var _region_distance_provider: Callable # (from_loc: String, to_loc: String) -> float
                                        #   跨图驻地距离（米/px）；返回 -1 = 未知对

func setup(position_provider: Callable, player_position_provider: Callable,
           region_distance_provider: Callable) -> void
func delivery_time(from_org_id: String, to_org_id: String) -> float   # 秒
func set_courier_speed(speed: float) -> void   # 测试快进注入口（常规走 BalanceConfig）
```

`delivery_time` 取距决策（首中即返，全确定性）：

```
from 位置 ← from_org == "" ? player_provider() : position_provider(from_org)
to   位置 ← position_provider(to_org)
① 双方均有实体坐标（同图）      → 直线距离 ÷ courier_speed
② 任一方 INF（跨图/无实体）      → 两组织 location 比较：
    location 相同（含同为 ""）   → 距离 0（同驻地内传令忽略不计）
    location 不同                → region_distance_provider 查：
                                      ≥0 → 该距离 ÷ courier_speed
                                      -1  → default_cross_map_distance ÷ courier_speed（fallback）
③ courier_speed ≤ 0（测试快进）  → 恒 0（短路，距离都不算）
```

- 指挥官空缺过渡态（§4.3）期间位置照取该组织**其余成员/子指挥官**位置？——不：位置 provider
  是装配层职责，P0 取不到就 INF 走跨图分支；空缺对延迟的惩罚体现为**命令停驻**（§4.3 续传裁决），
  不在传输层掺假距离。
- v2 信使任务替换本实现，接口不变（`set_courier_speed` 换成信使单位速度）。

#### 4.2.2 跨图驻地距离表（开放问题 #8 收口）

**v1 定稿 = 注入式 provider + fallback 常数**，静态距离表不立项：

- 区域是程序化生成的（世界地图种子随机），静态「区域 A↔B = X」表天生对不上运行时世界；
- 装配层注入的 `region_distance_provider` 在 3-F2 实现为：**world_map/scene_map 侧现成坐标的
  两区域（定居点/地图根）世界坐标直线距离**；3-F2 装配时若取数接口不顺手，先挂
  fallback 常数 + 登记待办（world_map 距离接口），不阻塞批次验收；
- `org.location` 当前除默认 "" 无赋值方——3-F2 装配时由 FormationSystem 建队/L1 位置回填起步，
  完整「组织驻地随实体移动更新」语义登记开放问题（§七）。

#### 4.2.4 CommandChain 职责重划（3-F2 改造规格）

- **撤** `BASE_DELAY` 常量与 `_calculate_delay()`（连同头注释旧公式）——抽象公式退役；
  `deliver()` 变**恒即时执行**（它退化为「送达执行器」：units 解析 + spread 散点 + set_order）。
- 既有调用方零破坏：玩家框选微操（`issue` source_tier=0）本就零延迟；team_ai 的
  `issue(SOURCE_TIER_AI=1)` 现算出 tier_diff=0 也是零延迟——撤公式后行为不变
  （战场本地 AI 对眼前小队下令 = 现场指挥，无传播）。`source_tier`/`squad_tier` 参数
  保留签名兼容（不再参与计算），对外语义注释改写。
- **新增** `issue_to_org` 接力执行（TacticalOrders 入口，详见下）——延迟只发生在跨组织层级
  传输时。玩家微操（对 L1 框选直令）不吃传播【提案/待定：现场电台抽象，是否改吃传播待裁决】。

**投递执行**：TacticalOrders 新增入口
`issue_to_org(org_id: String, order_type: int, target_pos: Vector2 = Vector2.ZERO) -> bool`：

```
1. plan ← OrgApi.build_dispatch_plan(org_id, {"order_type":…, "target_pos":…})
   plan.ok == false → push_warning + return false
2. 接力执行 hops（CommandChain 内新协程，按 hop 结构驱动）：
   - 时刻 0 发出玩家跳：t = transport.delivery_time(hop0.from, hop0.to)，await 计时
   - 某 to_org 送达时刻 T：该组织的全部出跳（from_org == 该组织）于 T 并行启动、各自独立计时

   - 送达的是 L1 组织（tier==1）：解析为 squad_id 走现有链路——FormationSystem.get_squad_units
     → CommandChain.deliver(...) 即时 set_order（含 spread 散点，零改动复用）
   - 送达的是中间层：无实体动作（P0 中间层不做决策，同令透传的下一跳由接力结构本身完成）
   - 战斗职责校验：非战斗叶（建造/劳工/运输）拒收号令（照 issue 既有 is_combat_squad 口径，
     plan 不挡、送达时挡——组织树可能混编，按叶各自判断）
3. order_issued 信号 + EventBus.order_issued 发射（既有口径，org 根 id 作 target）
```

### 4.3 指挥官不变量：中间层不可能无主

**中间层节点 = "某人正在实际指挥着下级指挥官"这一事实的结构化**（创始人裁决）。没有这个事实
就没有这个节点——两个排长合成不了一个元帅：就算把合成物命名为"元帅"，它的实际指挥规模就是
连级，其头目实际上只是连长/大队长。指挥层级不是设计出来的骨架，是**指挥事实的涌现**。

由此：

- **中间层（L2~L4）不存在"无指挥官"的结构状态**。创建中间层的操作本质是**任命统辖**：
  "任命张三统辖这三个排"→ 第一连（指挥官：张三）这个节点随之而生。任命在先，节点随之。
- **L1 叶层可以缺人**：编制模板先行、人员逐步补齐（FORMING 组建中 → ACTIVE 满编/可用）——
  招兵是真实的，架子可以是空的；但叶层没有"指挥下级指挥官"的问题。
- **玩家是动态虚拟层级**：从小卒成长起来，开局≈班长级（L1）；随统辖的指挥链增长逐步成为
  更高统帅（GDD §1.2 的"你是 L5+"是后期状态）。玩家当前直接统辖的组织树顶层 = 玩家位置，
  其层级**不写死**——dispatcher 的"玩家下令"入口取玩家当前位置（附身实体/统帅节点），
  不假设层级数值（等级成长与头衔承认检定 §8.2 挂钩，边界外任务）。
- **运行时校验**：非 L1 节点无 commander 时不得进入 ACTIVE（API 层把关，防脏数据）。

**伤亡是唯一的"位置事实空缺"来源**（过渡态，非稳态），处置靠**补位原则**（succession_rule，
每组织一条可配置规则）：

```
中间层指挥官伤亡 → 按该组织补位原则自动补位：
  ① 班内/组织内军衔最高者顶上（P0 默认——军衔系统未建前以成员指挥属性
     （attributes 五维之"指挥"）代理排序；军衔接入后切换）
  ② 玩家指定（不自动，等任命）
  ③ 补位无人可用（成员空）→ 持续空缺：命令停驻该位置，下级按 default_behavior /
     autonomy 行动（GDD §九 原文语义），面板可见"群龙无首"标记
  ④ 玩家手动重组（撤编上挂 / 跨组织调人）随时可用
```

补位完成的新指挥官就是**真指挥官**（排长顶上连长位，他就是连长——位置因他的实际指挥而
继续成立），不是代理空框。

对命令链的含义：dispatcher **不设"中间层无指挥官"分支**——不变量保证运行中每一跳都有接收者；
需要处理的只有伤亡空缺期的过渡（命令停驻），续传语义 3-P 已裁决见下方「补位引擎实施规格」第 5 条。

#### 4.3.1 补位引擎实施规格（3-P 定稿，Flash 可照做）

**触发点内聚到 manager**（3-F1 实施于 organization_manager，3-F2 只管战斗侧事件进组织侧）：
`remove_stickman(org_id, stickman_id)` 与 `remove_commander(org_id)` 内部检测——被移除者
== 该组织 commander_id 时自动跑补位。死亡/调离/手工撤职同一入口，无独立 `notify_commander_lost`
API（避免 FormationSystem 感知中间层、避免漏挂）。FormationSystem 死亡清理处既有
`_org_api.remove_stickman(...)` 调用即天然触发，零新增挂点。

```gdscript
# manager 内部补位流程（对外新只读 API：get_succession_candidates(org_id) -> Array[Dictionary]
#  供 OrgPanel 展示候选序 / 单测断言；[{id, cmd}, ...] 按 cmd 降序）
1. rule ← org.succession_rule
2. rule == PLAYER_CHOSEN → 不自动补（保持空缺，面板"群龙无首"标记，等玩家任命）
3. rule == RANK_HIGHEST（默认）：
   候选池 = org.personnel ∪ {直接子组织的 commander_id}（去重、剔除空串、剔除被移除者本人）
   ——L1 自然退化为班内成员（无子组织），中间层自然退化为下级指挥官（personnel 通常空，
     直属副官与排长同池竞争符合语义）
4. 候选池空 → {"ok":true,"data":{"filled":false,"reason":"no_candidate"}}（持续空缺态）
5. 非空 → cmd 属性排序取最高（平局按池序稳定——personnel 先于子指挥官）
   → assign_commander(org, id)（既有 API，补上的人就是真指挥官）
   → EventBus.commander_assigned.emit(org_id, instance_id)（既有信号，battle_panel UI 已消费；
     3-F2 新增 FormationSystem 订阅：org_id ∈ 本地 _squads 时回写 squad.leader =
     instance_from_id(id)（有效性校验），L1 队长 UI/光环随之自动恢复）
6. 同时发 report_filed(type="commander_lost")——必报型，无视 autonomy 门控（§4.4）
```

**注入依赖**：cmd 属性排序需查 stickman 实体 attributes.cmd——organization 零出向，
manager `setup()` 追加注入 `attribute_provider: Callable(stickman_id: String) -> float`
（装配层实现：instance_from_id → attributes.cmd，失败返回 -1 沉底）。
军衔系统接入后 provider 换实现，manager 不动。

**停驻命令处置（续传裁决，3-P）**：空缺期到达该组织的命令**直接丢弃**——不做队列、不做
新指挥官上任后续传。理由：①铁律因果链——旧指挥官没收到/没转发的命令在模拟中不存在，
补位者从头指挥；②v1 延迟秒级、空缺窗口极短，续传收益趋零而复杂度（队列/去重/时序）高；
③玩家与 team_ai 是 P0 仅有的两个下令源，重发成本低。新指挥官上任后由下令方重发即可
（team_ai 周期性重评估号令，天然覆盖）。【提案/待定：若后续出现长空缺+高价值命令场景再立续传项】

- **配套改动（批次 2）**：OrgPanel「新建子组织」操作语义 = **任命统辖**（选中若干下级单位 +
  指定指挥官人选 + 命名，一次完成）；不再有"先建空框再填人"的流程。FormationSystem 既有
  "框选编队→任命排长"正是此语义的战斗侧先例。
- **下级长期无指令的行为**：走 `default_behavior`（§3.1 默认战术，现成）+ autonomy_level。
- **越级请示**（GDD §九）：空缺期的下级向上级直接请示——依赖上报通道，登记 §七，P0 不做。
- **指挥官能力（skills）**：影响决策质量与犹豫时间（指挥官决策模型），不是传输系数；批次 3
  只有转述没有决策，skills 暂不消费，登记"指挥官决策 AI"演进项——不发明假机制。

### 4.4 信息上报骨架（GDD §4.2，P0 最小实现——3-P 定稿规格）

**信号**（organization api 新增）：

```gdscript
signal report_filed(org_id: String, report: Dictionary)
# report schema（组织侧只透传不解释）：
# {
#   "type": String,        # 见枚举表
#   "filed_at": int,       # Time.get_ticks_msec()（毫秒；游戏日历时间接入后换 TimeManager 口径）

```

**type 枚举（P0 三种）与 payload schema**：

| type | 触发（combat 侧挂点） | payload |
|------|----------------------|---------|
| `commander_lost` | 补位引擎流程第 6 步（manager 内发，§4.3.1） | `{"prev_commander_id": String, "filled": bool, "successor_id": String}`（未补位时 successor_id=""） |

| `contact` | FormationSystem `_decide_squad_targets` 小队首次获得敌方共享目标（每场接敌一次，脱离接触后重置） | `{"enemy_count": int, "position": Vector2}` |

**autonomy 三档门控**（门控规则是组织学规则，归 organization 侧判定——combat 只发原始事件）：

```gdscript
# api 增量：evaluate_report_gate(org_id: String, type: String, payload: Dictionary) -> bool
# combat 挂点侧用法：if OrgApi.evaluate_report_gate(sid, type, payload):
#                        OrgApi.file_report(sid, {"type": type, "filed_at": …, "payload": payload})
# api 增量：file_report(org_id: String, report: Dictionary) -> void（内部校验 schema 后发信号）
```

| type \ autonomy | HIGH（全自主） | MEDIUM（阈值） | LOW（全量） |
|---|---|---|---|
| commander_lost | **必报** | **必报** | **必报**（组织结构事件，上级必须知道——补位/重组依据） |
| casualty_threshold | 不报 | 存活比 < `var_report_casualty_threshold`（0.30）报 | 每次死亡报（阈值形同虚设） |
| contact | 不报 | 首次报 | 每次报 |

- **传播**：P0 只发**一层**——信号载荷是发起方 org_id，消费方（OrgPanel 详情区显示最近 N 条 /
  后续 AI）自取其 parent_org 归档；"每层再判断是否继续上浮"的逐级衰减是 P1（依赖批次 3 的
  层级语义先跑通）。上报不吃传递延迟（开放问题 §七 保持）。
- **非战斗组织**：P0 三类事件全产自战斗域；科研/工程组织的上报类型（项目完成/资源告急）后续随
  各域深化立项，schema 槽位已留。

## 六、测试策略（3-P 定稿场景设计）

**通用快进机制（三批共用）**：延迟全部来自 transport_layer，测试不碰时钟——

- **单测**（manager/dispatcher/transport 纯逻辑，不进场景树，照 test_command_chain 先例）：
  - v2 预设往返不变量（结构同构+模板逐项相等）、apply_preset 挂接/回滚（批次 1 既有，保持）。

    DISBANDED 子树跳过、同令透传（每跳 order 字典与入参逐项相等）。
  - **transport_layer**：同图坐标直线距离÷速度、跨图不同 location 查 provider、provider 未命中
    fallback 常数、location 同（含同空串）距离 0、INF 走跨图分支、speed=0 短路恒 0。
  - **succession**（manager）：RANK_HIGHEST cmd 最高顶上、平局按池序、L1 退化为班内
    （personnel）、中间层退化下级指挥官（子 commander 进池）、personnel∪子指挥官并池去重、

  - **report 门控**：evaluate_report_gate 三档 × 三 type 全矩阵（commander_lost 恒 true、

- **集成 3-F2**（两幕，进场景树，快进模式跑）：
  - 幕一「下令传播」：搭 L2 连（两 L1 排）+ 注入零距离 provider → 对 L2 issue_to_org(ADVANCE) →
    断言两排成员 behavior 变更（move+目标点）且 order_delivered 各触发一次；受控坐标版
    （单测层）断言 L1 收令时刻 = 各跳延迟之和。
