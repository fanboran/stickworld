# 音乐系统（运行时架构）

> 本文写**引擎侧**的音乐系统怎么组成、怎么工作、为什么这么设计。
> 音乐本身的设计意图见 [音乐设计文档.md](../../设计/音乐/音乐设计文档.md)；
> 离线制作管线见 [音乐制作管线.md](../音频/音乐制作管线.md)。

## 一、组成

| 部件 | 位置 | 职责 |
| --- | --- | --- |
| `MusicDirector` | `core/services/music_director.gd`（Autoload） | 曲目解析、分层播放、交叉淡化、强度档位、stinger、环境音层、压限请求 |
| `AudioManager` | `core/services/audio_manager.gd`（Autoload） | **总线音量的唯一消费方**、音效事件表、音乐压限量的应用 |
| `music_manifest.json` | `stick-world/assets/audio/bgm/` | 作曲家与引擎的契约：循环点、分层、档位、默认音量 |
| 交付资产 | `stick-world/assets/audio/bgm/<cue>/<layer>.ogg` | 每个 cue 一个目录，每层一个 OGG |
| 环境音 | `stick-world/assets/audio/ambience/*.wav` | 风/鸟/蝉/夜虫/海浪/溪流，随情境切换 |

两个 Autoload 的分工是刻意的：**音乐（放什么）与音频基础设施（多大声）分开**。
好处是设置面板的音量逻辑不必知道音乐系统的存在，音乐系统也不必自己算 dB——
而"总线音量只有一个写入者"这条纪律，正是靠这个分工守住的。

## 二、数据契约：music_manifest.json

```jsonc
{
  "version": 1,
  "cue_count": 9,
  "cues": {
    "field_day": {
      "title": "原野·昼",
      "bpm": 72,              // 循环网格：清单是循环信息的唯一真相源
      "bar_beats": 4,
      "bars": 32,
      "beat_count": 128,      // 循环体拍数（= bars × bar_beats）
      "loop": true,
      "loop_offset": 0.0,     // 前奏长度（秒）；纯循环曲为 0
      "key": "D major",
      "duration_s": 106.7,
      "loudness_lufs": -17.0,
      "layers": [
        { "name": "piano",   "file": "field_day/piano.ogg",   "tier": 0, "db": 0.0 },
        { "name": "strings", "file": "field_day/strings.ogg", "tier": 1, "db": -3.0 },
        { "name": "harp",    "file": "field_day/harp.ogg",    "tier": 2, "db": -5.0 },
        { "name": "bells",   "file": "field_day/bells.ogg",   "tier": 2, "db": -7.0 }
      ]
    }
  }
}
```

**为什么循环参数放清单而不是写进音频文件**：Godot 的 `AudioStreamOggVorbis` 不读取
内嵌循环元数据，只认 `loop` / `loop_offset` / `bpm` / `beat_count` / `bar_beats`
这几个属性；若手工在 Inspector 里填，就会出现"文件换了、Inspector 忘了改"的
不一致。清单由渲染管线自动生成，加载时一次性赋值，只有一处真相。

清单缺失或格式不对时，`MusicDirector` **安静降级**（警告一次、不放音乐），
不刷屏报错——音频资产没就位不应该让游戏跑不起来。

## 三、分层播放（纵向混音 / vertical remixing）

一个 cue 的每一层是一个独立的 `AudioStreamPlayer`，**在同一帧 `play()`**。
同采样率、同长度、同起点 ⇒ 采样级同步，不需要额外的对齐机制。

> 为什么不用 `AudioStreamSynchronized`：它虽然能保证同步，但**运行时不暴露
> 逐层音量接口**，而本系统的核心玩法正是"运行中逐层淡入淡出"，因此反而不适用。

强度档位（tier）决定哪些层发声：

| tier | 含义 | 表现 |
| --- | --- | --- |
| 0 | 地基 | 永远在场（钢琴 / Pad） |
| 1 | 常规 | 加入弦乐垫、低音弦、定音鼓 |
| 2 | 点亮 | 加入竖琴、钟琴、木管独奏 |

`set_tier(n)` 会把 `tier > n` 的层淡到 -60dB（不是停止播放——**"关"是淡到听不见，
不是切断**，这样任何时刻都不会有开关式的爆音）。

层的进入顺序固定为 **钢琴 → +弦乐 → +钟琴**（设计文档 §五），
退出顺序相反。调用方只报告强度，不关心具体是谁进出。

## 四、曲目解析（状态 → 曲目）

调用方**只报告情境**（在哪、在干什么），不直接点名曲子：

```gdscript
MusicDirector.set_context("map_type", WorldAPI.MapType.VILLAGE)
MusicDirector.set_context("battle", true)
MusicDirector.set_context("strategic", true)
```

解析规则集中在 `_resolve_cue()`，按"最具体优先"逐层回退：

```
battle > interior > strategic > 地图类型(VILLAGE/ROAD/INDOOR/…)
        > 户外兜底（按昼夜选 day/night）
```

情境由 EventBus 信号驱动（`map_loaded` / `battle_started` / `strategic_map_opened` /
`interior_entered` / `mega_interior_entered` / `game_paused` …），接线集中在
`_wire_event_bus()`，`_safe_connect()` 保证信号不存在时不炸。

**为什么不写 `play_music("field_day")`**：那样调用点就与曲库绑死，加一个状态
就要去改所有调用点，且无法回答"现在为什么在放这首"。集中解析让规则可读、可测、
可改，也让"某个状态没音乐"这类缺口一眼可见（`_resolve_cue()` 返回空即缺口）。

### 昼夜

**当前没有驱动源**——游戏还没有昼夜系统（`WorldState.game_time` 只是累计时间）。
机制已就位：`MusicDirector.set_time_of_day(true/false)` 或
`set_context("night", true)`。将来的昼夜系统只要调这一个入口即可。
在此之前记住：**昼夜不换曲，而是换到同主题的另一首**
（`field_day` D 大调 ↔ `field_night` B 小调，同一串音阶级数），
所以切换不会让人觉得"换台"。

## 五、切换与淡化

| 转换 | 时长 | 曲线 | 理由 |
| --- | --- | --- | --- |
| 换 cue | 3.0s | 正弦（等功率近似） | 72BPM 下约 1 小节；等功率避免中段音量凹陷 |
| 换 tier | 2.0s | 正弦 | 层的进出要"听得见但抓不住" |
| stinger | 0.35s | 正弦 | 短句要立起来，但不要爆音 |
| 环境音 | 4.0s | 正弦 | 环境层变化必须比音乐更慢，否则像开关 |
| 压限 | 0.6s | 正弦 | 压限本身不能听出"台阶" |

切 cue 采用 **重叠淡化**：新 cue 的层从 -60dB 起播并淡入，旧 cue 的层同时淡出，
淡化结束后旧播放器延时释放。两首曲子短暂共存，这是"无缝"的前提。

**为什么不做"量化到下一小节再切"**：本作的切换几乎都发生在场景加载/面板开合
这些本身就有过渡的时刻，3 秒交叉淡化已经足够自然；真正的"小节对齐切换"需要
把切换请求排队并在小节边界触发，复杂度换来的收益在本作的使用场景里很小。
如果将来出现"战斗中实时切段落"的需求，再用 `AudioStreamInteractive` 的
`NEXT_BAR` 补齐（引擎已支持，只是现在不需要）。

## 六、暂停、压限与环境音

- **暂停不中断音乐**：`MusicDirector.process_mode = PROCESS_MODE_ALWAYS`，
  所有 Tween 也用 `TWEEN_PAUSE_PROCESS`。暂停只把音乐压低 9dB。
  音乐被暂停硬切会非常突兀——尤其本作是"看着世界运转"的游戏，暂停时音乐继续
  反而强化"世界还在转"的感觉。
- **战斗让路**：`battle_started` 后音乐压低 6dB（战斗音效与语音优先），
  结算时叠一句 stinger（`sting_victory` / `sting_defeat`）再恢复。
- **压限的实现位置**：`MusicDirector.duck()` 只是**请求**，真正写总线的是
  `AudioManager.set_music_duck_db()`。因为设置面板的音量滑条也写总线，
  两处都写会互相覆盖；把"应用压限量"合进 `_apply_volumes_to_buses()` 后，
  音量与压限量永远是一起算出来的。
- **环境音**：随情境切换（战斗与室内不播——那两种情况不该有环境音抢戏），
  线性音量 0.34（约 -9.4dB）叠在音乐之下。文件缺失时静默跳过：
  环境音是锦上添花，不能因为它没就位就让音乐系统报错。

## 七、怎么改、怎么测

### 常用的调试入口

```gdscript
MusicDirector.play_cue("village")      # 直接放某一首（调试用，绕过情境解析）
MusicDirector.set_tier(2)              # 手动叠满所有层
MusicDirector.set_time_of_day(true)    # 切夜间曲（昼夜系统未接入前的手动入口）
MusicDirector.play_stinger("sting_victory")
MusicDirector.get_state_report()       # 当前 cue / tier / 各层 dB / 压限量 / 情境
MusicDirector.set_enabled(false)       # 整体关闭（自动化测试里避免出声）
```

### 测试

- `tests/integration/test_music_director.gd`：清单完整性（每个 cue 有 bpm/beat_count/
  layers、循环体是整数小节、层文件存在）、情境解析表（各状态 → 期望曲目）、
  tier 与层音量的关系、压限请求转发。**不出声**（用 `set_enabled(false)` 或只测解析）。
- 音频资产本身的客观指标不在 Godot 里测，在离线管线：`tools/music/qa_audio.py --check`。

### 加一首曲子

1. 作曲与渲染（见 [音乐制作管线.md](../音频/音乐制作管线.md) §五）；
2. 新 cue 会自动进 `music_manifest.json`，无需改引擎代码；
3. 若新 cue 要接进游戏流程，在 `MusicDirector.CUE_FOR_MAP_TYPE` 或 `_resolve_cue()`
   里加一条规则。
