## 〇、一页结论

**导出物**：每栋建筑一个目录 `stick-world/temp/bake/<def>_w<格数>/`，内含四件套 + 元数据：

| 文件 | 内容 | alpha | 游戏里干什么 |
|---|---|---|---|
| `albedo.png` | 白天光照下的完整外立面 + 道具 + **接地接触阴影**；1 px = 1 世界单位 | 真透明（`film_transparent`） | `Exterior` 基础图（非交互建筑的唯一图） |
| `albedo@2x.png` | 同上，2 px/单位（`px_per_unit = 2.0`） | 真透明 | 高清档 / 未来放大、缩放抗锯齿源 |
| `glow.png` | **纯发光层**：非发光材质→纯黑、世界全黑、灯全关，只剩自发光 + 光晕 | 建筑轮廓内 alpha=1，框外 0 | 夜里 `albedo × tint + glow` 的加法层 |
| `back.png` | 内景后层（`Interior`）：后墙 / 地板 / 楼板 / 家具 / 暖光 | 真透明 | 可进入建筑的室内底图 |
| `front.png` | 内景前层（`WallFront`）：前墙 + 屋顶 + 门窗框，**窗玻璃真透明** | 真透明 | 交互时 `modulate.a → 0.3` 的那张覆盖层 |
| `meta.json` | 格宽 / px_per_unit / **前墙面基线锚点（世界→像素）** / 门位置与宽度 / 发光件清单 / 层文件名 / 自动自检 | — | 引擎定位 + 门禁校验 |

**核心设计（一条）**：**四张图共用同一台正交相机、同一取景、同一像素网格**（`yaw=0 / tilt=20°`，§0.3 硬约束）。因此"front 叠 back"、"glow 叠 albedo"、"albedo 换 front"全部**不需要任何对位**；`meta.anchor` 只负责把整组图落到世界坐标上。

**本轮实测规模**（`BAKE_NO_DEMO=1` 全量导出）：**60 个 def×宽度档**（26 装配器 × 各自 `*_TIERS` 档 + 3 别名各一处标准档），**0 失败**；产出 **300 张 PNG + 60 份 meta.json**（每栋 5 图 + 1 meta）；其中 **24 栋有发光件**（glow 非空，共 4 类族：lamp/fire/ember/crystal/stained_glass）；**60/60 通过四件套像素自检**（判据见 §2.6）。

**引擎侧叠加顺序**：

```
昼：  draw(albedo)                         （可进入建筑：albedo 后垫 back）
夜：  draw(albedo × tint_night)            再 additive 叠 draw(glow × 1.0)
交互：front.modulate.a: 1.0 → 0.3          （Tween 0.2s，地图与场景图.md §5.2.1）
```

`tint_night = (0.11, 0.14, 0.26)`、`glow_strength = 1.0` —— 取自 `daynight.py` 的**实测标定值**（夜 = albedo×tint + glow×1.0，MAE 0.011）。

> **注意（HD-2D 分叉）**：本节的"夜 = albedo×tint 合成"只适用于 2D 建筑接入路径（bake_export 四件套）。**HD-2D 街景运行时**（proto_hd2d 卡片）月夜档不走合成——用烘卡端多烘的夜版卡 `<卡>_night.png`（`night_mix` 整卡切换 + `night_comp` 亮度补偿），设计口径见 [`HD-2D街景系统.md`](HD-2D街景系统.md) §2.3。

## 一、导出器：`tools/blender_buildings/bake_export.py`

### 1.1 跑法

```bash
# 全量：26 装配器 × 各宽度档（宽度档从 buildings.py 的 *_TIERS 表自动展开）
blender -b --factory-startup -P tools/blender_buildings/bake_export.py

# 过滤（调参与回归用）
BAKE_ONLY=house,smithy1  BAKE_WIDTHS=8,12  BAKE_SAMPLE=32  blender ... -P bake_export.py
BAKE_NO_DEMO=1           # 只导出，不拼游戏内一屏

# 合成演示（系统 python，只用 PIL/numpy；把导出的 sprite 按游戏比例拼成两屏）
python tools/blender_buildings/bake_export.py
```

渲染模式末尾会写 `stick-world/temp/bake/_bake_index.json`（全量索引 + 自检汇总）。

### 1.2 覆盖范围

- **26 个装配器** × **各自 `*_TIERS` 的宽度档**（宽度档不硬编码：`TIER_TABLE` 只登记表名，档位由表的 key 展开）。
- **3 个别名 def**（`plaster_house` / `church` / `chapel`）按 `interiors._FRONT_ALIAS` 解引用到目标装配器（`house` / `cathedral`），各取一处标准档 —— 它们的**内景**是独立内容（各自 `back`/`front`），外立面与目标装配器同图，因此不重复出全部宽度档。
- 道具层走 `props.dress()`（配方键与 `probe_delivery.DRESS_OF` 同源：`smithy1~4→smithy`、`rowhouse→townhouse`）；**没有 DRESS 配方的 def 不摆道具**（`props.DRESS` 现有 14 键），不虚构排布。

### 1.3 每栋的渲染顺序（四件套 + 一次自检）

```
buildings.ASSEMBLERS[asm](wc)         → 外立面 + 接地接触阴影
props.dress(...)                      → 道具层（与外立面同 builder 之外的独立对象）
interiors.build_back(def, wc)         → 内景后层 (+ L 内景定尺)
interiors.build_front(def, wc)        → 内景前层（切后半栋 + thin_glass 真透明窗）

union(外立面, 道具, back, front) → 取整取景矩形 → 一台正交相机（2x / 1x 两次改分辨率）
  ① albedo@2x  白天 3 光 + 渐变天光，film_transparent
  ② albedo     同相机 1x
  ③ glow       非发光材质→纯黑(dn_black) + 灯全关 + 黑世界 + add_halos(光晕)
  ④ back       室内暖色点光 + 室内环境
  ⑤ front      与 albedo **同光照**（同一套 3 光 + 天光），保证换层不跳色
→ _verify()：量四张 PNG 的 alpha 包围盒，结论写进 meta.verify
```

关键点（都由踩坑换来的，别改）：

- **glow 层是"全帧加法层"**：非发光几何被换成纯黑，但**仍然不透明**（alpha=1）。这是 `daynight.py` 的既定做法 —— glow 用 additive 混合整块贴上，黑区加 0、无副作用；不要试图把它改成"只有发光像素 alpha>0"，那会在引擎里需要两次 blend。
- **front 与 albedo 同光照**：若 front 用另一套光照，前墙覆盖到 albedo 上会出现色差（0.3 淡出时尤其明显）。
- **接地接触阴影只在 albedo**：`interiors.crop_back_half(drop_shadow=True)` 明确删掉 `shadow_*` 面，所以 front 不含阴影 —— 这是设计，不是漏。
- **glow 的光晕**：Blender 5.2 合成器不可用，光晕只能由 `daynight.add_halos()` 的 billboard 贴片出；引擎侧仍建议补真 bloom（阈值 0.75 起）。

## 二、烘焙契约

### 2.1 目录与命名

```
stick-world/temp/bake/
  _bake_index.json                全量索引（entries + 自检汇总）
  _game_screen_report.json        两屏演示的落位报告（供核对锚点）
  <def>_w<格数>/
      albedo.png                  1x（1 px = 1 世界单位）
      albedo@2x.png               2x
      glow.png
      back.png
      front.png
      meta.json
```

- `<def>` = 装配器/别名 def_id，**与 `interiors._WIDTHS` 的键一致**；文件名里**不出现空格/中文**。
- 宽度档 `<格数>` 是**格数**（4/6/8/12/16），不是像素。
- 命名唯一真源 = `bake_export.bake_list()`；入库脚本与引擎路由都从 `_bake_index.json` 读，不各自拼字符串。

### 2.2 坐标系（Blender ↔ 建筑局部 ↔ PNG）

沿用 [`建筑室内结构.md`](建筑室内结构.md) §2.5 的三套坐标，本文只补 PNG 侧的本轮落地：

| 坐标系 | 定义 |
|---|---|
| Blender 世界 | 正面 = **−Y**；+Z 向上、地面 z=0；建筑以原点为中心、进深向 ±Y 各半、X 关于 0 对称 |
| 建筑局部（Godot） | x ∈ [0, width×32]（原点 = 建筑左缘）；y = 0 为地面线，向上为负 |
| PNG 像素 | **自顶向左**为 (col, row)；`meta.frame.res_1x` 给画布尺寸 |

取景是**正交**且 `yaw=0`，所以屏幕 right 轴 = 世界 +X、up 轴 = `(0, sin20°, cos20°)`。映射：

```
col(u) = (u − u0) × ppu                 u = right·p = p.x
row(v) = res_y − (v − v0) × ppu         v = up·p  = p.y·sin20° + p.z·cos20°
ppu    = 1.0（albedo/glow/back/front）或 2.0（albedo@2x）
```

**取景矩形取整**（`floor/ceil`）使 `res = 取景宽高 × ppu` 恰为整数 $$\Rightarrow$$ **1x 下 1 世界单位 = 恰好 1 像素**（无半像素缩放糊）。这是"1 格 = 32px"能精确成立的前提。

### 2.3 锚点语义（`meta.anchor`）—— **前墙面基线**

```jsonc
"anchor": {
  "kind": "front_wall_baseline",
  "world": [0.0, -75.0, 0.0],   // 建筑横向中心 × 前墙面(y = -depth/2) × 地面(z=0)
  "px_1x": [211.0, 391.65],      // 该点在 albedo.png 里的 (col, row 自顶)
  "px_2x": [422.0, 783.3],
  "pivot_col_1x": 211.0,         // 世界 x=0 的像素列（= 建筑横向中心，用于对齐自检）
  "ground_row_1x": 391.65        // 地面线 z=0 在该 y 平面上的像素行
}
```

**为什么锚在"前墙面 × 地面 z=0"而不是包围盒底边**：包围盒底边被两件事污染 —— ① 接地接触阴影向下伸出 20~35px；② 台阶/门前板等前凸件的 y 偏移在 20° 俯角下把投影像素拉低。用"前墙面落地线"这个**语义明确的世界点**，`meta` 才在改几何/改阴影后依然自洽。

**引擎落位（唯一一处算术）**：设建筑根节点在 `(cell_x × 32, ground_y + 96)`（`construction_project.gd:322`），Sprite2D `centered = false`：

```gdscript
sprite.position = Vector2(width_px * 0.5 - anchor_px[0], -anchor_px[1])
# width_px = width_cells * 32；根节点局部 y=0 = 地面线 = 建筑基线
```

于是锚点像素恰好落在 `(cell_x×32 + width_px/2, ground_y + 96)` —— 建筑横向中心 × 建筑基线。

### 2.4 三层叠加顺序

```
                 ┌──────────────────────────────┐
  z 高           │ glow.png  (additive, 夜)      │  albedo×tint + glow×1.0
                 │ front.png (WallFront 覆盖层)  │  interact: a → 0.3
                 │ back.png  (Interior 底图)     │  常驻或交互时可见（见下）
  z 低           │ albedo.png (Exterior 基础)    │  昼 = 原图
                 └──────────────────────────────┘
```

**两种建筑用两种叠法**（本轮明确，供引擎实现）：

- **非交互建筑**（大多数）：`albedo` (+ 夜间 `glow`)。`back`/`front` 不出场。
- **可进入建筑（A 类剖视）**：把 `front.png` 当 `Exterior` 用（它与 albedo **同网格**，替换不跳位），其后垫 `back.png`，交互时 `front.modulate.a → 0.3`。这样"娃娃屋剖视"成立：屋顶留在 front 图上，前墙化掉、内景露出。
  > 这与 [`建筑室内结构.md`](建筑室内结构.md) §2.4「待引擎侧确认 #4：是否把 `_front` 拆成 `_front` + `_roof`」直接相关：**若拍板要"屋顶不参与淡出"，需要管线把 front 再拆一张 roof**（成本 = 多一次"隐藏屋顶渲一张"）。本轮未拆，如实登记为待拍板项。

**窗玻璃的两个透明度来源**（不可互相替代，见 §2.4 该文档）：① `front` 窗格像素真透明（常驻，"站在街上从窗看见屋内"）；② `front` 整层 `modulate.a`（交互时）；两者相乘。

```jsonc
  "px_per_unit": { "x1": 1.0, "x2": 2.0 },
  "frame": { "u0": -211, "u1": 211, "v0": -95, "v1": 366, "res_1x": [422,461], "res_2x": [844,922] },
  "anchor": { ... 见 §2.3 ... },
  "door": { "x": -64, "w": 52, "h": 150, "sill": 8,

  "tier": { "depth": 150, "eave_h": 219, "total_h": 331, "plinth_h": 14, "overhang": 52, "bays": 2 },
  "layers": { "order": ["albedo","back","front"],
              "composite_day": "albedo",
              "composite_night": "albedo*tint_night + glow*1.0" },
  "files": { "albedo": "albedo.png", "albedo2x": "albedo@2x.png", "glow": "glow.png",

  "shadow": { "contact": "baked_in_albedo", "note": "..." },
  "glow": [ { "family": "lamp", "mat": "lamp", "strength": 2.5, "color": [...],

  "glow_count": 2,
  "dress": [ { "prop": "barrel", "x": -150.0, "y": -86.0 }, ... ],

```

字段纪律：**除 `frame/anchor/door.px_*/glow.px_1x/verify` 外，一律世界单位或格数**；像素字段一律显式带 `px` 后缀并注明是哪一档（`_1x`/`_2x`），避免 v2 `_shift_meta()` 那种"含出血 vs 不含出血"两套口径混用（[`建筑室内结构.md`](建筑室内结构.md) §2.5 末）。

### 2.6 自动自检（`meta.verify`）

导出后立刻量四张 PNG 的 alpha 包围盒（`alpha > 0.06`），判据：

| 判据 | 阈值 | 含义 |
|---|---|---|
| `front` 的 **横中心** = 世界 x=0 像素列 | ≤ 3px | 同网格、同中心（阈值 3px 的理由见下） |
| `back` 的 **横中心** = 同一列 | ≤ 3px | 内景与外皮同中心（圆塔/退台塔改判 `back ⊆ front`） |
| `front` 的 **顶行**（屋面线）= albedo 顶行 | ≤ 3px | 换层不跳位 |
| `front` ⊆ `albedo` 的包围盒（x 与顶行，3px 容差） | — | albedo 是 front 的超集 |
| `back` 跨度 = `interior_width_px × ppu` | ≤ 3px | `clip_to_walls` 生效 |

阈值取 3px 而不是 1.5px：**几何本身就带不对称**（实测 `mage_tower_w4` 的尖顶/侧凸把 front 中心推偏 2.5px，w6/w8 则 0.5px）；而"换错相机 / 漏改分辨率"这类真错会偏几十到几百 px —— 3px 足以把两者分开。60 栋里只有这 1 栋落在 1.5~3px 区间，其余都在 0.5px。

**刻意不把 albedo 的 bbox 与 front 划等号**，因为 albedo 多出三样东西（全是设计使然，记进 `verify.content_delta`）：

1. **道具**（`props.dress`）常单侧 → 中心偏移（实测最大 23.5px，`cathedral_w16`）；
2. **接地接触阴影**比建筑宽、比地面线低（实测伸出地面线下 **6.8~62.2px，均值 32.5px**）；
3. `interiors.crop_back_half(y_cut=0)` 会连同**后半栋的侧向凸出**（后殿 / 扶壁 / 横厅）一起切掉，而它们在正面投影里本来就露出一截 → 实测 albedo/front 跨度差最大 158px（`cathedral_w16`）。**这是真发现**：见 §八-1。

`meta.verify.OK` 是入库门禁；不过的栋在批量汇总里打 `!!` 并打印原因。`BAKE_VERIFY_ONLY=1` 可在**不重渲**的前提下重算全部自检并重写 meta/索引（判据迭代后回填现有 60 栋就靠它）。

## 三、阴影三层方案

阴影拆三层，**只有第一层进 sprite**，另两层由引擎出（成本/质量/可控性各占其位）：

| 层 | 做法 | 载体 | 状态 |
|---|---|---|---|
| **① 接地接触阴影** | 建模期 `buildings.contact_shadow()` 的阶梯贴片（`shadow_near/mid/far` 三档递淡），渲进 `albedo` 的 alpha 内 | **烘入 albedo.png**（`shadow.contact = "baked_in_albedo"`） | ✔ 已实现；实测伸出地面线下 **6.8~62.2px（均值 32.5px）**，全在 96px 落地箱内 |
| **② 太阳长影** | 由引擎按**太阳方位**画一枚椭圆/斜切贴片（不烘进图，因为昼→昏→夜方向与长度都在变；烘死会与光照脱钩） | 引擎运行时（一张椭圆 shadow sprite） | 提案/待定：贴片与参数由管线另出一张 `shadow_ellipse.png` + `meta`，或在引擎里程序化生成 |
| **③ 檐下 AO** | **已几何化**：`roof_gable(ao_mat=...)` 在檐口下方压一道 9px 暗带（浅墙用 `shadow_ao`、深色木板墙用 `shadow_mid`），随屋面形态走 | 烘入 albedo（几何面，不是贴片） | ✔ 已实现（`buildings.py` 常量表注释） |

为什么长影必须引擎侧：20° 俯角下屏幕高度混入了"进深×sin20°"，同一栋建筑在正面光照与低角度光照下的投影长度差很大；烘死一张长影会在早晨/傍晚读作"影子方向不对"。**接触阴影可以烘**是因为它只跟"物体贴地"有关，与光方向无关。

> 引擎侧已有 `stains/decal` 等贴片机制；长影贴片建议直接走同一套 `Sprite2D` + `modulate` 路径，不新增系统（提案/待定，未实现）。

## 四、入库规范

**目标目录**（提案/待定，本轮产物仍在 `stick-world/temp/`，避免污染 `assets/`）：

```
res://assets/buildings/gen/
  <def>/w<格数>/
      albedo.png  albedo@2x.png  glow.png  back.png  front.png  meta.json
  index.json            # 由 bake/_bake_index.json 转换而来（加 res:// 前缀 + 校验哈希）
```

规范：

1. **只收 `verify.OK == true` 的目录**（门禁脚本读 `meta.verify`，不过则拒绝入库并打印原因）。
2. **`meta.json` 直接沿用本契约**，不改字段名；`index.json` 由导出索引转换，**唯一真源是管线**。
3. **Godot 导入设置**：`albedo`/`glow`/`back`/`front` 一律 **Filter = Nearest（1x 档）**，`albedo@2x` 用 **Linear/Mipmap**；关闭 `Fix Alpha Border` 之外的自动处理；不要开 `Premultiplied Alpha`（图是直通 alpha）。
4. **不裁剪**：四件套必须整组入库、同一 `<def>/w<n>` 目录（裁掉 `frame` 后锚点就失效）。
5. **命名不许改**：文件名与 `meta.files` 强绑定；重命名 = 改契约。
6. 版本化：`index.json` 里记 `source`（`tools/blender_buildings` 的 git commit）与 `baked_at`，便于回溯是哪版几何/材质出的图。

## 五、`modules/building_gen/api.gd` 重定向方案（**只写方案，不改游戏代码**）

现状（只读核对）：`api.gd` 用 `const _BUILDING_SCENE_PATHS` 把 def_id 映射到 `buildings/*.tscn`，`load_building_scene(def_id)` 是外部模块唯一的取建筑入口；`get_default_building_def_ids()` 供建造系统注册。v3 baked 资产**目前没有任何入口**。

### 5.1 目标

把"建筑 = 手搭 .tscn"改成"**建筑 = baked sprite 组（优先）+ .tscn（兜底）**"，且**不动模块边界**（外部仍只走 `api.gd`）。

### 5.2 方案（加，不删）

```gdscript
## —— 新增：baked 资产注册表（管线产出，随 assets/buildings/gen/index.json 走）
const _BAKED_ROOT := "res://assets/buildings/gen/"
const _BAKED_FALLBACK := ...          # 无 gen 资产时回退现有 _BUILDING_SCENE_PATHS

## 返回某 def 在某宽度档下的 baked 图集描述；无资产返回 {}。
static func get_baked_sprite_set(def_id: String, width_cells: int) -> Dictionary:
    # 读 index.json（可缓存）→ 命中则返回 {"albedo":…, "albedo2x":…, "glow":…,
    #   "back":…, "front":…, "meta":…, "phase": "baked"}

## 新的统一取建筑入口（外部模块改用这个；旧名保留为薄包装，避免一次大改）
static func build_building(def_id: String, width_cells: int, parent: Node) -> Node:
    # 1) baked 命中 → 组装 Sprite2D 组：
    #      Exterior(Sprite2D.albedo)  [+ 可交互时 Interior(Sprite2D.back) + WallFront(Sprite2D.front)]
    #      落位按 meta.anchor（§2.3 的一行算术）
    # 2) 未命中 → 回退 load_building_scene(def_id).instantiate()
    # 3) 两者都没有 → push_warning + null
```

### 5.3 迁移纪律

1. **入口唯一**：外部模块只调 `api.gd`；`_BUILDING_SCENE_PATHS` 仍是私有 const（现契约不变）。
2. **def_id 映射表**：管线 def（`house`/`smithy1`/`warehouse`…）↔ 运行时 def（`placeholder`/`timber_cottage`/`smithy_lv1`/`warehouse`/`stone_warehouse`/`manor`/`grand_hall`）**需要一张显式表**（[`建筑室内结构.md`](建筑室内结构.md) §4.3 已登记为未做项）。建议放在 `api.gd` 私有 const，键为运行时 def，值为管线 def + 首选宽度档。
3. **宽度档路由**：建筑被拉宽时，选**最近的已导出档**，剩余按"居中 + 两侧用 `back` 补缝"（[`建筑室内结构.md`](建筑室内结构.md) §2.2 契约）。本轮所有档都已导出，路由只需查表。
4. **兜底不删**：`_BUILDING_SCENE_PATHS` 的 .tscn 在 v3 全量验收前**保留**，提供滚回路径（对应 §4.4「α 降级为兜底」的结论）。
5. **门禁**：`build_building()` 在 baked 命中时必须校验 `meta.verify.OK`，否则拒绝并回退 —— 防止坏资产静默进游戏。
6. **不在本轮范围**：z_index 落地（[`建筑室内结构.md`](建筑室内结构.md) 待确认 #1）、`Interior.visible` 常驻（#3）、`_front` 拆 `_roof`（#4）都是引擎侧前置，先做这三条，baked 组装才谈得上"窗户透内景"。

## 六、与建造网格的对齐规则

三条数字（全部有出处）：

| 数字 | 值 | 出处 |
|---|---|---|
| 格 | **32px** | `PlacementGrid.CELL_SIZE`；`construction_project.gd:322` |
| 建筑基线（落地线） | **`ground_y + 96`** | `construction_project.gd:322`；`建筑与定居点.md` §4.3.1 |
| 落地箱垂直范围 | **`ground_y ~ ground_y+96`** | `建筑与定居点.md` §4.3.1 |
| 火柴人 | 130px = 1.70m | `buildings.STICKMAN_H`；交接档 §0.3 约束 3 |

对齐规则：

1. **`grid_w_px = width_cells × 32`，必须精确**（`meta.grid_w_px` 是引擎可用它反查档位的量）。导出侧已由"取景取整 + ppu=1"保证建筑本体的 1:1 像素无缩放。
2. **落地锚 = 建筑基线**：sprite 的前墙面基线锚点落在 `(建筑横向中心, ground_y+96)`（§2.3 那行算术）。因此建筑"种"在落地箱底边上，与 `vis.position = Vector2(cell_x×32, ground_y+96)` 完全一致。
3. **接触阴影落在落地箱/地面带内**：albedo 的阴影比锚点低 6.8~62.2px（< 96px 落地箱高），所以阴影压在地面带的上沿附近，读作"建筑把地面踩实了"，且**不会**越过地面带下缘。
4. **出檐是出血，不进碰撞**：albedo 画布比 `grid_w_px` 宽（出檐 = min(宽 × 20.5%, 60) 绝对封顶，左右各伸出），这段像素**只用于观感**；占地/阻挡/交互区一律用 `grid_w_px` 与既有 `PassageBarrier`（`建筑与定居点.md` §4.3）。引擎若按画布尺寸算占地会多算 2 格左右，**必须按 `meta.grid_w_px`**。
5. **相邻建筑间距**：出檐出血会盖住邻栋的落地裙边，因此**最小净距 ≥ 1 格（32px）**；演示图按 1~3 格排布（交接档 §三.7「禁止完美直线排」）。
6. **宽度档要与建造宽度落在同一档**：`width_cells` 是 4/6/8/12/16 之一；非档位宽度（如 10 格）按 §5.3 最近档 + 补缝。

## 八、已知落差（诚实清单）

1. **`_front` 未拆 `roof`**：交互时整张 front（含屋顶）被 0.3 加权，屋顶也跟着化掉 —— 与 `地图与场景图.md` §5.2.1「屋顶常驻」冲突（[`建筑室内结构.md`](建筑室内结构.md) 待确认 #4）。本轮按现状交付，待拍板。
2. **`front.png` 不是 albedo 的纯子集（本轮实测发现）**：`interiors.crop_back_half(y_cut=0, z_cut=eave)` 按"檐口以下 + y>0"删面，会连带删掉**后半栋的侧向凸出**（大教堂的后殿/扶壁/横厅在正面投影里本就露出一截）。实测 `cathedral_w16` 的 albedo 比 front 宽 **158px**（其余 def 0~34px）。后果：§2.4 的"用 front 当 Exterior 替换 albedo"在 `cathedral` 这类带侧翼的建筑上会**丢侧翼**。修法（提案/待定）：给 `build_front` 传一个"只切后墙与室内、保留侧向凸出"的裁剪口径，或按 §八-1 拆 roof 时一并处理。
3. **太阳长影未实现**：目前只有接触阴影（烘入）+ 檐下 AO（几何化），引擎侧长影贴片是提案，未做。
4. **glow 层无 bloom**：Blender 5.2 合成器不可用，光晕只到 billboard 贴片；夜观感的"辉光"要靠引擎 bloom 补（阈值 0.75 起）。
5. **道具只覆盖 14 个 DRESS 配方**：多数 def 的道具是空的；空立面在游戏尺寸下仍会读作"秃"（交接档 §0.3 约束 8）。
6. **接缝/背景残留**：`back` 未裁到内景包围盒（[`建筑室内结构.md`](建筑室内结构.md) §5.3 同款问题），`glow` 是全帧层（含大量黑像素，贴图内存偏高）。
7. **演示图的地面是兜底色**：合成演示跑的时候 `ground_tiles/` 正被**同 worktree 的地面返工任务线**清空重出，段文件不存在，于是按任务书允许的兜底走了"纯色夯土带 + 文字标注"；`ground_tiles` 的 `pieces`（落地裙边/门前小径）也只有 manifest、无导出 PNG，演示里以建筑自身的接触阴影代替裙边。这是**演示图的观感损失**，不是导出契约问题（早一轮段文件在位时，同样的铺带代码出的是真实分段纹理）。
8. **入库目录 `res://assets/buildings/gen/` 尚未创建**：产物仍在 `stick-world/temp/`，入库脚本未写（§四为规范，不是已完成状态）。
9. **比例遗留**（门宽 0.60~0.76m vs 规范 0.9~1.0m、瞭望塔段高、20° 俯角抬升屋顶屏占）来自交接档 §二/§三，本轮未动 —— 它们会改变 `meta.door` 与 footprint，**改口径时需重跑导出**。
10. **1x 与 2x 是两次独立渲染**（不是缩放）：更稳但更慢（全量 60 栋约 25 分钟）。若只为省时间，可改成"渲 2x 后用 Blender `Image.scale()` 降采样"，代价是 1x 会带一次重采样（当前选择保清晰度）。
