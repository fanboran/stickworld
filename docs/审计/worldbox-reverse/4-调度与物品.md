## 一、调度架构真值表

**总结构**：`ActorManager.cs:336`（`BuildingManager.cs:66` 同构）每帧调 `_job_manager.updateBase()` → `JobManagerBase.cs:23-30` 依序跑 **Pre → Parallel → Post** 三桶；每桶遍历本批次的 job 列表。批次是并行与容量单元：**每批 256 个 Actor**（`JobConst.cs:3` MAX_ELEMENTS=256），装满自动开新批（`JobManagerBase.cs:174`），`Config.parallel_jobs_updater` 开启时 `Parallel.ForEach` 跨批多线程（`JobManagerBase.cs:118`）。

**桶划分依据**（BatchActors.cs:45-78 createJobs，无 Pre 桶 job）：

| 桶 | 系统（job id : 容器） | 跳帧真值 |
|---|---|---|
| Parallel（可跨批并行，只读/复位类） | prepare；update_timers（=c_main 全量：帧内标志复位+计时器）；update_visibility；update_stats | 全部每帧 |
| Post·更新域 u1-u10 | u1 在船内、u2 儿童列表、u3 精灵动画（仅 is_visible）、u4 死亡动画、u5 当前地块、u6 冰冻、u7 增益效果、u8 计时器、u10 平滑移动；update_shake/hovering/pollinating/death（c_check_deaths 用后清空 :485-497） | **u7 skips=20**（:61），其余每帧 |
| Post·行为域 b1-b6（编号即执行序） | b1 受力、b2 校验当前敌人（c_check_attack_target）、b3 找敌、b4 任务校验器、b5 寻路移动、**b6_0 决策**（c_make_decision，消费后清空 :392-404）、b6 跑 AI 行为、b55 自然死亡 | **b3 skips=5、b55 skips=20**（:65,:69），其余每帧 |

**跳帧机制**（Batch.cs:94-105 runUpdater）：job 每次执行完后 `current_skips = Randy.randomInt(0, random_tick_skips)`，期间整桶跳过——**不是"每 N 帧跑一次"的固定节拍，而是"跑完随机歇 0..N 帧"**，均值 N/2，天然去同步（各单位不同帧跑，抹平尖峰）。真值只有三档：0（每帧）/5/20。

**三层降本手法**（对"哪些系统进哪桶"的补全）：

1. **帧内标志级联**：Parallel 桶 `updateParallelChecks` 每帧复位 `_update_done/_beh_skip`（Actor.cs:9321）；Post 桶 u1→b55 依次检查（Actor.cs:9370-9379 skipUpdates/skipBehaviour），谁真正处理了该单位就让下游全部跳过——**每帧每单位最多一个行为系统实际干活**（如 b5 已在寻路移动则 b6 决策/AI 全跳）。
2. **事件容器（一次性队列）**：c_make_decision / c_check_deaths 只装"有待办"的单位，消费后 `_cur_container.Clear()`。决策三件套：行为树空闲任务 `make_decision`（BehaviourTaskActorLibrary.cs:460-470）→ `BehMakeDecision.execute` 把 actor 加进 `batch.c_make_decision`（BehMakeDecision.cs:11）→ b6_0 消费：`DecisionHelper.makeDecisionFor`（DecisionHelper.cs:5-26）跑效用决策选 DecisionAsset → `setTask`。**决策无全局定时器**——单位行为栈空了才排一次队，队列每帧随到随消。
3. **可见性门禁**：u3 动画只在 `is_visible` 时更新；updateDeathCheck 只在无窗口遮挡时跑（BatchActors.cs:487）。

容器本体：`ObjectContainer<T>` = HashSet + 延迟增删（to_add/to_remove，`ObjectContainer.cs:9-13`），遍历前 `checkAddRemove()` 合并——增删不中断当帧遍历。

## 二、城市建造决策链（CityBehBuild.cs，813 行）

**节拍**：城市行为树节点 `execute`（:21-46）——`timer_build > 0` 跳过；被占领/危险中跳过；否则 **timer_build 重置 5s** 后跑一次 buildTick（CityFastUpgrades 调试项降到 0.2s）。城市级 5s 决策拍，与个体单位无关。

**buildTick 决策序**（:48-132）：

1. **修路**：>2 建筑且文化可修路 → 随机选一建筑，连路到最近 2 个可修路建筑（:50-57, :677-715）。
2. **单工地约束**：全城同时只允许一个 `under_construction_building`（含扫描既有建筑补登记 :62-76），有在建直接返回——**建造吞吐天然被钳制**。
3. **生成候选**：按种族 `actorAsset.build_order_template_id` 取 `CityBuildOrderAsset.list`（**声明式建造序列表**），逐条过 `canUseBuildAsset`（:201-259）：min_zones / 建房限流（housing_free>10 不再建房 + getHouseLimit）/ 类型上限 / check_full_village（有人无房不建）/ required_pop / required_buildings / requirements_orders（**沿 upgrade_to 升级链递归找前提建筑** :261-286）/ requirements_types / 码头需海位。再按 `BuildingAsset.cost` 分流有资源/无资源。
4. **选单**：候选表 `GetRandom()` **均匀随机**，无效用加权（:88）。
5. **升级单**：随机选同 ID 已有建筑 → 沿 upgrade_to 升一级并扣费（:103-116, :150-164）。
6. **选址**（tryToBuild :304-355）优先级：训练假人→兵营周围 2 环随机；码头→海洋区专找；`build_prefer_replace_house`→随机覆盖低 priority 住房原址；否则 `fillPossibleZones` 按布局约束过滤 zone（build_place_single 独占/batch 成群/borders 靠边 :357-367）→ `tryToBuildInZones` 随机 zone 序（build_place_center 先试中心区），布局模式 `CityLayoutTilePlacement` 四种：**Random / CenterTile / Moonsteps（棋盘跳格）/ CenterTileDrunk（中心+60% 概率醉步挪邻格）**（:431-497）；无 spread 文化且有城心时取**离城心最近**点位（:390-426）；农田类校验 region+邻区 `can_be_farm` 地块 **>30**（:617-634）。
7. **落地**：addBuilding + setUnderConstruction + **开工一次性扣资源**（:351-353）。

## 三、物品域 schema

**双轨制**：资源（粮食/金币等）走**计数袋**，装备走**世界实体**，互不相通。

### 3.1 装备槽（ActorEquipment.cs:6-49 / EquipmentType.cs）

- 6 槽常量 SLOTS_AMOUNT=6：**Weapon / Helmet / Armor / Boots / Ring / Amulet**（无副手、无腿部；饰品双槽）。字段即槽（helmet/armor/weapon/boots/ring/amulet）+ Dictionary<EquipmentType,Slot> 索引。
- 槽规则（ActorEquipmentSlot.cs:49-67）：setItem 按 `item.asset.equipment_type` 自动入槽；同槽已有则先 takeAway（旧件脱手成世界实体）；穿脱即 `pActor.setStatsDirty()` 触发重算；**cursed 词缀锁槽**（canChangeSlot=false）。
- 存档只存 Item 的 long id 列表（ActorEquipment.cs:74-90）。

### 3.2 物品定义（ItemAsset.cs / Item.cs / ItemData）

| 层 | 字段（真值） |
|---|---|
| ItemAsset（静态配置，继承 BaseAugmentationAsset：group_id/priority/combat_actions/各 action 回调） | equipment_type/subtype；attack_type(Melee/Range)+projectile+path_slash_animation；**cost 三组**：cost_gold + cost_resource_id_1/amount_1 + cost_resource_id_2/amount_2；rarity、quality(R0_Normal..R3_Legendary)、**mod_rank/mod_type/mod_can_be_given**（词缀位）；durability=100、rigidity_rating；metallic/colored/animated/path_gameplay_sprite/material；**pool/is_pool_weapon/pool_rate**（装备池权重）；name_templates（命名生成器模板列表）；item_modifier_ids |
| ItemData（存档态） | durability、asset_id、material、**modifiers:ListPool\<string\>**、by/from（制造者/势力+色）、creator_id/kingdom_id、kills、created_by_player |
| Item（运行时） | 归属双态 **unit_has_it / city_has_it** 互斥（:244-258，挂 Actor 或 City 仓库）；耐久 getDamaged（eternal 词缀免伤 :88-98）；词缀增删按 **mod_type 互斥**（同组只能一条 :219-236）；reforge(pTries) 重掷词缀+改名（:154-165）；transmute 按装备池换形态+reforge(5)（:172-197）；价值=equipment_value+mod_rank*2、品质取词缀最高（ItemTools.cs:57-62） |

物品是独立管理器 `World.world.items` 的系统对象（Item.cs:30）——**逐件实例、可掉落/回收/收藏/销毁**。出生装备优先从世界回收无主旧物，否则 `asset.default_weapons` 随机新造（Actor.cs:7212-7241）。

### 3.3 资源袋与掉落（ActorBag.cs:9-12 / DropsLibrary.cs）

- ActorBag = `Dictionary<string, ResourceContainer>` + last_item_to_render（渲染用缓存），**无容量上限、无逐件实体**（ActorBagExtensions.cs:10-53 add/remove）；`giveInventoryResourcesToCity` 直接倒进城市仓库（Actor.cs:7201-7209）。
- 掉落：`DropAsset`（12 类 DropType：Seed/Bomb/Building/Mineral/Creep/TraitRain/EquipmentRain/Magic/Generic/Tile/Status/Trait），DropsLibrary 注册 **58 个**掉落资产；每个资产带 `action_launch/action_landed` 回调（60+ 个静态 action 函数：雨/炸弹/尘埃/诅咒…，DropsLibrary.cs:1045-2006）+ 掉落视觉参数（falling_speed=3.2 等）+ `drop_type_low/high`（落地改写 TileType 视觉）。**掉落表=「资产定义+落点回调」工厂**，掉率组织在调用侧（如 biome/mineral 模板 `$spawn_mineral$`）。

## 四、对本项目启示【提案/待定】

### 4.1 分帧调度 → 战斗规模化30fps（docs/项目/交接/战斗规模化30fps-进度与交接.md）

本项目现状：TeamAi 层已用 `beat_interval=0.5s` 固定节拍+DECIDE/BUILD 相位轮转（team_ai.gd:206-238）；单位层已有"物理/AI 30Hz 对半交错"分帧刀（交接档 ③）；待办 C 是"决策类逻辑每刻只更新 1/N 单位"。WB 给出三个可抄的替代/补充答案：

1. **决策用事件队列，不用定时器轮询**：WB 单位决策不在"每 N tick 全员轮一遍"，而是行为栈空闲才进 c_make_decision 队列、当帧消化。本项目单位 AI 摊销若做成 1/N 固定轮转，N 大时决策延迟= N×tick 周期；改"空闲才排队+队列消费上限/帧"可让排队长度自然等于闲置单位数，接战期决策量反而集中可控。
2. **随机跳帧代替固定相位**：`randint(0,N)` 间隔（真值 0/5/20 三档）让低频系统（找敌 5、状态结算 20）不同单位不同帧跑，避免 1/N 轮转的整批共振；实现成本极低（job 结构体里一个 int）。
3. **帧内标志级联**：每帧每单位"动过一次就短路下游"（b5 在移动→跳过 b6 决策），配合 Parallel 桶集中复位——这是单线程下把 O(系统数×单位数) 削成近似 O(单位数) 的关键一招；本项目 battle_sim 若按"移动中单位不重决策"短路可白拿一笔。批容量 256+跨批并行的结构在 Godot 多线程（若开）也可平移：批次即并行任务粒度。

### 4.2 物品 schema → inventory 模块（modules/inventory/，设计 docs/设计/系统/10-武器装备与个人库存.md 与 背包与装备系统.md）

1. **双轨制值得抄**：本项目 ItemStack(def_id+count) 逐件堆对玩家背包正确；但 town-life NPC 职业（铁匠/伐木/矿工）的产出/搬运若也走逐件实体会虚增存档与 GC——WB 的 ActorBag 计数袋（`Dictionary<id,amount>`，零 UI、可整体倒库）是 NPC 侧携带/城市仓库的轻量参照（ItemStack 批量聚合即可近似，不必逐件）。
2. **装备槽对照差距**：本项目 5 槽（主手/副手盾/头/胸/腿）vs WB 6 槽（weapon/helmet/armor/boots/ring/amulet）——互有取舍（本项目有腿部与副手，WB 有饰品双槽），槽位机制同构（按 asset 类型自动入槽、同槽替换自动卸下），ItemDef.Category→槽位映射已够用；可补的是 **cursed 锁槽**类"穿脱限制"字段位。
3. **ItemDef 后续深化时的字段位清单**（当前 ItemDef 缺）：cost 多资源组、durability/耐久、Rarity 四档品质、**mod_type 互斥词缀组**（词缀系统的最小骨架就是 asset.item_modifier_ids + data.modifiers + mod_type 查重三件）、name_templates 命名模板、pool/pool_rate 装备池（掉落/商店按组抽+解锁门槛）。这些与设计文档 10 的装备规划吻合时再引入，现阶段只作 schema 预留参考。
